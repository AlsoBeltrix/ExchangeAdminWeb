Queue item 14 – Migrations interface

Three shapes for the Migration Status view. Nothing is decided and no plan is written. These are throwaway HTML, not app code – they use the repo's own Bootstrap so the look is honest, but none of the buttons do anything except the ticks, which update the selection bars, and the "Open panel" button in mockup C.

What is wrong with the page today. The Migration Status tab is one wide batch table. Clicking a batch injects a second user table inside the row, so everything below is pushed down. The bulk-action bar sits above the table and scrolls out of sight while you tick rows below it, and the ticket confirmation appears at the row's own position, which may be off screen. That is the "burying controls" and "hiding selected items" you named.

Current candidate – attention-first

A's two panes kept, but the page leads with what needs a person, multi-select is gone from browsing, every batch has its own address so browser Back works, and bulk removal is described by a rule instead of assembled by ticking rows.

Earlier explorations, kept for reference.

A – Split pane

Batch list in a narrow left column, the selected batch's detail in a right column that is always on screen. Each side scrolls independently and has its own pinned action bar at the bottom.

Gains: you can see the batch you picked and its users at the same time; no nesting; batch actions and user actions never move.

Costs: the user table gets a narrower column, so error text is tighter. Two selections can be live at once (batches left, users right), which needs care so the wrong one is not acted on.

See A at 100–2000 batches and 137–2000 users →

B – Drill-down to a batch page

The list is only a list. Clicking a batch opens its own full-width page with a Back link. Two screens: list then batch.

Gains: one job on screen at a time, which is the strongest answer to UI-induced error; the widest room for the user table and for anything items 12 and 13 add; the two selections can never be confused because they are never both on screen.

Costs: you cannot watch several batches at once; comparing two batches means going back and forth; it is the largest change to how the page is navigated.

C – Keep the table, pin the bar, detail in a drawer

Today's single table stays. The toolbar and selection bar are pinned so they never scroll away, and batch detail opens in a panel that slides over the right-hand side instead of expanding inside the row.

Gains: smallest change and the least risk to the existing click-gating tests; keeps the sortable columns you have now.

Costs: the drawer covers the table it came from; the per-row action column stays dense, which is the shape the Developer Guide warns about for destructive actions; it fixes the symptoms without changing the density the item complains about.

All three show where queue items 12 (a future "complete after" time) and 13 (per-user ticks with their own action bar) would sit, because item 14 has to leave room for them.
