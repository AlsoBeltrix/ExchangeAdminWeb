DOWNLOADCSVASYNC NAMES THREE CALLS, the only one of the nine that does.
GetSortedBatches( is the opening pin and is named in its own right rather than
folded into the build, because it applies the pane's filter and sort to the
whole batch list and is what makes this export the filtered, sorted set rather
than the raw one - a promise MigrationStatusPageTests pins separately, in the
same test that reads the button's tooltip. BuildCsv( is the projection and
JS.InvokeVoidAsync( the closing pin.

EXPORTOPENREPORTASYNC IS THE ONE CASE WHERE THE ENCODE IS THE OPERATION. There
is no projector to name: R24c requires the file to be the bytes already on
screen, so the payload is the report text the store holds and the only
operation-scale work in the handler is walking it twice, once for UTF-8 and
once for base64. System.Text.Encoding.UTF8.GetBytes( therefore opens the
window. That is the same strict reading of rule 1 that let
MessageTrace.ExportCsv pin CsvEscape(, a local pure helper: operation-scale
LOCAL work counts, and the scale here is a report R24 describes as tens of
thousands of lines. Its Complete message is a deliberate LITERAL - the label
already names the address, and a literal cannot disagree with a field another
handler owns.

DOWNLOADREPORTEXPORTASYNC IS THE HEAVIEST AND THE ONLY NON-CSV EXPORT IN THE
SHAPE, and its early return had to become an if/else. THE SCANNER FORCED THAT,
not taste. ProgressScan.ActivitiesIn takes the FIRST "<name>.Complete(" after
the Begin as the window's close, so a refusal Complete written above the
transfer would have unpinned JS.InvokeVoidAsync( on EVERY path, including the
successful one - exactly the trap 49ee687 recorded on AdminEventLog's three
Completes for the next slice to hit, met here for the first time. One Complete
below both named calls holds both ends, and the success flag is read off
bytes: nothing to package is a refusal the build RAN and reached, so it
completes FALSE with the banner's own words rather than falling out of scope to
the dispose fallback, whose "This did not finish." would be wrong about work
that finished and said no. Behaviour is otherwise identical - the if/else has
no code after it but the Complete, and the finally runs the same on both paths.

NO SNAPSHOT WAS ADDED ANYWHERE ON THIS PAGE, and that is a decision rather than
an omission. isDownloadingCsv is a member of this page's IsBusy predicate and
all three handlers raise it ABOVE the yield, so the page is shut for the whole
window and nothing can replace migrationBatches, expandedBatch or userReport
under the work. That is exactly the difference from BitLockerRecovery and
BlockedSenders earlier in this batch, which are ClickGate-unconverted, gate
nothing, and did need the capture.

count in the label where there is one. The transfer MECHANISM is deliberately
untouched in all three: docs/DownloadMemoryRetention-Plan.md proposes replacing
it with streaming and is a DRAFT, not approved.
