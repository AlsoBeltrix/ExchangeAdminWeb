# kd-30: MigrationStatusPageTests.StripRazorComments is still a regex and mis-reads a @* inside a C# string

**Severity**: LOW - latent test-infrastructure defect (the kd-20 family). `ExchangeAdminWeb.Tests/MigrationStatusPageTests.cs` about 2482 (18 callers).
**Status**: Verified on branch; awaiting merge and codex review

## Evidence

At `fix/kd-misc` `ea087879`. Trigger: a `"@*"` literal in a scanned block. Predicted failure: text blanked to the next `*@`.

## Approach

Re-read at `ea087879`:

- `ExchangeAdminWeb.Tests/MigrationStatusPageTests.cs:2527-2528` -
  `private static string StripRazorComments(string source) => Regex.Replace(source, @"@\*.*?\*@", "", RegexOptions.Singleline);`
  - removes from any `@*` to the next `*@` wherever they are, a C# string included.
- 18 callers; the inputs are the whole page (`StripRazorComments(ReadPage())`, e.g. `:234`, `:772`, `:2460`) and markup
  slices with no @code block - the `BatchActionsMenu` render-fragment member (`:267`), row markup (`:2246`), a page
  prefix (`:2347`).
- kd-20 routed a page to `ClickGateSource.BlankComments`. That view reads every input as a component, so a slice with no
  @code block is markup and its Razor comments are blanked - which is what these callers need (kd-20's other route, the C#
  view for method bodies, does not blank Razor comments and would be wrong here).

What changes: `StripRazorComments(source) => ClickGateSource.BlankComments(source)`, documented. The view blanks Razor
comments in the markup and in the code - measured, not assumed: a `@* *@` inside an @code block is blanked as comment
trivia (a probe on a fixture, and Migration.razor's 20 such comments in its render-fragment templates, `:1273`-`:1535`),
while a `"@*"` string survives. It also blanks C# comments, which callers scanning for markup are better without.
Blanked, not deleted, so offsets hold.

Declared files: `ExchangeAdminWeb.Tests/MigrationStatusPageTests.cs` (the helper and the guard), this record.

Mutation: the regex restored.
