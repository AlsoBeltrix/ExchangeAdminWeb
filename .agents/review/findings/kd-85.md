# kd-85: the job service's cancel read-back and start-up sweep notifications are unprotected reads

**Severity**: LOW, pre-existing, the kd-84 class. (1) `Services/Jobs/BulkJobService.TryCancelJob` (about 197) reads the job
back after the cancel landed, outside any try; a store failure on that read shows and files the cancel as failed though it
happened (Admin Bulk Jobs files failed and throws to the circuit; Comms-10k shows "The job action failed" and files refused or
failed; the module's cancel mail is not sent). (2) `InitializeAsync` (about 143-151): the start-up sweep's completion
notifications stop at the first failed read, so the remaining interrupted jobs get no completion mail and nothing is logged.
**Status**: Fixed on branch, verified; closes on guard proof. Two parts, one commit each
**Branch**: `fix/kd85` (worktree `D:\source\ExchangeAdminWeb-wt\kd85`, from master `917b56ff`)
**Commit**: one per part - (1) `f6b8b9f6`, (2) the commit that adds this line (its SHA in the implementer's hand-back)
**Reviewer**: implementer (candidate)

## Evidence

At `f6b56994`: the kd-84 record's candidates.

## Approach

- (1) the read-back inside a try: a failed read after a landed cancel is logged as a notification failure, the cancel is
  reported as it happened (the write's own result), the hook skipped; test with the kd-84 stand-in shape; mutation: the try
  removed.
- (2) per-job try in the sweep: a failed read is logged once and the loop continues with the next interrupted job; test
  with two interrupted jobs and the first read failing - the second is notified; mutation: the try removed.
- Shared service; the base bump is already owed for this release.

  `Comms10k_CancelJob` "RefusedOrFailed" (1176);

guard only read. Reachable as described: M0 below is the file as at `917b56ff`, and both cases of the test fail on it - the

- **The read in one try with the hook** (`Services/Jobs/BulkJobService.cs` 208-217; the comment 205-207, the remarks on
  `CancelJob` 186-193). After the write and `JobChanged`, as before, the read and the call to the hook are in a try of their
  own - the shape kd-84 gave the runner's tail (`FinishAndNotify`, 761-770 at this commit). A throw:
  - is logged once, an error with the read's own exception, in the words every failed completion notification is logged in:
    "Completion notification for bulk job {Job} failed (non-fatal)" (216). The Constitution: "Notification failure must not
    change or mask the backend operation result. Catch notification exceptions and log them separately."
    (`docs/ProjectConstitution.md` 82);
  - runs no hook, the hook being given the job as read;
  - goes no further: the method answers true (218) - the write's own result, the job Cancelled - so `CancelJob` and
    `CancelOwnedJob` answer as for any cancel that took effect.
- **Every caller reports it as the cancel it was**, its code unchanged (read at this commit, the lines above): Admin Bulk Jobs

- **Unchanged**: a read that works - the same job to the same hook, no line; a cancel whose write did not land (`TryFinish`

- **Version**: none here. `BulkJobService` is a shared service, so a base app version bump is owed (2.36.0 at this commit);
  as briefed, it is the supervisor's and is not made here.

**Operator-visible change.** None for a cancel whose read-back works: every cancel while the jobs database takes its reads.
When the database fails the read right after it took a queued job's cancel, the cancel is shown and audited as made - Admin
Bulk Jobs' "Cancellation requested ..." and its row Success, Conference Rooms' row Success, Comms-10k's "Cancellation requested

## (2) The start-up sweep's notifications past a read that fails (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `f6b8b9f6` (part (1)'s commit; these lines as at `917b56ff`): `InitializeAsync` (119-153 there)
reads the unfinished jobs (`GetActive`, 135), marks every one Interrupted (`InterruptAllNonTerminal`, 136), says how many
(139) and then, in a fire-and-forget task (143-151), reads each back - `_repository.Get` (147) - for `NotifyCompleted` (149),
whose try covers the hook but not the read. A read the store failed threw out of the loop and out of the task:
- the jobs after it in the list were never read back, so their modules' completion hooks did not run - Conference Rooms' and
  Comms-10k's mail for an interrupted job, Message Analysis' mail and its audit row;
- the task is discarded (`_ = Task.Run(...)`, 143), so its exception was never observed and nothing was logged, though the
  comment above it (140-142) calls the notifications fully guarded.

The statuses stood: every job was marked Interrupted before the loop. Reachable as described: M0 below is the file as at
`f6b8b9f6`, and the test fails on it - no hook for the second job. That nothing was logged is read, not run: the test stops
at the hook.

- **A try per job** (`Services/Jobs/BulkJobService.cs` 156-165; the comment 154-155, the remarks 119-125). Inside the loop,
  each job's read and the call to its hook are in a try of their own. A throw:
  - is logged once, an error with the read's own exception, in the words every failed completion notification is logged in:
    "Completion notification for bulk job {Job} failed (non-fatal)" (164), the job named - the Constitution's rule
    (`docs/ProjectConstitution.md` 82), as in part (1);
  - runs no hook for that job, the hook being given the job as read back;
  - goes no further: the loop goes on to the next job, whose read and hook are made as before.
- **One try per job, not one around the loop**: a try around the loop would log the first failure and end the sweep there,
  the jobs after it unnotified as before (M2 below).
- **Unchanged**: the migration, the prune, and the read and write before the loop - on the start-up path, where a failure
  still stops the start as before; a read that works - the same job to the same hook, no line; `NotifyCompleted` and its own
  try; the task still fire-and-forget, so start-up does not wait for mail. The comment's "fully guarded" (147-149) now holds.
- **Version**: none here; the base bump owed for `BulkJobService` (2.36.0 at this commit) is the supervisor's, as in part (1).

**Operator-visible change.** None while the jobs database takes its reads at start-up. When it fails the read back of one
interrupted job, that job gets no module completion mail, as before, and the log now says so - a failed completion
notification naming the job - where it said nothing; the interrupted jobs after it get their mail, where they got none. The
job lists show every one Interrupted, "Interrupted by application restart.", as before.

## Found while doing it, not fixed (one finding per commit)

- **Admin Bulk Jobs reloads its job list after a cancel or a removal outside any try.** `AdminBulkJobs.razor` `CancelJob`
  (357) and `RemoveJob` (411) `await RefreshJobs()` once the row is filed, and `RefreshJobs` (222-231) calls
  `LoadJobsFromStore` (201-208) - up to three reads of the jobs store - with nothing around it; the page's first load (188)
  and its Refresh button (45) take the same path. A store that fails that read after a cancel or a removal that happened
  throws out of the handler to the circuit, the row already filed as it should be. Since part (1) it is what an operator of
  that page meets when the store fails the reload as well as the cancel's read-back. The kd-82 (2) class (Conference Rooms'
  `RemoveJob`, fixed there) on Admin Bulk Jobs; nothing is misfiled. Pre-existing, LOW (a store failing a read right after
  it took a write); a candidate, from reading, not run. Conference Rooms' and Comms-10k's reloads after a cancel are guarded
  (`OnJobChanged`, `LoadOwnedJobsAsync`, each catching and logging).

## Known gaps

- After a failed read the module's completion mail for that job - and, for a Message Analysis job, the audit row its hook
  files - is not sent, as before, in both parts: the hook is given the job as read, and the read is not made again (the
  brief: a failed read is a notification failure). The log carries it.
- (1) The callers' reporting after the fix is read, not run: each page files and shows what the service answers, at the lines
  cited in part (1), and no page test drives a read-back failure - their store failures are a jobs database with no tables,
  which fails the cancel's write first, a path this change leaves as it was.
- (2) The sweep is fire-and-forget with no handle a test can await, so the test waits up to 30 s for a hook and then looks: a
  mutant that ends the sweep early fails only after the whole wait, and a sweep slower than 30 s on a starved machine would
  fail it too (none seen).
- The stand-ins fail the read with a renamed table and recover at the service's next line, a test device; a locked or
  unreadable database was not used. The lines are asserted through the test's logger; the production sink is not exercised.
