# kd-94: on-premises "this mailbox has no archive" may no longer read as not-found, making most ToCloud checks Undetermined

**Severity**: HIGH, unverified - sweep item 3. `Services/ExchangeServiceBase.cs` about 782-794: `Get-MailboxStatistics -Archive`
catches only `when (IsNotFound(ex))`; anything else becomes "Get-MailboxStatistics -Archive failed" and `MigrationService.cs`
about 225-229 files Undetermined. The old build caught every throw. Reviewers recall on-premises Exchange filing "no archive"
under InvalidArgument, not NotFound (assumption). About 80% of prod's October ToCloud reads hit a no-archive mailbox.
Independent of kd-89.
**Status**: Open - awaiting the owner's one dev Migration check. The logs were searched (2026-10-31) and carry no
no-archive failure's text, so the code is left unchanged rather than guessing its shape
**Branch**: `fix/sweep-b` (record only, no code) | **Commit**: the commit that adds this line (its SHA in the implementer's
hand-back) | **Reviewer**: implementer (candidate)

## Approach

- Treat "no archive" as "archive size zero", recognised by the error's own words and category as the logged shape shows,
  while every other failure stays Undetermined; test with the stand-in shaped from the dev log line once the owner's check
  produces it (if the check passes on dev, close as not a defect). Mutation: the recognition removed.

## What was searched (implementer, 2026-10-31, read-only, no live call)

The brief: find the exact text of a no-archive failure from `Get-MailboxStatistics -Archive` in the dev and prod logs; recognise
that shape if found, otherwise leave the code and say what was searched.

- **Files.** Every app log in both instances: `D:\inetpub\ExchangeAdminWebDev\logs` (30 files, `app-20260923.log` to
  `app-20261030.log`) and `D:\inetpub\ExchangeAdminWeb\logs` (30 files, `app-20261002.log` to `app-20261031.log`). Also,
  read-only, the trace and audit JSONL under `E:\WWWOutput\ExchangeAdminWeb`, and the repo (records, docs, tests) for any
  captured copy.
- **Patterns** (case-insensitive): `archive`, `Get-MailboxStatistics`, `-Archive`, `-Archive failed`, `archive size could not
  be read`, `have an archive`, `no archive`, `archive mailbox`, `ArchiveGuid`, `MailboxStatistics`.
- **Found:**
  - prod: 104 `On-prem mailbox size for ...` lines; after them 23 `On-prem archive size for <address>: <n> GB` (an archive
    was read) and 81 `No archive mailbox found for <address>` (74 of them on 2026-10-08);
  - dev: 5 size reads, all 5 `No archive mailbox found` (2026-09-23 x2, 2026-10-07 x2, 2026-10-22), all on the old build;
  - no `-Archive failed`, no `archive size could not be read`, no `Get-MailboxStatistics` anywhere; the trace JSONL holds only
    `OnPremMailboxSizeRequested` steps, none with an error or exception.
- **Why none of it is the shape.** Every `No archive mailbox found` line comes from the old build's catch-all, which logged
  that sentence and nothing of what was thrown (`32d28f96`, `GetOnPremMailboxSizeAsync`: `catch { _logger.LogInformation("No
  archive mailbox found for {Email}", emailAddress); }`) - so the lines prove only that the archive read threw, for about 78%
  of prod's on-premises size reads, never its category, reason, error id or words. The build that would log them
  (`Get-MailboxStatistics -Archive failed: <reason>`, aud-a23o) has run on dev since 2026-10-29 without a single Migration
  check or Recipient Lookup (sweep, "Never run"), and is not on prod.

So the shape the recognition would key on is unknown, and the code is left as it is: recognising a guessed category or
sentence could read a real failure as "no archive" and pass a ToCloud quota check on a mailbox whose archive was never read.

The same base read (`ExchangeServiceBase.GetOnPremMailboxSizeAsync`) serves Recipient Lookup's on-premises sizes
(`RecipientLookupService` about 263), where the same failure reads as a warning that the archive size could not be read; the
one check below settles both. The Exchange Online archive reads (`MigrationService` about 1707, `RecipientLookupService`
about 172) are not this row.

## The check that settles it (the owner's; read-only)

The sweep's checks 1 and 3, either is enough:

1. **Dev, Migration page, one minute.** A ToCloud eligibility check of one on-premises mailbox with no archive. Eligible (or a
   real reason): not a defect - kd-89's sentence rule or the structural test already reads it; close this row. "Could not be
   determined" naming `Get-MailboxStatistics -Archive failed: ...`: the defect, and that line in `app-<date>.log` is the shape.
2. **On-premises Exchange shell, two minutes:** `try { Get-MailboxStatistics -Identity '<on-prem mailbox with no archive>'
   -Archive -ErrorAction Stop | Out-Null; 'row' } catch { '{0} | {1} | {2} | {3}' -f $_.CategoryInfo.Category,
   $_.CategoryInfo.Reason, $_.FullyQualifiedErrorId, $_.Exception.Message }`.

With the line in hand the fix is the Approach above: that shape, and only it, is "no archive" (archive size zero, no marker);
every other failure stays Undetermined; a stand-in built from the logged line; the mutation removes the recognition.
