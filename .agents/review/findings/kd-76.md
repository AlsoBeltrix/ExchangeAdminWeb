# kd-76: Blocked Senders starts the unblock before it looks at an already-cancelled token

**Severity**: MEDIUM - `Services/BlockedSenderService.cs` about 86-104: `RunAsync` is started, the submission guard
`TrySend()` (about 172) checks only its own state, and the token is observed only by `WaitAsync` afterwards. A cancel
during the page's awaited protection check (`Components/Pages/BlockedSenders.razor` about 470) passes a cancelled token
in; with a warm pool the worker claims Sent and runs `Remove-BlockedSenderAddress` before `WaitAsync` sees the cancel.
The sender is unblocked after the operator cancelled; the page records an unknown outcome or a success.

## Approach

- `ThrowIfCancellationRequested` before `RunAsync` starts, and the token made part of the submission guard so a cancel
  that lands before the claim wins (the claim fails, nothing is sent). Tests: a pre-cancelled token - no command runs,
  filed Cancelled; a cancel racing the claim - either the claim wins and the result is Undetermined/Success, or the cancel
  wins and nothing is sent, never both. Mutation: the pre-start check removed.

## As implemented (implementer, 2026-10-27; lines at this commit)

Read first, confirmed at `ec5a19f7`: `UnblockSenderAsync` started `RunAsync` (86) before anything looked at the token;
the page's `ConfirmUnblock` awaits its permission re-check and its protection gate before the call
(`Components/Pages/BlockedSenders.razor` 383, 413) and passes its activity's token (470). With a warm pool the borrow
completes inside `RunAsync` and the pooled call runs on the thread pool at once, so its `TrySend` - which compared only the
submission's own state - could claim Sent before the waiter's `TryAbandon`. On a circuit the waiter resumes on the
circuit's dispatcher, which widens that window whenever the cancel lands before the claim.

1. **Nothing starts on a token already cancelled** (91-95). After the address check, before the submission and `RunAsync`:
   a cancelled token throws the kd-57 cancellation, "Cancelled by the operator before the unblock of X was sent, so nothing
   was changed and the sender is still blocked." No connection is asked for. The sentence is now built in one place,
   `CancelledBeforeTheSend` (156-159), which the existing cancel path (133) uses too - its words unchanged. Not the
   framework's `ThrowIfCancellationRequested`, whose "The operation was canceled." the page would show and file
   (kd-57's rule); the same check, in the app's words.
2. **The token in the guard** (`UnblockSubmission`, 178-206). The submission takes the caller's token. `TrySend` with the
   token cancelled moves Pending to Abandoned and refuses - so a cancel made before the claim wins, as the caller's giving
   up does, even when the waiter has not seen it yet. A claim made first stands. A pool retry of a call that already
   claimed stays sent (the retry runs only when the first attempt provably sent nothing - the existing aud-a76 rule).
   `IsAbandoned` (205) reads the state.
3. **A refusal by the guard is a cancel, however the wait ends** (114-153). The wait is restructured so every path where
   the run has ended reaches one check: when the guard refused, nothing was sent, so the method throws the kd-57
   cancellation rather than return the failed result the refusal leaves inside `RunAsync` ("The unblock was abandoned before
   it was sent"). That covers the waiter resuming after the run ended (the circuit case) and the run ending before the
   wait saw the cancel. A wait that gave up while the run was still going is unchanged: `TryAbandon`, then the cancel, the
   bound's failed result, or `BlockedSenderUnblockUnconfirmedException`.

Kept, as briefed: a cancel after the send stays Undetermined (the claim won, so `TryAbandon` fails); a wait that runs out
before the send stays a failed result. The page is unchanged: its existing catch (`BlockedSenders.razor` 481) files the
cancellation Cancelled with the service's sentence, the servicer note kept, the administrators notified as before.

Version: Blocked Senders 1.5.2 -> 1.5.3 (`Modules/ModuleCatalog.cs` 641-644). The service is the module's own; no shared
service changed, so no base bump. Test helper: `MigrationStubExchange.TraceEvents()` (731), beside `AuditEvents()`.

**What the operator sees**: an unblock cancelled during the checks before it - or before Exchange Online's call claims
the send - says "Cancelled by the operator before the unblock of X was sent, so nothing was changed and the sender is still
blocked." and the sender stays blocked, where the unblock could go through and be reported unknown or done. Nothing
offered or withdrawn.
