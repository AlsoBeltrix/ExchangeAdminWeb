# kd-21: BlankComments reads a C# comment inside a markup @if body as text

**Severity**: LOW - latent. After kd-12, `ClickGateSource.BlankComments` blanks C# comments inside `@code` and markup `@{ }` blocks and Razor comments in markup, but a C# comment inside a markup `@if` / `@foreach` body is still read as text. No page has one today.

## Evidence

At `fix/kd-misc` `1f11fe45`. Trigger: `@if (x) { // note` in markup. Predicted failure: a guard reads the comment as code (a false match or a false miss).

## Approach

Re-read at `0b68d60d` (kd-20's commit):

- `ExchangeAdminWeb.Tests/ClickGateSource.cs:73` - `BlankComments(string source) => RazorSyntax.ComponentCommentsBlanked(source);`:
  C# comment trivia in @code regions and in markup `@{ }` blocks, Razor comments in the markup. The body of a markup
  `@if` / `@foreach` is neither: it is code with markup elements in it, so Roslyn cannot be pointed at it whole, and its
  comments were left as text.
- The record suggests `ExtractMarkupBlock` (kd-11) for where the bodies are. It finds an assertion's block by balancing
  raw braces over the markup view; that is the wrong tool here, because the comments being looked for are exactly the text
  that can hold a stray brace and end a body early.

What changes: `BlankComments` runs one more pass, `BlankControlFlowComments`, over kd-12's view. Every `@if`, `@foreach`,
`@for`, `@while`, `@switch`, `@lock`, `@using`, `@do` and `@try` in the markup (not escaped, not in @code, not in a
Razor comment, not in an attribute value) has its parenthesised header skipped with Roslyn tokens and its body walked
from the brace, as are its `else`, `else if`, `catch`, `finally` and `while` continuations. In a body, a markup element at
code level (start tag to matching end tag, or a self-closing or void one) and a `@:` line are skipped as markup; a C#
literal is skipped as one Roslyn token, so a `//` in a string is not a comment; a `//` or `/*` at code level is a comment
and is blanked; and braces are counted at code level only. A construct nested in an element is found by the same scan and
walked on its own. Offsets hold. `MarkupView` (kd-11) reads through `BlankComments`, so it gains the same blanking.

Declared files: `ExchangeAdminWeb.Tests/ClickGateSource.cs`, `ExchangeAdminWeb.Tests/ClickGateTests.cs` (the guard),
this record. No module version: test infrastructure only.

## Known gaps

- A heuristic, not Razor's parser. A `<` in a C# expression inside markup that is immediately followed by a letter
  (`@if (a<b)`) is read as a tag; the element is then never closed, the walk stops, and later comments in that body stay
  unblanked - a miss, never a blanking of code. Text at code level is assumed to be C#, which is what Razor requires.
- HTML comments (`<!-- -->`) are still not blanked.
