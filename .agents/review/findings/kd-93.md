# kd-93: Defender's four-minute enrichment budget also cancels the Site column

**Severity**: HIGH at scale - sweep item 10. `Services/DefenderEndpointDeviceService.cs` about 100 and 554-560: the hunting
enrichment and `ApplySitesAsync` share one four-minute budget; when hunting spends it, the site read (`Services/AdSiteDirectory.cs`
about 57) is cancelled and every Site reads "(unavailable)"; the Site filter keeps those rows, so a site search returns the whole
inventory. Site is the module's primary output (decision 2026-10-14).
**Status**: Fixed on branch, verified; closes on guard proof
**Branch**: `fix/sweep-b` (worktree `D:\source\ExchangeAdminWeb-wt\sweep-b`, from master `81ae0762`)
**Commit**: the commit that adds this line (its SHA in the implementer's hand-back) | **Reviewer**: implementer (candidate)

## Approach

- Read and match sites outside the hunting budget (one directory read plus in-memory matching); test: hunting budget spent,
  sites still filled; mutation: the shared budget restored.

## The fix (implementer, 2026-10-31; branch `fix/sweep-b` from master `81ae0762`)

- **`Services/DefenderEndpointDeviceService.cs`**:
  - `ListDevicesAsync`: the four-minute `enrichmentBudget` now lives only around the hunting enrichment, and whether it
    fired is read as the hunting ends (`huntingDeadlineReached`), so time the site read takes afterwards cannot make a
    finished hunting run read as "The four-minute enrichment deadline was reached". The site read is called without it.
  - `ApplySitesAsync(devices)`: its own budget, `DefaultSiteReadDeadline` (two minutes), begun after the no-directory and
    no-devices returns and measured on the same `EnrichmentTimeProvider` seam. It bounds the wait for the directory worker,
    the read and the matching, exactly as the shared deadline bounded them; reaching it marks the unevaluated cells
    "(unavailable)" and reports `SiteMapRead` false as before. Nothing else in the site path changed: one worker per
    directory (cdr-d7's admission), cooperative stop, completed matches kept.
  - Why two minutes: the read is one directory query whatever the device count (one `Get-ADRootDSE`, one `Get-ADObject` for
    the subnets) and the matching is in memory, so a bound of minutes is a stall, not a slow directory. Worst case the
    response now takes up to two minutes more than the hunting's four; before, those two minutes were the Site column.
- **`Modules/ModuleCatalog.cs`**: Defender for Endpoint Devices 1.6.17 -> 1.6.18 (module-scoped behaviour), with its
  history line; `ModuleCatalogTests` pin moved. `AdSiteDirectory` is unchanged.
- Help checked (Known Failure Class 5): the page's banner ("Site details could not be completed for every device ...") and
  the deadline reason ("The four-minute enrichment deadline was reached ...") stay true; no page, README or module doc text
  describes the site read sharing the deadline, so none changes. No page line moved.
- The approved plan's D7 ("bound the enrichment work") is kept: the hunting keeps its deadline and the site read gains its
  own bound; only cdr-d7's implementation choice of one deadline across both is undone, which the sweep and this row name as
  the defect.
