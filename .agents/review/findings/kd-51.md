## Approach

- Back to groups retires the active load (token-aware) and clears the busy state so a stale load can neither publish nor clear a newer load; test with a never-completing stand-in; mutation: the retire removed. In place.

Taken as written, in two halves, both needed:

- **`BackToGroups` lowers `isLoadingMembers`** beside the token advance it already made, so leaving retires the load
  whole: it can no longer publish, and it no longer holds the view.
- **`LoadMembers`' `finally` lowers the flag only while its own token is current.** kd-19 made that lowering
  unconditional on purpose, and said why: Back advanced the token without lowering the flag, so a token-guarded lowering
  would have left it stuck. Back lowers it now, which turns that reasoning round - left unconditional, a retired load
  returning late would lower the flag of a newer load still reading and leave that view clickable mid-load. Whoever holds
  the current token lowers the flag: the load, from its `finally`, or Back, which retires it. It is the shape
  `GroupManagement.SelectGroup` already uses for `isSelecting`.
- **`isChanging` and `isResolving` are not reset by Back.** They have no token, and the registry's reason for not
  resetting them from outside (an old operation's `finally` would later lower a flag a new view raised) still holds.
  The finding names the member load.
- The registry's prose said, in three places, that a flag reset in `BackToGroups` was considered and rejected for all
  three flags. It now says the member load is the exception since kd-51, and why.
- Self-Service Groups 1.14.0 -> 1.14.1 (patch, per the brief). Page-scoped; no base app bump.

## Known gaps

- **A hung load still shows its progress activity** ("Loading members of ...") until the backend returns: the activity
  is the load's own `using`, and Back cannot complete it without saying a read finished that has not. The view is usable
  again, which is what was stranded.
- **The same strand for a change or a paste resolve, not fixed.** A membership change or a bulk resolve whose backend
  never returns still keeps `isChanging` or `isResolving` up after Back, so Manage members stays disabled until a
  refresh. Not this finding, and not the same case: the registry records the door staying shut while a write started
  before Back is in flight as the design, and neither flag has a token to make a reset safe. Reported, not admitted.
- In this fixture the second group's load waits behind the hung first one at Delinea's token lock, so the second group
  opens but its list waits for the first request. Whether that happens live depends on where the backend hangs; the page
  no longer adds to it.
- No live check; no rendering (no bUnit harness).
