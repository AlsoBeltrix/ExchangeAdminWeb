## (1) The runner: a failed read of the queue is made again (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `bc126312`: `DrainQueueAsync` (410-438) read the queue - `_repository.GetActive()` (419), under
`_gate`, inside the loop's one try - and a throw from that read went to the catch (430-437): "Bulk job pump loop faulted",
`_pumpRunning = false`, and the loop ended. `EnsurePump` (376) is the only thing that starts the loop and `Enqueue`
(160-168) its only caller, so after a failed read nothing ran until the next submit, in any module, and start-up flips every
job still Queued to Interrupted (`InitializeAsync`, 131). In kd-80's case - the store failing a read just after the job's
write - the runner's first read is that read. Reachable as described: M1 below is the loop as it was, and fails both tests.
Of the brief's two shapes the retry is the one the code supports: while the runner is stopped, only a submit, a cancel or
a removal raises JobChanged, so re-arming on the next event would wait for the very submit the finding is about.

- **The read's own try** (`Services/Jobs/BulkJobService.cs` 443-451, its catch 452-468). The read and the no-work check
  are as they were, under `_gate`, the flag cleared in the same lock when nothing is queued (445-450); only the `return`
  moved below the lock (479-480), after the recovery line. A throw:
  - is counted (454); below `QueueReadAttempts` (6, at 369) the loop waits `QueueReadRetryDelay` - 1, 2, 4, 8 and 16 seconds
    (372), about half a minute in all - through `WaitBeforeQueueRead` (375-376: `Task.Delay`, a test seam of the shape of
    `JsonlLogService.WriteLineBytes`) and reads again (465-467);
  - at the sixth failed read, clears the flag under the lock and then says so once - an error, with the read's own
    exception: "The bulk job queue could not be read in 6 attempts; the runner has stopped and starts again when the next
    job is submitted" - and returns (455-462). The flag goes first, so a submit made after the line finds the loop stopped
    and starts it. A store that keeps failing is read six times and left, never spun on; the next `Enqueue` starts the loop
    again, as before.
- **While it waits the flag stays raised**, so a job submitted meanwhile is taken by this loop's next read rather than
  starting a second loop: one loop and one job at a time, as the class remarks require.
- **One line per run of failed reads**: the error above when the loop stops, or, when a read works again, one warning with
  the last failure's exception - "The bulk job queue could not be read N time(s); it was read on the next attempt and the
  runner carries on" (470-477) - after which the count starts from nothing. Before, a failed read was one error and the end.
- **Unchanged**: `RunJobAsync`, `EnsurePump`, `Enqueue`. The outer catch (485-493) still ends the loop, flag cleared, on
  anything else that escapes; its comment now says the read is handled above.
- **Version**: none here. `BulkJobService` is a shared service, so a base app version bump is owed (2.36.0 at this
  commit); as briefed, it is the supervisor's and is not made here.

**Operator-visible change.** None while the jobs database is healthy. When it fails a read - locked, or unreadable for a
moment - a job submitted then starts once the queue can be read again, within about half a minute, without a second
submit, and the log says so once (a warning). A database still unreadable after that leaves the job Queued until the next
submit, as before, with one error in the log naming the six attempts.

## Found while doing it, not fixed (one finding per commit)

- **A job whose processor cannot be built stops the runner, and every later start of it.** `RunJobAsync` is "TOTAL by
  contract", but it creates the job's scope and resolves its processor (505-506) above its try, so a processor whose
  construction throws - a scoped dependency that cannot be built - escapes to the loop's outer catch (485-493): "Bulk job
  pump loop faulted", and the loop ends. The job stays Queued and, being the oldest, is the first job the next submit's loop
  reads, so it ends that loop too: every job behind it waits until a restart marks them all Interrupted. Pre-existing,
  shared service, LOW (it needs a processor that cannot be constructed); a candidate, from reading, not run.
- **A store failure on a job's terminal write stops the runner until the next submit.** `RunJobAsync`'s backstop catch
  calls `FinishAndNotify` (555), whose `TryFinish` (638) is a store write; when the store that has just failed the job's
  run fails that write too, it escapes to the same outer catch, the loop ends with the job left Running (or Queued), and the
  jobs behind it wait for the next submit - this finding's class on the write path. Pre-existing, LOW; a candidate, from
  reading, not run.

## Known gaps

- (1) After the sixth failed read only the next submit starts the runner again, as before; a job queued while the store stays
  unreadable waits for it, or for the next restart's Interrupted.
- (1) A submit that lands between the last failed read and the flag being cleared finds the loop still running and starts
  nothing, so its job waits for the next submit as well. Its insert has to succeed on a store that is failing reads, the
  same narrow window the loop's stop always had.
- (1) The waits are in-process: a restart during one still marks the queued job Interrupted, as before.
- (1) The lines are asserted through the test's logger; the production sink is not exercised.
- (2) After a reload failure the job list is not refreshed: the job stays listed as it was shown until the next read that
  works - a job event, a later removal or submit, the page's next load.
- (2) The banner does not carry the exception's text; the log does, and the log line is not asserted (the page tests'
  logger is a null logger). Like every banner on this page, it stays until dismissed or replaced.
- (2) Driven by reflection with substitutes for the authentication state and the policy decision; no renderer.
