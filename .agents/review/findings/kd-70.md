# kd-70: Message Trace's detail download does not stop when the operator cancels, and is filed as a success

**Severity**: LOW - read-only work over rows the operator selected, but the cancel button does not do what the page's
own comment says it does. `Services/MessageTraceService.cs` `GetMessageDetailAsync` / `RunDetailBackendAsync` turn every
exception, a cancellation included, into a per-message error ("Delivery detail failed: A task was canceled."); the cloud
read takes no token (kd-58). After the operator cancels, the loop runs on, the CSV is pushed to the browser and the row is
filed as a successful download. The Cancelled filing kd-57 added is reached only by a cancellation from the browser call
or the frame. Also (kd-57 note 2): that catch has no filter on the activity's own token, so a browser-call timeout is filed
as the operator's cancel.

## Approach

- Honour `activity.CancellationToken` in the detail loop: a cancellation of the activity's own token stops the loop
  before the next message, nothing is downloaded, and the row is filed Cancelled in the operator's words (kd-57's
  filing); a per-message failure that is not the operator's cancel stays a per-message error as today. Only the
  activity's token counts as the operator's (kd-57's Recipient Lookup rule); any other cancellation stays a failed read.
- Test: a stand-in whose second message blocks until the token is cancelled; assert no CSV, the Cancelled row, the
  wording. Control: a timeout cancellation not from the activity's token is filed as a failure. Mutation: the token check
  in the loop removed - the download completes and the test fails.
- Message Trace module version bump.

### As implemented (implementer, 2026-10-27; lines at this commit)

- Read first, confirmed: `Components/Pages/MessageTrace.razor` `DownloadSelectedDetails` (1176) looped over the selection
  with `details.Add(await MsgTrace.GetMessageDetailAsync(m, activity.CancellationToken))`; the read is fail-soft by its
  plan's rule (`MessageTraceService.RunDetailBackendAsync`, "GetMessageDetailAsync therefore never throws"), so a cancel
  came back as a per-message error and the loop, the CSV push and the success row all followed. Its
  `catch (OperationCanceledException)` had no filter, and the activity was declared inside the `try`, out of the catch's
  reach.
- **The loop honours the token.** After each message's read, `activity.CancellationToken.ThrowIfCancellationRequested()`
  (1212): the operator's cancel ends the download before the next message, and before the CSV is built or pushed. After
  the read rather than before it, so the read that the cancel interrupted is discarded too. The push itself takes no
  token, deliberately: once the CSV is being sent it may reach the browser whatever happens to the call, and a row filed
  Cancelled for a file that arrived would be false.
- **Only the activity's token is the operator's.** The activity's `using` moved above the `try` (1202) so the catch can
  read it; the catch is `when (activity.CancellationToken.IsCancellationRequested)` (1226). There it completes the activity
  not succeeded with "Cancelled by the operator" (1235) - it used to be left to the dispose's fallback - and files the row
  Cancelled in those words, as kd-57 did. Any other cancellation - a browser call that timed out (`TaskCanceledException`
  from the JS interop) - falls to the existing catch: a download that failed, shown and filed in its own words.
- The service is unchanged: the detail job reads the same fail-soft details (kd-59 already marks a detail its caller's
  token stopped; this loop needs only the token itself).
- Version: Message Trace 1.8.2 -> 1.8.3 (`Modules/ModuleCatalog.cs` 528-532).
- Page: 1,391 -> 1,397 lines; "not started" in `ClickGateRegistry` (no line-keyed entries). `ProgressRegistry`'s entry
  names `MsgTrace.GetMessageDetailAsync`; the Begin still opens above it and the Complete still sits below the push.
