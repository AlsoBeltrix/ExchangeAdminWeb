# kd-27: Conference Rooms CancelJob and RemoveJob never re-check authorization

**Severity**: MEDIUM - the aud-a29 class on two handlers. `Components/Pages/ConferenceRooms.razor` `CancelJob` (about 837) and `RemoveJob` (about 923) run without the per-click authorization re-check the page's write handlers perform, so an operator whose access was revoked can still cancel or remove jobs from an open tab until the circuit revalidation (aud-a29b) catches it.
**Status**: Merged to master `c3af5bd4`; codex defect review cr-batch-9 in flight
**Branch**: `fix/psl10-a2y` (worktree `D:\source\ExchangeAdminWeb-wt\psl10-a2y`, from `f7b794cb`, no merge of master)
**Commit**: the commit that adds this line (SHA in the implementer's hand-back)
**Reviewer**: implementer (psl10-a2y agent, candidate; not yet confirmed by the supervisor)

## Evidence

At `07f2d371`. Trigger: revoke an operator with the page open; they click Cancel or Remove. Predicted failure: the action succeeds and is audited under a revoked operator.

## Approach (to be written by the implementing agent before code)

- Both handlers run the same authorization re-check the four write handlers run (kd-7 put the ticket gate before it; mirror the order), refusing with an audited denial; tests by reflection; mutation: re-check removed. In place on the line-keyed page.

### As written before the code (branch `fix/psl10-a2y` from `f7b794cb`; no merge of master, as briefed)

**Verified.** `Components/Pages/ConferenceRooms.razor` 837 `CancelJob(BulkJob)` (kd-5's one line) and 923-945 `RemoveJob(BulkJob)`
reach `BulkJobs.CancelJob` / `BulkJobs.DeleteJob` with no re-check. The four write handlers re-check with
`ReauthorizeAsync()` (1692): the page's "ConferenceRooms" policy against the current token, the banner set to
"Authorization denied." on a refusal. On master kd-7 put each write's ticket gate before it; the two job controls take no
ticket - their rows carry the job's own submission ticket - so no ticket gate applies and the re-check is their first step,
before any store call, which is where it sits relative to the mutation in the write handlers. `ReauthorizeAsync` itself
audits nothing (nor on master), so the denial's row is written here.

**The change, in place (1758 lines, no line-keyed entry moves).**
1. 838 (blank) becomes `JobControlAllowedAsync(action, job)`: `ReauthorizeAsync()`; on a refusal one row under the
   control's own action - `ConferenceRooms_CancelBulkJob` / `ConferenceRooms_RemoveBulkJob` - Failed, "Authorization
   denied.", the job as rendered (its id, ticket and the old values `RemoveJob` records), and the aud-a28 refusal fields
   `refusedAt` "Authorization" (the app's label for this refusal) and `mutationAttempted` false.
2. 946 (blank) becomes `AuditJobControl(action, job, success, error, refusedAt)`: that row's shape once, catch-and-log as every
   audit helper on the page; `refusedAt` null leaves the refusal fields off.
3. 837: `CancelJob` becomes `async Task` and starts `if (!await JobControlAllowedAsync(...)) return;`; its kd-5 row is written
   through `AuditJobControl`, the same fields as before.
4. 925-926 (`BulkJobs.DeleteJob(` over two lines) become the re-check and the call on one line, so `RemoveJob` refuses before
   the delete; its own row is unchanged.
5. 836's comment says what the three lines are. `ProgressRegistry`'s two exemptions name the local re-check; the
   `ClickGateRegistry` conditions for 511 and 575 stay true (both still take the rendered row and look nothing up).
6. Tests in `ConferenceRoomPageTests`: a revoked operator's Cancel and Remove - the job untouched, one denial row, the banner
   "Authorization denied."; an allowed Remove - deleted, its row Success; kd-5's cases now await the handler (it returns a
   Task). Mutations: each re-check removed; the re-check after the delete; the denial's row dropped.
7. Conference Rooms' 2.10.0 note (kd-28, this batch) gains this line.
