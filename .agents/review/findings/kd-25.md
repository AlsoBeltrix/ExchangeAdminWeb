# kd-25: the 60 s drain poll and the writers' 60 s release holds in ExtendedLogServiceTests are the file's most exposed bounds

**Severity**: LOW - flaky-test class. `ExchangeAdminWeb.Tests/ExtendedLogServiceTests.cs`: the drain poll at about 659-663 in `AFullQueue_CountsTheEntriesItDiscards` (600 x 100 ms for 1,025 entries) took 33 s on a loaded host, over half its 60 s limit; the writers' `release.Wait(60 s)` holds at about 645, 700 and 743 run the other way (the consumer waits for the test), and a hold that runs out early changes what is dropped in two tests. Exposure, traced:
- **The drain poll** is a count of sleeps: 600 rounds of a 100 ms sleep plus a `GetEntries` read of
  up to 1,025 lines, so its real length is 60 s and more, and grows with the reads. 1,025 entries
  with no sleep in the writer took 33 s on a loaded host (kd-22).
- **The holds** are the consumer waiting for the test: each must outlast the test's own steps
  between `entered` and `release`. Ran out early, `Dispose_Counts...` fails outright (the writer drains
  the 50 before `Dispose` sees them, so 0 dropped, not 50), and `AFullQueue...` can see fewer than 5
  dropped if the test thread stalls before it has queued all 1,029. In the kd-16 test an early end
  is harmless; it is one of the listed holds, so it joins the one bound.

Chosen: **the shared bound for all four, as a deadline, not a count.**
- The drain poll becomes a deadline loop: `ConsumerWait` (2 minutes) from `release.Set()`, polling
  every 100 ms as now, so `GetEntries` time no longer stretches it and nothing else about the check
  changes. Not an event: the check reads the entries back through the service, which a write
  counter in the hook would not.
- The three holds wait `ConsumerWait` too. `ConsumerWait`'s comment says it now bounds both
  directions - the test waiting for the consumer and a held consumer waiting for the test - one knob,
  far above any stall.
- Test-only; `Services/ExtendedLogService.cs` untouched (aud-a64 (5)).

Files (declared): `ExchangeAdminWeb.Tests/ExtendedLogServiceTests.cs`, this record.

Proof, the injected-delay method, a 75 s stall each - beyond the old 60 s bounds (and the old poll's
real length, about 60-75 s), inside the new 2 minutes with the drain's own 11-31 s on top:
- **the drain**: in `AFullQueue...` the consumer stalls 75 s after it is released, so the queue
  drains 75 s and more after `release.Set()`;
- **a hold**: in `Dispose_Counts...` the test stalls 75 s between queueing and `Dispose()`.
Run with the fix (both pass), on the pre-fix file with the same stalls (both fail - "the queue never
drained", and 0 dropped instead of 50), and on the restored final bytes (both pass).

## Known gaps

- **The holds now block a failed test's consumer longer.** `AFullQueue...` and the kd-16 test release
  only on their success path (`Dispose_Counts...` has a `finally`); when one of them fails before its
  `release.Set()`, the consumer thread stays parked up to 2 minutes instead of 60 s. A background
  thread in a run that has already failed; not restructured here.
- **The setup lock wait** (`JsonlFileAppender.Lock(path, 10 s, ...)` in `HoldTodaysLock`) stays at
  10 s: uncontended, not an exposure, as admitted. Checked on the final file: every other timing
  value left is either `ConsumerWait`, the drain poll's 100 ms cadence, or a seam a test sets as its
  subject - the 300 ms `LockWait` the lock-drop test needs to run out, the `Dispose` floor and
  allowances (kd-16's 100 ms and 1 s, `Dispose_Counts...`'s 1 ms), and kd-16's 20 ms per-entry sleep.
