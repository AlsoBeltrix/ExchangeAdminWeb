### As written before the code (branch `fix/psl10-a2y` from `e69f4c18`, kd-53 and kd-54 on it; no merge of master)

**Verified.** `Services/ADDirectorySearchService.cs` `ExecuteValidateExists` (456-527) opens the same session as the searches
(`GetOrCreateRunspace`, psl-11's `CreateSearchRunspace` seam) and runs `Get-ADUser`, `Get-ADGroup` or
`Get-ADOrganizationalUnit` by kind, with that kind's properties; a DN-shaped Group identity is routed to its own domain
with `-Server` (pgwt-5). Its tests today (`ADDirectoryValidateExistsTests`) cover the pure helpers and the unavailable
path only - the directory half, like the search's before psl-11, is proven by nothing that runs here.

**The change (tests only).**
1. `ADDirectorySearchServiceTests.AvailableStandInService` takes what its directory commands answer - one object (today's
   behaviour, so psl-11's theory is untouched), none, or two - each command still noting its call and, for a group, its
   `-Server`.
2. New in `ADDirectoryValidateExistsTests`, all on that stand-in, no directory:
   - each kind (User, Group, OU) with one answer: `Found`, the command that kind runs and only it, and the match mapped -
     its object type, DN, label (the OU's from `Name`), and the group's `ObjectGUID`, which the protected-target admin
     page stores;
   - each kind with no answer: `NotFound`, no match - the outcome that must never be confused with `Unavailable`, which is
     what the class exists for;
   - a DN-shaped group: `-Server` the DN's own domain (pgwt-5's forest-wide revalidation), and a non-DN group: no `-Server`;
   - two answers: `Found` with `Ambiguous` true (pgwt-4), which `ResultSetSize 2` makes decisive.
3. Mutations, at the call site in `ExecuteValidateExists`: the OU kind's command removed (it falls to `Get-ADUser`); the
   group kind's; the `-Server` routing dropped; the no-results branch answering `Found`.
4. No behaviour change, so no module version moves.
