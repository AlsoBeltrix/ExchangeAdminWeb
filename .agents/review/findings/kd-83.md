# kd-83: a job whose processor cannot be built, or whose final status write fails, stops the bulk job runner

**Severity**: LOW-MEDIUM, pre-existing, the kd-82 (1) class. `Services/Jobs/BulkJobService.RunJobAsync` resolves the job's
processor before its try: a processor that cannot be built stops the runner, and because that job stays first in the queue it
stops it again on every later start, so every job behind it waits until a restart. And if the store fails a job's final status
write (`FinishAndNotify` / `TryFinish`), the runner stops until the next submit.
**Status**: Fixed on branch, verified; closes on guard proof. Two parts, one commit each
**Branch**: `fix/kd83` (worktree `D:\source\ExchangeAdminWeb-wt\kd83`, from master `4c754f08`)
**Commit**: one per part - (1) `e6face05`, (2) the commit that adds this line (its SHA in the implementer's hand-back)
**Reviewer**: implementer (candidate)

## Evidence

At `c47b0354`: the kd-82 record's candidates.

## Approach

- A processor that cannot be built: the job is marked Failed with the reason (one audit row, administrators told as for
  any failed job), the runner moves to the next job; test with a job type no processor serves; mutation: the resolve moved
  back outside the try.
- A final status write that fails: retry with the kd-82 (1) back-off; if it keeps failing, log once, leave the job for the
  next start's Interrupted sweep, and continue with the next job rather than stopping; test with a store that fails one
  final write then recovers, and one that keeps failing; mutation: the retry removed.
- BulkJobService is shared: base bump already owed for this release.

## (1) A processor that cannot be built (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `4c754f08`: `RunJobAsync` (503-558) created the job's scope and resolved its processor (505-506)
above its try (509). `ResolveProcessor` (648-654) is `scope.ServiceProvider.GetService(type)`, which answers null only for a
type the container does not hold, and throws when it holds the type and cannot build it - a constructor that throws, or a
scoped dependency that throws as it is built or is not registered. That throw left `RunJobAsync` before any write, reached
`DrainQueueAsync`'s outer catch (485-493) - "Bulk job pump loop faulted", the flag cleared - and the loop ended with the job
Queued. Being the oldest, it was the first job the next submit's loop read (447), so it ended that loop too, and every job
behind it waited for a restart to mark them all Interrupted (`InitializeAsync`, 130-131). Reachable as described: M0 below
is the file as it was, and the test fails on it - the job behind still Queued. The completion hook's own build,
`NotifyCompletedInScope` (672), was above its try as well.

**How a failed job is audited and notified today** (read, as the brief asks the same path be used; the brief's "Failed" and
"one audit row" have no counterpart in the code, and the change follows the code):
- There is no Failed status (`Services/Jobs/BulkJobModels.cs` 10-30: Queued, Running, Completed, Cancelled, Interrupted).
  A job the runner cannot run is Interrupted with the reason: "No processor registered for module '<module>'." (511-519),
  "Job faulted: <reason>" (548-557).
- The runner has no audit or mail of its own: `BulkJobService` holds neither `AuditService` nor `EmailService`. Every
  terminal path goes through `FinishAndNotify` (635-646): the compare-and-swap to the terminal status and its message - the
  job's durable record, which the pages list - then `JobChanged`, then the module's completion hook,
  `IBulkJobProcessor.OnJobCompletedAsync` ("where a module sends its completion admin notification",
  `IBulkJobProcessor.cs` 42-50): Conference Rooms' administrator mail, not-success for an Interrupted job
  (`ConferenceRoomBulkProcessor.cs` 187-211); Comms-10k's, outcome "Interrupted" (`Comms10kReplaceProcessor.cs` 297-336);
  Message Analysis' mail and its one audit row (`MessageTraceDetailJobProcessor.cs` 94-136); Migration export has none.
- Every other audit row is the processor's, per row or per replace. A job that fails before its first row - a module no
  processor is registered for, a payload that cannot be parsed, a fault before the start - files none today in Conference
  Rooms, Comms-10k or Migration export. There is no runner-level audit row to reuse, so none is added (a new audit or mail
  channel in the runner would be a logging/notification change the Constitution puts behind a written plan).

The change:
- **The resolve inside the try** (`Services/Jobs/BulkJobService.cs` 518-531, the remarks 503-510). The processor is resolved
  in a try of its own inside the job's try. A throw:
  - is logged once, an error with the exception - "The bulk job processor for module {Module} could not be built; marking
    job {Job} Interrupted" (525), the shape of the "No bulk job processor registered" line beside it (535);
  - finishes the job through `FinishAndNotify`, Interrupted from Queued or Running, with the reason: "The processor for
    module '<module>' could not be built: <the exception's message>" (527-529) - as a job no processor is registered for
    is, so its record, its `JobChanged` and its completion hook take the path every failed job takes;
  - returns, and the loop reads the next job.
- **The completion hook's build inside its try** (`NotifyCompletedInScope`, 692-710). The processor the hook needs is now
  built inside the try that already caught the hook's own failure. For this job the build fails again (the same scope
  builds it again), and it is logged as any failed hook is - "Completion notification for bulk job {Job} failed
  (non-fatal)" - never a throw out of the runner's terminal tail. A build failure that has passed by then is built, and the
  hook runs as for any Interrupted job.
- **Unchanged**: a processor that builds, a module no processor is registered for, a payload that cannot be parsed, a
  fault later in the job, and every job that succeeds or fails as before; `FinishAndNotify`, `DrainQueueAsync`, `Enqueue`.
- **Version**: none here. `BulkJobService` is a shared service, so a base app version bump is owed (2.36.0 at this commit);
  as briefed, it is the supervisor's and is not made here.

**Operator-visible change.** None for a job whose processor is built. A job whose module's processor cannot be built - a
dependency of it failing as it is built - is listed Interrupted with "The processor for module '<module>' could not be
built: <reason>" where it sat Queued and held every job behind it until a restart; the jobs behind it run. No module
completion mail is sent for it, since that mail is the processor's own; the log names the failure twice, the build and
the hook.

## (2) A final status write the store fails (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `e6face05` (part (1)'s commit): `FinishAndNotify` (657-668 there) made the terminal write once -
`_repository.TryFinish` (660), the compare-and-swap UPDATE of `BulkJobRepository.cs` 187-214 - with nothing around it, and
every terminal path of `RunJobAsync` calls it: a processor that cannot be built (527), a module no processor is registered
for (537), a payload that cannot be parsed (551), the job's end (568) and the backstop (577). A write the store failed
threw:
- from the job's own try into the backstop (570-580), which logged "Bulk job {Job} faulted unexpectedly" and wrote again,
  Interrupted with "Job faulted: <the store's message>" - so a store that took that second write reported a job whose rows
  had all run as Interrupted, and its module's mail went as a failure;
- from the backstop out of `RunJobAsync` to the loop's outer catch (485-493) - "Bulk job pump loop faulted", the flag
  cleared - so the runner stopped until the next submit, the job left Running (or Queued, for a job finished before it
  started), and the jobs behind it waited.

Reachable as described: M0 below is the tail and the read as at `e6face05`, and all three tests fail on it - the runner
stops at the first job's write and the job behind it stays Queued.

- **The write's own retry** (`Services/Jobs/BulkJobService.cs`, `FinishAndNotify` 695-739, its remarks 685-694). The
  write is in a loop's try; a throw:
  - is counted (710); below `FinalWriteAttempts` (6, at 387 - `QueueReadAttempts`, the queue read's bound) the tail waits
    `FinalWriteRetryDelay` (390 - kd-82's `QueueReadRetryDelay`: 1, 2, 4, 8 and 16 s, about half a minute in all) through
    `WaitBeforeFinalWrite` (392-397, a test seam of the shape of kd-82's) and writes again (720-721), `finished_at` the time
    of the write that lands;
  - at the sixth failed write, passes the job over from then on (713) and says so once - an error, with the write's own
    exception: "The final status (<status>) of bulk job <job> could not be written in 6 attempts; the job is left as it
    is, for the next start to mark Interrupted, and the runner carries on" - and returns (714-717): no `JobChanged` and no
    completion hook, since nothing was written. The job stays Running (or Queued) until the next start's sweep
    (`InitializeAsync`, 135-136), which marks every unfinished job Interrupted; `RunJobAsync` returns normally, so the
    backstop does not write a fault over it, and the loop reads the next job.
- **One line per run of failed writes**: the error above when the job is left, or, when a write is then made, one
  warning with the last failure's exception - "The final status (<status>) of bulk job <job> could not be written N
  time(s); the next attempt succeeded and the runner carries on" (725-730). The tail then goes on as before: `JobChanged`,
  and the completion hook if the compare-and-swap fired.
- **The pass-over** (`_leftForNextStart`, 56-59; the queue read, 471-472, and its remarks 454-456). A job finished before it
  started is written from Queued, so a write the store keeps failing leaves it Queued and still the oldest in the queue:
  taken again, it would be written for ever while the jobs behind it waited. The set is read under `_gate` with the queue,
  and lives as long as the process - the job is left for the next start, not the next submit. A cancel still reaches it:
  `CancelJob` finishes a Queued job as before.
- **The waits are not cancelled** (the seam's remarks, 392-396), unlike the queue read's: the write records the job's
  result, and a cancelled wait would throw into the job's backstop, which writes a fault over that result. The waits are
  bounded instead. Production passes no cancellation to the runner (`EnsurePump`, `CancellationToken.None`).
- **The five call sites** await the tail (555, 565, 579, 596, 605), and `RunJobAsync`'s remarks (535-537) name the one
  job it does not finish; `FinishAndNotify` keeps its name, which the remarks of
  `BulkJobRepository.cs` 222 and `MessageTraceExportListing.cs` 263 cite.
- **Unchanged**: a write the store takes at once - no wait, no line, the same status, message, `JobChanged` and hook as
  before; `TryCancelJob`'s own write; `ExecuteRowsAsync`; the queue read's retry (kd-82).
- **Version**: none here. `BulkJobService` is a shared service, so a base app version bump is owed (2.36.0 at this commit);
  as briefed, it is the supervisor's and is not made here.

**Operator-visible change.** None while the jobs database takes its writes. When it fails a job's final status write -
locked, full or read-only for a moment - the job's own status (Completed, or Cancelled, or Interrupted with its reason)
lands once the database takes it again, within about half a minute, with the module's mail as for that status, and the log
says so once (a warning); before, the job behind it waited for the next submit, or the job was shown Interrupted, "Job
faulted: ...", though all its rows had run. A database that still fails the write after that leaves the job as it was
shown - Running, or Queued - until the next restart marks it Interrupted, with one error in the log naming the six
attempts, and the jobs behind it run.

## Found while doing it, not fixed (one finding per commit)

- **A failed read of the finished job, after its final write has landed, still leaves the tail.** `FinishAndNotify` reads
  the job back for the completion hook (`_repository.Get`, 736) outside any try. A store that fails that read, after it
  took the write: from the job's own try, the backstop takes it - "Bulk job {Job} faulted unexpectedly", then a write that
  matches nothing (the job is finished), so the result stands, but the completion hook is not run and the log line
  misnames it; from the backstop's own tail (a job that faulted, whose Interrupted write landed), it leaves `RunJobAsync`
  and stops the runner until the next submit - this finding's class, on the read after the write rather than the write.
  Pre-existing, shared service, LOW (a fault, then a write that lands, then the read right after it failing); a candidate,
  from reading, not run. The likely fix: the read and the hook inside one notification try, logged as a notification
  failure (the Constitution's "notification failure must not change or mask the backend operation result").
- **What the brief asked for and the code has no counterpart for** (part (1)): there is no Failed status, and no
  runner-level audit row or administrator mail - both are the module's processor's, through its completion hook. A job
  whose processor cannot be built therefore gets the record every failed job gets (its Interrupted status and reason) but
  no module mail and, for Message Analysis, not the hook's audit row: the hook is the processor's and cannot run. A runner
  audit row or mail for that case would be a new audit/notification channel, behind a written plan
  (Constitution, Planning Rules); not made, not raised as a finding.

## Known gaps

- (1) For a job whose processor cannot be built, the module's completion mail (and Message Analysis' audit row) is not sent:
  the hook is the processor's. The log carries the build failure and the hook's failure.
- (1) The test's processor fails as its dependency is built, a stand-in for the production causes (a constructor that
  throws, a dependency that throws as it is built or is missing from the container); no production processor was made to
  fail.
- (2) A job left by a write that keeps failing shows Running (Stalled once its heartbeat is old) or Queued until the next
  restart; a cancel of a Running one is recorded but nothing ends it before the restart. A Queued one can be cancelled as
  before.
- (2) The waits are in-process and about half a minute in all: a restart during them marks the job Interrupted, as before.
- (2) A store that fails a write and then takes a write that matches nothing - another administrator's cancel of a Queued
  job landing between the two - logs the warning ("the next attempt succeeded") and leaves the hook to the cancel, as
  before.
- (2) The stand-in fails one job's terminal write with a trigger; a locked, full or read-only database was not used. The
  lines are asserted through the test's logger; the production sink is not exercised.
- `RunJobAsync`'s scope is still created and disposed outside its try (541): a scoped service whose `Dispose` threw would
  leave the runner the same way. Of the disposable services in `Services/`, `ExoConnectionPool`, `OperationTraceService`,
  `ExtendedLogService` and `PageLoadTracker` are singletons, `JsonlFileAppender` and `SelfGrantDirectory` are not
  registered with the container, and the scoped `IActivityProgress` is a page's (Program.cs 324-331) - no service outside
  `Services/Progress/` names it - so a job's scope disposes none of them; read, not run.
