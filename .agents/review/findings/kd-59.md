# kd-59: the other modules' credential fetches pass no cancellation token

**Severity**: LOW. Conference Rooms, Message Trace and both permission services call the credential fetch with no token,
so their work stays uncancellable; kd-37 built the seam and used it only for Recipient Lookup.
**Status**: In progress on `fix/kd59-kd70` - one module per commit: Message Trace landed; Conference Rooms, Mailbox
Permissions and Calendar Permissions pending
**Branch**: `fix/kd59-kd70` (from master `69f11c23`; worktree `D:\source\ExchangeAdminWeb-wt\kd59-kd70`)
**Commit**: one per module - each module's is the commit that adds its section below (`git log -- .agents/review/findings/kd-59.md`)
**Reviewer**: implementer (aud-a68/kd-2 agent, candidate; not yet confirmed by the supervisor)

## Evidence

At `9ffc653c`; raised by the kd-37 agent.

## Approach

- Pass each caller's activity token through the seam kd-37 added, one module per commit, with the same warning-versus-cancel
  rule (an unasked vault timeout stays a warning); test per module; mutation: the token dropped at that caller.
- Kept to (implementer, 2026-10-27): kd-57's filing - a cancel the token now makes possible is filed result "Cancelled",
  words "Cancelled by the operator" (`AuditService.CancelledResult`, `CancelledByTheOperator`, `FiledCancelled`) - and its
  rule that only the activity's own token cancelled is the operator's cancel; any other cancellation stays a failure in
  its own words. The token goes to the credential fetch only, as kd-37's did: the throttle, the runspace and the Exchange
  Online reads (kd-58, sized as needing a plan) are not changed.

## As implemented - Message Trace (implementer, 2026-10-27; lines at this commit)

Starting point: the killed aud-a68/kd-2 agent's uncommitted diff in `D:\source\ExchangeAdminWeb-wt\a68-kd2` (the two
credential fetches given a token, the search given a parameter) and its two untracked test files. Re-read against master,
which kd-57 had moved; kept its fetch changes and its `CancellableVaultCredentials` fixture (extended), and added what it
did not have: the cancel filed as kd-57 files one.

- **The two fetches.** `Services/MessageTraceService.cs` `GetOnPremMessageDetailAsync` held a token (`ct`) and fetched its
  credential without it (203 now passes it); `GetOnPremMessageTraceAsync` had none (532; the search's
  `GetMessageTraceAsync` takes `cancellationToken = default`, 20, and hands it on).
- **The search lets the operator's cancel out as a cancel.** `RunMessageTraceBackendAsync` (423-437) turned every throw
  of a backend into "<backend> trace failed: ..."; a cancellation of the search's own token now goes out as it is, and
  any other throw - a cancellation the token did not cause included - is still that backend's failure. The page's
  `RunRealtimeTrace` (`Components/Pages/MessageTrace.razor` 844-878) takes the activity's token from `RunTrace` (828) and
  catches `OperationCanceledException` when that token is cancelled: the response's error and the row's are "Cancelled by
  the operator", the row is filed Cancelled, and `RunTrace` completes the activity not succeeded with the phrase (829). The
  cloud half takes no token (kd-58), so the cancel comes out once it has ended - at most the chunked search's few cloud
  round trips.
- **The detail stays fail-soft and says when the cancel stopped it.** `GetMessageDetailAsync` never throws - the
  MessageTraceDetail plan's rule, and the detail job reads every failure as a Failed row (`MessageTraceDetailJobProcessor`
  82-89). So the page cannot see the cancellation; letting it out would change the job's rows. Instead
  `RunDetailBackendAsync` (118-145) takes the caller's token and marks the detail `Cancelled` (new, `Models/LookupModels.cs`
  84-89) only when the throw was an `OperationCanceledException` and that token is cancelled; the error is set as before,
  so the job reads what it read. `ToggleDetail` passes `detailActivity.CancellationToken` (1086) and, for a detail marked
  Cancelled, shows and files "Cancelled by the operator", result Cancelled (1087-1096). A read that came back whole, or
  failed for any other reason, is filed as the read it was.
- **The live download** (`DownloadSelectedDetails`) already passed its activity's token; its on-premises messages now
  reach the vault with it. What it does after a cancel is kd-70's, the next commit.
- **The detail job** passes its job token to the same fetch, so a job cancelled during an on-premises row's vault read ends
  that read sooner; the row is still a Failed row in the framework's words, as a cancelled `Task.Run` already made it.
  Unchanged in kind; noted only.
- Version: Message Trace 1.8.1 -> 1.8.2 (`Modules/ModuleCatalog.cs` 524-526). `MessageTraceService` and the
  `MessageTraceDetail` model are this module's; no shared service changed, so no base bump from this commit.
- Page: `MessageTrace.razor` 1,371 -> 1,391 lines. "Not started" in `ClickGateRegistry` (no line-keyed entries); its
  `ProgressRegistry` entries name calls (`RunRealtimeTrace`, `MsgTrace.GetMessageDetailAsync`), both still present.
- Tests changed to follow the code: `MessageTracePageRoutingTests.RunTrace_RunsTheRealtimeTraceUnconditionally` pinned the
  literal `await RunRealtimeTrace()`; it pins `await RunRealtimeTrace(activity.CancellationToken)` now (its point - no
  date-width branch - unchanged). `MessageTraceDetailTests`' two `RunDetailBackendAsync` calls pass the test's token
  (xUnit1051, raised by the new parameter).
