# kd-59: the other modules' credential fetches pass no cancellation token

**Severity**: LOW. Conference Rooms, Message Trace and both permission services call the credential fetch with no token,
so their work stays uncancellable; kd-37 built the seam and used it only for Recipient Lookup.
**Status**: In progress on `fix/kd59-kd70` - one module per commit: Message Trace, Conference Rooms and Mailbox
Permissions landed; Calendar Permissions pending
**Branch**: `fix/kd59-kd70` (from master `69f11c23`; worktree `D:\source\ExchangeAdminWeb-wt\kd59-kd70`)
**Commit**: one per module - each module's is the commit that adds its section below (`git log -- .agents/review/findings/kd-59.md`)
**Reviewer**: implementer (aud-a68/kd-2 agent, candidate; not yet confirmed by the supervisor)

## Evidence

At `9ffc653c`; raised by the kd-37 agent.

## Approach

- Pass each caller's activity token through the seam kd-37 added, one module per commit, with the same warning-versus-cancel
  rule (an unasked vault timeout stays a warning); test per module; mutation: the token dropped at that caller.
- Kept to (implementer, 2026-10-27): kd-57's filing - a cancel the token now makes possible is filed result "Cancelled",
  words "Cancelled by the operator" (`AuditService.CancelledResult`, `CancelledByTheOperator`, `FiledCancelled`) - and its
  rule that only the activity's own token cancelled is the operator's cancel; any other cancellation stays a failure in
  its own words. The token goes to the credential fetch only, as kd-37's did: the throttle, the runspace and the Exchange
  Online reads (kd-58, sized as needing a plan) are not changed.

  Cancelled, shows and files "Cancelled by the operator", result Cancelled (1087-1096). A read that came back whole, or
  failed for any other reason, is filed as the read it was.
- **The live download** (`DownloadSelectedDetails`) already passed its activity's token; its on-premises messages now
  reach the vault with it. What it does after a cancel is kd-70's, the next commit.
- **The detail job** passes its job token to the same fetch, so a job cancelled during an on-premises row's vault read ends
  that read sooner; the row is still a Failed row in the framework's words, as a cancelled `Task.Run` already made it.
  Unchanged in kind; noted only.

## As implemented - Conference Rooms (implementer, 2026-10-27; lines at this commit)

- **Where the module fetches a credential.** `Services/ConferenceRoomService.cs` `LookupDirectoryCredentialAsync` (1633)
  is the module's one fetch, asked by four directory paths, all inside a single-room or bulk Room Finder apply
  (`SetRoomMetadataAndListAsync`): the City/State/Country preflight (1743) and the on-prem room-list preflight (2047),
  both BEFORE Set-Place, and the City/State/Country write (1847) and the on-prem room-list add (2159), both AFTER it. The
  Room Type paths fetch none.
- **The token reaches the two preflights, and only them - a design choice, stated.** `SetRoomMetadataAndListAsync`
  takes `cancellationToken = default` (511-514) and hands it to both preflights; `LookupDirectoryCredentialAsync` now
  takes a token (required, so each path names its own) and passes it to `ModuleCredentialService.LookupCredentialsAsync`
  or, with no credential service, the base's fetch. The two writes pass `CancellationToken.None`, on purpose: a cancel
  there would stop the row after Set-Place had committed and leave the room half-configured - the partial this module's
  preflights exist to prevent ("Preflight the AD step BEFORE any mutation ... so EXO is never partially written",
  573-577). So a cancel during either preflight's vault read ends the row with nothing written; once Set-Place is made
  the row runs on, as it always did. The navigation guard's own words allow exactly this: "Anything it has already
  changed will stay changed."
- **The bulk job is unchanged.** `IConferenceRoomBulkOperations.SetRoomMetadataAndListAsync` is now implemented
  explicitly (749-756) and calls the method with `CancellationToken.None`: the job's rows are not the page's activity,
  and its interface and its two test stand-ins are untouched.
- **The page.** `Components/Pages/ConferenceRooms.razor` `SetupSingleRoom` passes `activity.CancellationToken` (1075) and
  catches `OperationCanceledException` when that token is cancelled (1084-1093), ahead of the existing catch: the banner and
  the row's error are "Cancelled by the operator. Nothing was written.", the row is filed Cancelled
  (`AuditFinderAction`'s new `cancelled` flag wraps its extra in `AuditService.FiledCancelled`, 1728-1732), and the
  administrators are told as for a row that failed - the same notification, with that text. Any other cancellation goes
  to the existing catch, a failure in its own words.
- Version: Conference Rooms 2.19.1 -> 2.19.2 (`Modules/ModuleCatalog.cs` 1024-1027). No shared service changed.
- Page: `ConferenceRooms.razor` 1,758 -> 1,768 lines, every edit at or below 1075, below every line-keyed control on the

  lines at or above 622). `ProgressRegistry` names calls (`RoomService.SetRoomMetadataAndListAsync(`), still present.
- Tests changed to follow the code: `ConferenceRoomWriteIdentityTests`' override of `LookupDirectoryCredentialAsync`

  `ConferenceRoomWriteIdentityTests` 1235 and 1576.
