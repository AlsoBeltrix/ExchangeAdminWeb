Jobs; after kd-77 the store answers Removed / NotFinished / NotFound, which the page should word and audit.

## As implemented (implementer, 2026-10-27; lines at this commit)

Read first, confirmed at `a9b10b0d`: `RemoveJob` (923-945) called the two-argument `BulkJobs.DeleteJob(ModuleName, job.Id)`
and wrote its row inline - `success: removed`, no error text, no `extra` - so a removal the store did not make was a Failed
row that said nothing, and the handler set no banner: the operator saw only the list refresh. Since kd-77 the store decides a
removal in one write transaction and the three-argument overload says why (`BulkJobRemoval` NotFound / NotThisModule /
NotFinished). On this page NotFound is the one an operator meets - another administrator removed the job first, or it was
pruned: the Remove button is on the finished jobs only (`GetRecentJobsByModule` reads `GetFinishedByModule`, terminal
statuses), a finished job never runs again (`BulkJobService`: "There is no resume"), and the list is this module's alone. The
other two are defensive arms, as on Admin Bulk Jobs.

- **The outcome** (931-937): the three-argument `DeleteJob(..., out var outcome)`; a removal that did not happen takes Admin
  Bulk Jobs' reason from the same switch, word for word (`Components/Pages/AdminBulkJobs.razor` 382-387): NotFound "it no
  longer exists.", NotThisModule "it belongs to another module.", otherwise "it has not finished.".
- **The row** (939-940): through the page's own `AuditJobControl` (kd-27's helper, 946) - Failed, "The job was not removed:
  <reason>", `refusedAt` "JobState" and `mutationAttempted` false, kd-54's text and fields for the same refusal. A removal
  that happened passes no error and no `refusedAt`, so its row is the one the inline block wrote: the same
  `LogConferenceRoomAction` call, target, ticket and five old values, no `extra`, the same catch-and-log.
- **The banner** (941-942): for a removal that did not happen, `result` - the page's shared banner, shown above the Bulk Jobs
  card, where the access re-check's "Authorization denied." already shows - reads "Could not remove the <kind> job -
  <reason>": Admin Bulk Jobs' sentence, naming the job by this page's own label for it (`JobKindLabel`, the list's first
  column) where that page names the module and job type its list shows. A removal that happened leaves the banner as it was,
  as before. The assignment is a direct `new RoomOperationResult { ... }` and nothing reads `result` back, so
  ClickGateRegistry's dismiss exemption (452) and its remark that the scanner sees no bare-token raise of `result` stay true.
- **Unchanged**: what the operator can do; the access re-check first (kd-27); a throw from the store, which still leaves the
  handler before any row (see "Found while doing it"). ClickGateRegistry 575's condition (the rendered row, no lookup) and

- **Lines**: 1791 before and after, the edit inside 923-945, below every line-keyed entry; `ExpectedLineCount` unchanged, no

## Found while doing it, not fixed (one finding per commit)

- **A store failure on Conference Rooms' removal writes no audit row.** `RemoveJob` calls `DeleteJob` outside any try, so a
  throw from the jobs store (a locked or unreadable jobs database) leaves the handler before `AuditJobControl`: no row, no
  banner, the exception to the circuit. Admin Bulk Jobs closed that on its own removal in kd-62 (the call wrapped, the
  failure audited Failed with the store's message and no refusal fields, then thrown on), and this page's `CancelJob` audits
  its store failure the same way (kd-5). Pre-existing, not changed here. LOW, audit fidelity; a candidate.
