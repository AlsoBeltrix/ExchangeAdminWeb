# cdt-7: the Comms-10k yield-hold test context drops a continuation posted after its one drain, so the theory waits forever

**Severity**: MEDIUM. Test-only: no production code is wrong and no user sees anything. The
test's own synchronization context loses the page's continuation, so
`C6ValidationWaitsKeepTheCapturedTicketVisibleAndRejectDelayedInput(waitAt: "yield")` waits
forever without failing, and `dotnet test ExchangeAdminWeb.slnx`, the repo's required
verification gate, never finishes on this host (about four hours on 2026-10-21; 20 of 20
isolated runs hung at HEAD). CI passed the same day only because the race can be won there.
**Status**: Fixed on branch; awaiting merge

**Commit**: `<pending>`

## Evidence

A test defect, not a production one. At `1633ad0`:

- `ExchangeAdminWeb.Tests/Comms10kTicketDisplayTests.cs:83` starts the `yield` case's
  `ValidateEmails` under `C7YieldContext`; line 98 releases it with `context.Resume()`, and line
  99 is `await pending;`.
- `ExchangeAdminWeb.Tests/Comms10kBusyStateTests.cs:482-500`, `C7YieldContext`: `Post` only
  enqueues, and `Resume()` (line 493) is
  `try { while (_queue.TryDequeue(out var item)) item.Callback(item.State); }` (line 497). It
  runs what is queued at that instant, once, and returns. Nothing drains the queue again.
- The held continuation is the one after `await Task.Yield();` at
  `Components/Pages/Comms10k.razor:720`. Run by `Resume()` with the context installed, it passes
  the disabled ServiceNow check and the credential read synchronously and reaches
  `Services/Comms10kService.cs:255`, `return await Task.Run(() => ...)`. That await captures
  `C7YieldContext`. The delegate runs on a pool thread and its completion is `Post`ed back to the
  context. If the pool finishes before the drain loop's last `TryDequeue`, the loop runs it and
  the test passes. If it finishes after, the post lands in a queue nobody reads,
  `ValidateEmails` (awaiting at `Comms10k.razor:751`) never resumes, and `await pending` waits
  forever. No exception and no timeout, so the run blocks instead of failing.

- `C7YieldContext._queue`, one segment: Head 1, Tail 2. Slot 0 (SequenceNumber 32) is the

- No managed thread is running test code: the main thread waits in

- The full-suite dump `ExchangeAdminWeb.Tests_2384_20261021T140230_hangdump.dmp` shows the same

  `Sequence_*.xml` files (two full-suite, two isolated) record the `waitAt: "yield"` case as the

Whether the race is won depends on how soon a pool worker picks up the `Task.Run` body, so it
depends on the host and its load. It was won in CI and in one earlier local run that day. Here it
was lost every time (see Guard proof).

Production is sound. The page runs on the circuit's renderer synchronization context, which
runs every callback posted to it for the circuit's lifetime, so the same late continuation is
run. The page never blocks on a task. `ConfigureAwait(false)` at `Comms10kService.cs:255` would
not fix the test either: the page's own await at `Comms10k.razor:751` captures the context and
is completed from the pool, so that continuation would be the one posted late instead.

The two other `C7YieldContext` users have the same defect but cannot hit it today, because what
they resume completes synchronously: `C7ValidationCapturesInputsBeforeItsFirstYield`
(`Comms10kBusyStateTests.cs:208`) substitutes the resolver with a completed task, and
`C7SubmissionKeepsTheApprovedInputsAndCompletenessAcrossAwaits(false)` (line 287) resumes into
substituted auth and the synchronous `BulkJobs.Enqueue`. The Defender helpers `PausedContext`
(`DefenderSiteMatchingDeadlineTests.cs`) and `ControlledContinuations`
(`DefenderConcurrentEnrichmentTests.cs`) already pump until completion and are unaffected.

## Approach

Test-only. `C7YieldContext` becomes a pump, the shape the Defender helpers already use: `Post`
enqueues and releases a semaphore, and `Resume()` is replaced by `ResumeAsync(pending)`, which
waits for each post, runs it with the context installed, and stops only when `pending`
completes. Every continuation, early or late, is then run, as on the renderer context. Each wait
is bounded at 10 s (the theory's own bound for its gate) and throws `TimeoutException`, so a lost
continuation fails instead of hanging the run. The three call sites
`await context.ResumeAsync(pending)` where they called `context.Resume()`. No production change.

crosses a real thread hop.

the pool finishes the `Task.Run` body after the drain loop's last check. On this host that
happened in 30 of 30 pre-fix and mutated runs. In CI it did not always happen, so a regression
would hang here straight away but could pass CI.
