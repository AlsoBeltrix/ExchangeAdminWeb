## Approach

### As written before the code (branch `fix/psl10-a2y` from `eba9a5c3`; no merge of master, as briefed)

**Verified.** kd-54 put the reason behind a second call: `Components/Pages/AdminBulkJobs.razor` `RemoveJob` runs
`BulkJobs.DeleteJob`, and on a false reads `BulkJobs.GetJob(job.Id)` to say which refusal it was. Neither call is in a
try, so a store failure in either leaves the handler with no row and no banner, the exception going to the circuit -
and the read-back is the likelier of the two, running after a delete the store has just refused.

**Which option.** The first: the service returns the reason with the bool. It is strictly better than catching the
read-back, because `DeleteJob` already knows - it reads the job itself (`Services/Jobs/BulkJobService.cs` 242-255: `Get`,
then the module check, then `Delete`, whose `WHERE` takes only a terminal status) - so the page needs no second call,
there is no second failure mode to catch, and the reason stops being a guess made after the fact (a job removed by
another operator in between read "it no longer exists", which was true of the moment, not of the refusal).

**The change.**
1. `Services/Jobs/BulkJobService.cs`: `public enum BulkJobRemoval { Removed, NotFound, NotThisModule, NotFinished }`
   beside the service, and `public bool DeleteJob(string moduleId, string jobId, out BulkJobRemoval outcome)` - today's
   body, each return naming its outcome. The existing `DeleteJob(moduleId, jobId)` becomes
   `=> DeleteJob(moduleId, jobId, out _)`, so its other caller (`ConferenceRooms.razor` `RemoveJob`) and every test
   compile and behave unchanged. Shared code: a base version bump is due, outside this brief, and named in the hand-back.
2. `AdminBulkJobs.RemoveJob`: the richer overload, the reason from the outcome - "it no longer exists." (NotFound), "it
   has not finished." (NotFinished), "it belongs to another module." (NotThisModule, unreachable from this page, which
   passes the job's own module, but named rather than left to a wrong sentence) - and no read-back. The call sits in a
   try whose finally writes the row, so a store failure is audited Failed with its message and then thrown as before,
   rather than leaving no record: the hole kd-62 names, on the one call that remains.
3. Tests: `BulkJobServiceTests` - the outcome for each case (removed, gone, not finished, another module), and that the
   old overload still answers the same bool; `AdminBulkJobsCancelAuditTests` - kd-54's three refusals keep their rows and
   banners, and a new case drives a store that fails (a jobs database with no tables): one Failed row carrying its
   message, the exception still thrown. Mutations: the row's finally dropped (the kd-62 hole, reopened); the outcome
   ignored so every refusal reads "it has not finished."; `DeleteJob` reporting `NotFinished` for a job that is gone.
4. No module version moves here: Admin Bulk Jobs is at 1.2.0 on this branch from kd-53/54, and this is that fix's
   failure path. (kd-65 moves the Event Log's, separately.)
