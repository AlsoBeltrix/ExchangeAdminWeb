# kd-69: a cancel arriving during the configuration read still finishes as a successful lookup

**Severity**: LOW - read-only, but a cancelled run is still recorded as completed. `Services/ModuleCredentialService.cs`
about 58: kd-61 put the cancellation check first, so a token already cancelled throws. A token cancelled WHILE
`IsModuleCorrupt` or `GetValue` is reading meets no second check, and if that read then answers "unreadable" or

completes the activity as succeeded and writes a success audit row after the cancel. Distinct from kd-57, kd-58, kd-59
and from kd-61's own recorded gap about a caller answering before it calls this service.

## Known gaps

- A cancel that arrives after the last check and before the vault call's own is seen by that call, so the lookup still
  ends as a cancel; a cancel arriving after Delinea returns a credential is not, and the credential is handed back. The
  caller's next hop is where that lands, and for Recipient Lookup that is the on-premises read, which takes no token
  (kd-58's territory).
- kd-61's recorded gap stands: a caller that answers from its own state before calling this service would still finish
  a cancelled run.
- The reads are the store's; a store that blocks forever is not made cancellable by this - the check runs when the read
  returns.
- No circuit or browser ran: the service was called directly.
