# kd-87: the access re-check reads tokenGroups by SID, which Active Directory refuses, so every page is refused on the deployed build

**Severity**: HIGH - on the 2026-10-29 dev deploy every page request is refused with the neutral 403 ("Your access could not be
confirmed against Active Directory just now"). `Services/OperatorMembershipDirectory.cs` `Read` (about 155-205) runs
`Get-ADUser -Identity <SID> -Properties tokenGroups`; `tokenGroups` is a constructed attribute AD returns only from a
base-scope search, and an identity given as a SID is resolved by a subtree search, so AD answers "The requested search
operation is only supported for base searches." The read throws `DirectoryUnavailableException`, the page-request
revalidation (aud-a29g) and the circuit revalidation (aud-a29b) fail closed, and the operator is locked out of every page.
Landed 2026-10-21 (`cb3be915`), never run live before today. Prod is on the older build and unaffected.
**Status**: Fixed on branch, verified; closes on guard proof
**Branch**: `fix/kd87` (worktree `D:\source\ExchangeAdminWeb-wt\kd87`, from master `738c7b27`)
**Commit**: the commit that adds this line (its SHA in the implementer's hand-back)
**Reviewer**: implementer (candidate)

## Evidence

`D:\inetpub\ExchangeAdminWebDev\logs\app-20261029.log` 14:28:15, 14:50:16, 16:11:45; no occurrence in the 27th or 28th logs
(the code was not deployed). Each line ends "The access re-check could not be completed: The directory lookup for the
signed-in account failed: The requested search operation is only supported for base searches." The middle clause is
`Read`'s last catch (`catch (Exception ex)`, 197-202 at `738c7b27`), so AD's refusal reached the lookup as an exception
thrown by the command, not as an error record beside rows.

## Approach

- Two steps, both base-scope safe: resolve the account by SID without `tokenGroups` (`Get-ADUser -Identity <SID>` with
  `-Server` as today) to get its DistinguishedName, then read `tokenGroups` against the DN (`Get-ADUser -Identity <DN>
  -Properties tokenGroups -Server ...` - an identity given as a DN binds to the object, a base search; or `Get-ADObject
  -Identity <DN> -Properties tokenGroups`). Keep every existing rule: exactly one object, Enabled read, no groups is a
  failure, fail closed on any error, `Forget` the domain on failure, the cancellation token where it is today.
- Tests: the stand-in records both commands and their parameters; the SID read carries no `tokenGroups`; the DN read does;
  a stand-in that rejects `tokenGroups` on a non-DN identity with AD's exact message proves the old shape fails and the
  new one passes. Mutation: the DN step removed (the SID read asks for tokenGroups again) - the rejecting stand-in's test
  must fail.
- Shared service: base bump already owed (2.36.0 undeployed to prod absorbs it). No module bump.

## The fix (implementer, 2026-10-29; lines at this commit)

Read first, at `738c7b27`: `Read` (155-203) built one parameter set - `Identity` the SID, `Properties` `tokenGroups`,
`ErrorAction` Stop, and `Server` from `ResolveServer` when a NetBIOS domain is given - ran one `Get-ADUser` through the
cancellable overload where the session has one (171-173), and took exactly one non-null row, with no error beside it, to
`FromAccount` (120-135: `Enabled` must read as a bool, `tokenGroups` must yield a SID). Its catches (188-202) pass the
caller's cancel on, and otherwise `Forget` the domain's server and throw `DirectoryUnavailableException`, which
`CircuitMembershipRevalidator.CheckAsync` (173-176) turns into `LookupFailed`; the circuit's checks and the page-request
check both refuse on it. Reachable as described: M0 below is the read as it was, and the stand-in test fails on it with the
dev log's own words.

- **Two reads** (`Services/OperatorMembershipDirectory.cs`: `Read` 167-218, `ReadExactlyOne` 223-244, `WithServer`
  246-252; the class remarks 13-29, 37-48):
  1. **The account lookup** (174-182): `Get-ADUser -Identity <SID> -ErrorAction Stop`, `-Server` as before, and no
     `-Properties` - nothing beyond the cmdlet's default set, whose `DistinguishedName` is the only value taken. A name
     that is missing or blank is a failure (184-186) and no second read is made.
  2. **The group read** (188-199): `Get-ADUser -SearchBase <that name> -SearchScope Base -LDAPFilter
     "(objectSid=<SID>)" -Properties tokenGroups,Enabled -ErrorAction Stop`, with the same `-Server`. Its one row goes to
     `FromAccount`, unchanged.
- **Every rule kept, at each read** (`ReadExactlyOne`): the caller's token checked before and after the command, and the
  cancellable overload with the caller's token where the session has one - so a cancel during the lookup starts no group
  read; a cmdlet error is a failure; exactly one non-null row. The catches are unchanged, so a failure at either read
  forgets the domain's server and throws `DirectoryUnavailableException`, and a cancel is the caller's. Unchanged:
  `FromAccount`, `ParseSids`, `ResolveServer`, `Forget`, `GetMembershipAsync`, the admission gate, `TranslateGroupName`,
  and the revalidators and everything they do with the answer.
- **The cmdlet shape, and why neither of the two offered.** The brief offered `Get-ADUser -Identity <DN>` ("an identity
  given as a DN binds to the object, which is a base search") or `Get-ADObject -Identity <DN>`. Both rest on how the AD
  module finds an identity, and nothing in this repo or on this host shows that. The cmdlet's help says of `-Identity`
  only "The cmdlet searches the default naming context or partition to find the object", and of `-Partition` that for a
  distinguished-name identity the partition "is automatically generated from this distinguished name" - which reads as a
  search of that partition, not a read of the object (Get-ADUser on Microsoft Learn, read 2026-10-29). An unverified
  belief of exactly that kind about this read is what kd-87 is. `-SearchScope Base` states the scope in the command: "A
  SearchScope with a Base value searches only for the given user" - a base-scope search by definition, the one search AD
  computes `tokenGroups` in, whatever the module does with identities. `Get-ADUser` rather than `Get-ADObject` keeps
  `Enabled` as the module computes it, so `FromAccount` reads it as before; `Get-ADObject` has no `Enabled` (asking for
  it would be refused as an unknown property) and would need a new decode of `userAccountControl`. Assumption, not
  verified live: `-SearchBase <DN> -SearchScope Base` on a user's own name answers that user with `tokenGroups`, as AD's
  refusal text implies; the first live run is the next dev deploy.
- **Bound by SID** (`LDAPFilter`, 195). The class has always said its read is "Bound by SID, never by name", and a search
  at a name is a read by name: between the two reads the object at that name can change (a move or rename, then another
  account created there). With the filter, an object at that name that is not this account matches nothing and the read
  fails on the existing exactly-one rule - no new rule about what a row carries. The string-SID filter is the form this
  repo already sends AD (`ADDirectorySearchService.BuildSidFilter`, `ProtectedGroupMembership.GroupLookupFilter`),
  escaped the same way (`ProtectedPrincipalService.EscapeLdapFilter`, as `ResolveDomainServer` does). An implementer's
  addition beyond the brief's wording, kept because without it the class's stated binding would be false; the owner can
  veto it.
- **Docs**: the class remarks say what the two reads are and why. `IOperatorMembershipDirectory`, the revalidator's
  remarks and README "Session Revalidation" name `tokenGroups` but not the cmdlet, and stay true. Not edited: aud-a29b's
  design text and aud-a29g's cost section, which describe the one-read shape ("one `Get-ADUser -Properties tokenGroups`");
  they are history, and this record is where the shape now lives.
- **Cost**: one more `Get-ADUser` per lookup - two commands in the lookup's one runspace, one more round trip to the
  domain's directory web service. The 4-lookup cap, the 60 s bound (queueing and both reads inside it) and when a lookup
  happens are unchanged.
- **Version**: none here. A shared service, and the base bump is already owed for this release: 2.36.0, not deployed,
  absorbs it. No module bump.

**Operator-visible change.** On the deployed build every page was refused with "Your access could not be confirmed against
Active Directory just now". With this, a page loads when the directory confirms the operator's groups, as designed, and a
removed or disabled operator is still refused. Nothing else an operator sees changes. If the directory refuses the new
reads, the refusal is the same neutral 403, and the log line now names the read that failed ("The account lookup ..." or
"The account's group read ...").

- **The rest of the app.** A search of the app's code and scripts for `tokenGroups`, its two variants and the other
  constructed attributes AD restricts or computes (`msDS-User-Account-Control-Computed`, `msDS-ResultantPSO`,

  once more, as a deny-list prefix in the attribute editor, which reads nothing by it.

**A defect in a new test, found by the first full run and fixed before commit.** `ACancelDuringTheAccountLookupStartsNoGroupRead`
failed once in the first full run ("The lookup never ended.", 10 s) and passed in every class run. The test, not the
product: the stand-in cancels from inside the first read, on the lookup's own thread, and the test awaited the lookup
before waiting for it to end. Under load the await could be registered before the cancel landed, and then the cancel ran
the test's continuation inline on that thread, where the test waited for the thread it was on. The test now waits for the
lookup to end (its session disposed) before awaiting it (310-328). Shown deterministically with two temporary variants
of the test file, each delaying the cancel 300 ms so the test is already waiting: the old await-first shape (MD5
`3B836DF2F2AC3AC0E8844F9E971E8C62`) failed exactly so, "The lookup never ended." at 10 s; the new shape (MD5
`FC9892E0524217C58451668202AA3F55`) passed in 349 ms; the test file was restored byte for byte (MD5 above). Nothing in
production waits for a lookup's worker, so the product has no such wait. M0, M1 and M6 were run again against the final test
file: the same 21, 21 and 1 failures, M6's being this test.

## Known gaps

- **Not run against a live directory**, by instruction. What the new reads rely on is the cmdlet's help (above), AD's
  own refusal text, the default set carrying `DistinguishedName`, `SID` and `Enabled` (the help's example output), and the
  string-SID filter this repo already sends. The first real run is the next dev deploy. Live check: load a page as an
  operator holding a consulted group; expect the page, no `SessionRevalidation` refusal in the log or the audit; then
  aud-a29b's own live check (a removal ends the session within one interval).
- **The next unverified assumption on the same path** (aud-a29b Known gaps, first bullet, still open). The dev failure came
  before any row arrived, so `Enabled` arriving through `PowerShellDirectoryCommands` as a bool and `tokenGroups` as
  something `ParseSids` reads are first exercised live by the next deploy. If either arrives otherwise, every check fails
  closed again - with "The account's enabled state could not be read." or "The directory returned no group memberships
  for the account, which no real account has." in the log, not kd-87's line. Likewise if the app pool's identity may not
  read `tokenGroups` (the class remarks: the attribute then comes back absent). The remedy for all three is aud-a29b's:
  `Authentication:RevalidationEnabled` set to `false` and the app pool restarted, which is logged and audited.
- **The stand-in is a model.** It reproduces AD's rule and message, not the directory web service or the module.
  `RuntimeException` stands in for whatever the pipeline throws (the dev log shows only the message), and the "reported"
  case covers the same refusal arriving as an error record. It counts every `-Identity` read as a search that is not
  base-scope, a DN identity included - stricter than the brief's "any identity that is not a DN", on the reasoning above.
- **A move or rename between the two reads** fails that check closed (the group read finds nothing at the old name), as any
  directory failure does; the next check reads again.
