# kd-74: four pages let a second click or a dismissed banner disturb a run in progress

**Severity**: LOW to MEDIUM - found by the kd-72 sweep, a different shape from kd-72. (1) **Licensing Updates**: Apply has no
busy guard, so a double click runs a second bulk licence apply over the same rows - MEDIUM, a write repeated. (2) **Message
Trace Reports**: Download has no busy guard - a double click builds and pushes the file twice. (3) **Self-Service Groups**:
dismissing the result banner mid-run can skip the member-list refresh. (4) **Conference Rooms**: dismissing the result banner
mid-run makes the progress bar report not-succeeded on the two CSV applies (the prog-7 shape: completion read from a
dismissible field).
**Status**: In progress on `fix/kd73-kd74` - (1), (2) fixed and verified on branch; (3) not reachable as described, hardened
as prog-7 was (see its section); (4) next

## Approach

- (1), (2): a busy guard matching the button's disabled condition, in the kd-72 shape; test: a second click during a run
  is ignored (the stand-in counts calls); mutation: the guard removed.
- (3), (4): the completion and the refresh read from a local, not from the dismissible result field (as ExecuteOnPrem did
  in Mailbox Permissions 1.2.4 / prog-7); test: the banner dismissed mid-run, the refresh still runs / the activity still
  completes succeeded; mutation: the local replaced by the field.

## As implemented - (3) Self-Service Groups (implementer, 2026-10-27; lines at this commit)

- **Read first, at `0d6c272b` - and the premise does not hold there.** `Components/Pages/SelfServiceGroups.razor`
  `RemoveListedMember` (684) and `ChangeMember` (926) decided their member-list refresh on `changeResult?.Success` (then
  719 and 963), and the banner's dismiss (300) nulls that field. But each handler nulls `changeResult` at entry, before
  its first await, and `ShowFor` assigns it (709, 950) with no await between that assignment and the refresh test - the
  `finally` between them is synchronous. A dismiss is a browser event, dispatched only when the handler yields, so it
  cannot land in that stretch; a dismiss while the write is awaited nulls a field already null. No reachable interleaving
  skips the refresh. `ClickGateRegistry`'s exemption for that dismiss (SelfServiceGroups 300) rested on exactly this
  condition; the kd-72 note this sub-item came from did not take it into account. See "Record correction" below.
- **Changed anyway, as prog-7 did,** because the safety rested on where the awaits sat, and only the registry's prose
  protected that: an await added between the two - a notification moved after `ShowFor`, a reload awaited - would have
  skipped the refresh silently after a successful write (the registry's own words). Both refresh tests now read the local
  `completed` (720, 965), which the handlers' activities already completed from. Behaviour is unchanged on every
  reachable path: whenever the group is still shown, `completed` and the field hold the same outcome, and the
  `ReferenceEquals(selected, group)` test is unchanged.
- `ClickGateRegistry`: the exemption's `ConditionThatKeepsItTrue` (4378-4385) and the entry's remarks (4210-4215) described
  the old read; they now say no handler reads `changeResult` back, and name the tripwire. `ExpectedLineCount` 1286 -> 1288:
  both edits are at 718 or below, and every line-keyed control on the page is markup at or above 443 (read from the
  entry), so nothing else moves.
- Version: Self-Service Groups 1.14.1 -> 1.14.2 (`Modules/ModuleCatalog.cs` 877-881), the brief's bump; its comment says
  nothing the operator sees changes today.
- Page 1,286 -> 1,288 lines; `ProgressRegistry` names methods.
