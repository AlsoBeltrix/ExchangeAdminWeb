# g3: Account Lockout ran directory work before its cheap refusals, and `Executed` meant "was asked to execute"

**Severity**: LOW - nothing was logged off that should not have been: every refusal still refused. The cost was
order and wording. An execute request with no ticket, or from an operator without the Logoff permission, fetched the
module credential and read the directory (lockout events, or the sweep's computers) before it was refused, and the
administrators' mail then reported the refusal as a failed execution of zero machines.

## Fix

- One private method, `RefuseBeforeDirectoryWorkAsync`, holds the refusals that need no directory, in the order an
  operator was already told them: module access, readable configuration, then for an execute request the ticket and
  the Logoff permission. The sweep calls it in place of its own access and configuration checks (after its two input
  checks, as before); the lockout-sources path calls it for an execute request before discovery. A dry run on the
  lockout-sources path goes straight to discovery as it did.
- The Logoff refusal writes the audit row it always wrote (the path's action, target "(multiple)", Failed,
  "Authorization denied.", the ticket). The lockout-sources path opens a trace operation named for its action only
  when it refuses, so an allowed request's trace is what it was.
- `Executed` is true only once the remote step is reached on an execute request (a local set immediately before the
  remote call; the catch reports it). Every earlier return says false.
- The mail no longer keys on `Executed`. It is sent for every execute request, except one whose result is the
  missing-ticket refusal. Subject, rows and recipients are unchanged.
- `RunLogoffAsync` keeps its own ticket and permission gates: it is an internal test seam, and its second permission
  check immediately before the remote call is unchanged.
- No page text changed (the page never read `Executed`; it has no note about mail). README: one bullet under Account
  Lockout Remediation. No click-gate entry moved.
- App code: +95 / -54 lines (`git diff --numstat d8aee0a6~1 d8aee0a6 -- Services Components`).

## Mail, per outcome of an execute request (both paths unless said)

| Outcome | Before | Now |
|---|---|---|
| Missing ticket (blank, or invisible characters only) | Mailed as failed, 0 machines - with whichever message the request died on: credentials, discovery, or the ticket refusal if it got that far | **Nothing** |
| Not allowed to log users off | Mailed as failed, 0 machines - with the permission refusal only if credentials, discovery and the ticket were all good; otherwise with the earlier failure | Mailed as failed, 0 machines, error "You are not authorized to log users off." - always this refusal, before directory work |
| No target users / no search base or computers (sweep) | Mailed | Mailed (same) |
| No module access; corrupt module configuration | Mailed | Mailed (same) - still told before the ticket, so these mail with or without a ticket |
| Credentials unavailable | Mailed | Mailed (same) |
| Discovery failed, or no lockout events (lockout sources) | Mailed | Mailed (same) |
| Sweep resolved more computers than the limit | Mailed | Mailed (same) |
| No actionable machines | Mailed as success, 0 machines | Mailed (same) |
| All users blocked by protection; no user matched to a SID; permission lost before the remote call; exception | Mailed | Mailed (same) |
| Logoff ran | Mailed | Mailed (same) |
| Dry run, any outcome | Never | Never |

What an operator sees differently: with no ticket (the page's buttons already require one, so this is a direct or
stale call) the answer is "Ticket Number is required for logoff execution." even where the request would earlier
have died on credentials or found no events; without the Logoff permission the answer is the permission refusal in
those same cases, and its audit row is now written in them.

## Left alone, and why

- The mail for a refused execute still uses the logoff summary rows (machines, sessions, failures, all zero) with the
  refusal as its error. The plan asks for the order and the flag; the mail's shape is phase 3.
- Module access and configuration are checked twice on an allowed lockout-sources execute (the early check, then
  discovery's own). Both are in-memory; removing discovery's would change the dry run.
- README "Ticket presence" still says this service checks presence with `string.IsNullOrWhiteSpace`; that sentence
  was already out of date before this slice and is not about this defect.
- Finding IDs and history were stripped from the comments of the methods touched (`LogoffLockoutSourcesAsync`,
  `SweepScopedComputersAsync`, `RunLogoffAsync`, `EmptyLogoffResult`, `NotifyLogoffAdminAsync`) and nowhere else.
- Version: Account Lockout Remediation 1.3.6. No base bump: no shared code changed.
