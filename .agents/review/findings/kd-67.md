## Evidence

At `3bfdc1af` as admitted. Line numbers below are master `1d0a7fb2`.

**The four sites take the AD-first resolver, not the Exchange-target one.** `GroupManagementService.cs:63`,
`M365GroupManagementService.cs:209`, `MigrationService.cs:587` and `MfaReset.razor:367` all call
`ProtectedPrincipalService.ResolveWithExchangeFallbackAsync`, and their literal (`:68`, `:217`, `:592`, `:371`) is chosen
on that call's status. `ResolveExchangeTargetAsync`, the method aud-a2b and aud-a2c gave the new ambiguity sources, has
two production callers: `ConferenceRoomProtectionGate.cs:162`, which aud-a2aa fixed, and `PermissionValidator.cs:349`,
whose text is already neutral (`:356`, "it matches multiple directory objects"). There is no production override of
either method; they are virtual only as test seams.

**On the fallback path an `Ambiguous` is a `Get-ADUser` multi-match, and nothing else.**
`ResolveWithExchangeFallbackAsync` (`ProtectedPrincipalService.cs:507`) returns `Ambiguous` only as the status
`ResolveWithStatusAsync` handed it: for the typed string (`:510-511`, every status but NotFound passes straight through)
and for the canonical address in the alias case (`:542`, returned at `:557`). Where the two directories disagree it
returns `Unavailable` (`:554`, `:568`), never `Ambiguous`. `ResolveWithStatusAsync` (`:422`) produces `Ambiguous` at one
place, `:463-466`, catching an `InvalidOperationException` whose message contains "Ambiguous". The only such throw is
`:1013`, `Ambiguous: '{identity}' matches {users.Count} AD users.`, raised in `ResolveViaActiveDirectory` when the
`Get-ADUser` at `:999` returns more than one row; any other failure there is caught at `:468-472` as `Unavailable`.
(Assumption, not traced into PowerShell itself: none of its own exceptions on that path is an
`InvalidOperationException` whose message says "ambiguous".) `Get-ADUser` returns users.

**The non-user sources are out of reach from there.** `:636` (a cloud-only recipient with an on-premises namesake),
`:665` (the directories reading the string as different objects) and the mailbox-GUID holders (`:674` into
`ProveMailboxBackingAsync`, then `SelectMailboxBacking` at `:742` and `:753`, found with `Get-ADObject` so any class is
seen) are all inside `ResolveExchangeTargetAsync`. No caller of `ResolveWithExchangeFallbackAsync` can see them.

So at these four sites "matches multiple AD users" is accurate.

## Approach

- Each site uses the neutral `AmbiguousMessage` aud-a2aa introduced, or its module's equivalent; update the pinned
  test with the wording; one commit per module; mutation: one site's literal restored.

**Not taken, because it would make four accurate messages wrong.** aud-a2aa's `AmbiguousMessage` reads "it matches more
than one directory object, or Exchange Online and Active Directory do not name the same one". On the fallback path the
second clause is never the cause - a disagreement is reported as `Unavailable` - and the first is vaguer than the truth:
an operator who has a real collision of two user accounts would no longer be told that it is user accounts to look at.
A "module's equivalent" that stays true has to say users, which is what the four sites say now. Under the standing
mandate (find and fix bugs; do not significantly change intended functionality) replacing accurate operator text with
partly false text is a regression, not a fix, so no code was changed and no mutation was run.

**Nothing was taken from the earlier agent's worktree, either.** The brief named `git -C D:\source\ExchangeAdminWeb-wt\a2e
diff` as this finding's starting point. That unstaged diff holds no kd-67 hunk at all: it is kd-68's refusal-audit work
(`RoomOperationResult.RefusedAt`, `ConferenceRoomService.WithRefusal` and the `RefusedAt*` constants, threaded through
the Room Finder page and the bulk processor), which index.md records as superseded by aud-a2ad. The a2e agent's kd-67
output is only the staged record (`git -C ... diff --cached`), which contests the finding as this one does.

## What is true, and worth deciding

1. **The wording is only right while the call site keeps its resolver.** Conference Rooms' text went wrong the day
   aud-a2b moved its gate to `ResolveExchangeTargetAsync`, and nothing failed. Any of these four moving the same way would
   repeat it silently.
2. **The fallback path's callers word it five ways.** "multiple directory objects" (`BlockedSenderProtectionGate.cs:93`,
   `EmergencyDisable.razor:363`), "multiple directory users" (`IntuneDevices.razor:1086`, `RiskyUsers.razor:900`), "more
   than one directory user" (`CloudPasswordReset.razor:580`), "Target identity is ambiguous." (`AccountLockoutRemediationService.cs:464`,
   `:705`), and "matches multiple AD users" at the four named here. The four are the most precise; the two "directory
   objects" ones are, by the trace above, the least.

## Options

- **(a) Recommended: decline.** The four are accurate; close kd-67 with no code.
- **(b) Harmonise anyway**, to one wording across the fallback path's callers. If chosen, it should stay true on that
  path ("matches more than one Active Directory user" keeps the precision and drops the abbreviation), not borrow
  aud-a2aa's text, whose second clause cannot happen here; `MigrationMessageTests.cs:114` moves with it.
- **(c) (a) plus a tripwire**: one test that fails when a call site pairs `ResolveExchangeTargetAsync` with an "AD users"
  message - the regression that actually happened. No operator-facing change. Not added: it is outside this finding's
  approach.
