# kd-72: Delegation Report re-reads the bound address during a run, so a second submit can report one mailbox and audit another

**Severity**: MEDIUM - a production incident (owner, 2026-10-27): a report submitted for mailbox A, then for mailbox B, showed
A's progress label and A's results while the audit row recorded B; the third submit was right. `Components/Pages/DelegationReport.razor`
reads the live bound field `emailAddress` at 154 (progress label), 158 (the service call), 165 (the audit row) and 170
(the catch path). The input is `@bind` on change (27-28), no `@bind:event="oninput"`, and `RunReport` (144-149) captures no
target and has no busy guard. Enter's keydown reaches the server before the change event, so the run starts on A; at the
await on 158 the queued change event applies B; the audit on 165 then records B against A's results. The click path can
race the same way. `MailboxPermissions.razor` 352-362 documents this bug class and captures the target above its first
await; `RecipientLookup.razor` 29-30 and 214 bind on input and capture once.

## Approach

- Capture `var target = emailAddress.Trim();` once before `Progress.Begin` and use it for the label, the service call, the
  audit row and the catch path; `@bind:event="oninput"` on the input; an `if (isLoading) return;` guard at the top of
  `RunReport` so a second submit during a run is ignored rather than re-entered.
- Test: a service stand-in that blocks until released; submit A, change the field to B while blocked, release; assert the
  audit row, the result and the label all say A, and a second run then says B. Mutation: the capture removed (the audit
  row reads B); the guard removed (a second submit re-enters).
- Delegation Report module version bump; ClickGate / Progress re-anchor if line counts move.
- **Sweep**, same slice, one commit per page found: every page under `Components/Pages/` whose run handler reads a
  `@bind`-bound field after its first `await`, or binds a submit field on change rather than on input. List every page
  checked and the verdict in this record, so the sweep is auditable.

## Record correction

The severity line says "The click path can race the same way." It cannot, in this shape: a click moves focus to the
button, and the box's change event fires on that blur, before the click, so the server holds the new address when the
click arrives. The Enter path is the one that races, because Enter's keydown is dispatched in the box before its change
event. Left as written above; noted here. Both paths now meet the guard and the capture.
