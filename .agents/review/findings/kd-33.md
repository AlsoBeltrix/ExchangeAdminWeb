### As implemented (implementer, 2026-10-23, branch `fix/a68-kd2`; lines at `ee5caf05`)

- Where a row is missing, settled by reading the executors: `Components/Pages/Migration.razor` `ExecuteBatchAction`
  (`var result = await action();` 3319, the row at 3324, the catch at 3349-3352), `ExecuteUserAction` (3383, 3388,
  3412-3415), and the two bulk loops (`await action(batchName)` 3578, the row at 3581; `await action(email)` 3727, the row
  at 3730). A throw out of the action leaves the try before the row, and the run's loop before its batch's row.
- What can throw, settled by reading the base: every action these executors run is a `MigrationService` write over
  `RunAsync` (`Services/MigrationService.cs` 1238, 1271, 1307, 1321, 1566, 1578, 1590, 1606, 1618, 1630), which turns a
  throw inside its delegate into a failed result (`Services/ExchangeServiceBase.cs` 49-107); what it lets out is the
  pool's - the borrow, its connect (a sign-in that fails), and the retry's borrow after a first attempt the pool read as
  never having run (`Services/ExoConnectionPool.cs` 492-548).
- Failed or Undetermined, by aud-a73's rule as aud-a76 left it: the page cannot tell a throw before the command from one
  after, so the service says so, as the permission writes do since aud-a76. Each of the ten writes takes a
  `PermissionWriteSubmission` (`Services/PermissionWriteSubmission.cs`): `TrackAsync` around the `RunAsync` call and
  `Submitting()` immediately before its first write command (for the approval, before `Set-MigrationUser
  -ApproveSkippedItems`, after its reads). A throw before then is a `PermissionWriteNotSubmittedException`, its message
  the cause's; one after goes out as it is. The mark is never cleared, so a first attempt that reached its command keeps
  a retry's failed sign-in Undetermined (aud-a76's rule).
- The page: one helper, `AuditedIfItThrows`, around each executor's `action(...)` call, in place. A throw is audited
  through `LogMigrationAction` with `success: false` and filed Failed when the write was never sent - "Nothing was
  written: the connection to Exchange failed: <cause>." - or Undetermined - "Whether the change was made could not be
  confirmed: <cause>." - the cause through `ResolveFailure` (aud-a23i), looked for inside the not-sent wrapper as
  `PermissionChangeFailure.Banner` does. The audit call is guarded; the throw goes on to the executor's catch, so the
  banner, the activity and the run's end are as before.
- `Services/AuditService.cs` `LogMigrationAction` (192) takes a last optional `AuditResult? filedAs = null`, as
  aud-a73 gave the two permission methods, through the same `ResultText`; every other caller writes the row it wrote.
  App-wide: yes (the shared audit service).
- Tests: the ten writes, built not to connect, say nothing was sent; a write whose command was sent and whose retry
  cannot connect goes out as it is; each executor, over the real service, files the in-flight target's row Failed for a
  failed sign-in and Undetermined for a sent-then-failed retry, in the cause's own words. Mutation: the catch row dropped.

## Known gaps

- The banner and the activity of a single action that threw still read the raw `ex.Message`: kd-34's. Neither says
  that a change may have been made when the row is Undetermined; the row does.
- A write that threw sends no admin notification, in all four executors (the notification follows the action), and a
  bulk run that throws part-way skips what follows its loop: the batches or mailboxes accepted before the throw stay
  ticked, their stored reports are not invalidated, and the run's one notification is not sent. Named as candidates.
- Both creates (`CreateSingleMigrationBatch`, `CreateMigrationBatch`) write their `LogMigrationBatch` row only once
  `CreateMigrationBatchAsync` returns, and it lets a failed sign-in out the same way: the same gap, outside this record's
  sites. Named as a candidate.
- The marker's names say "Permission" (`PermissionWriteSubmission`, `PermissionWriteNotSubmittedException`); they mark a
  Migration write the same way. A rename touches the permission services and pages; not done here.
- Exchange's pre-check text the pool retries on is the test's stand-in; that the live module still words it so is
  aud-a76's assumption, unchanged. No circuit or browser ran: the executors were driven directly.
