# kd-10: Blocked Senders - a failed unblock by an authorised servicer drops the servicer note from the audit row

**Severity**: LOW - audit evidence. `Components/Pages/BlockedSenders.razor` about 498: on a failed unblock the servicer note is not written, so the row does not say who was authorised to try. The pgwt-7 rule puts the note on every outcome.

## Evidence

At `e3cc2d7a` on `fix/kd-misc` (the line is pre-existing). Trigger: a servicer's unblock fails. Predicted failure: the audit row lacks the servicer note.

## Approach

Re-read at `e3cc2d7a`:

- `Components/Pages/BlockedSenders.razor:498-506` - the `UnblockSender` row:
  `var serviced = (opResult.Success || outcomeUnknown) && !string.IsNullOrWhiteSpace(gate.AuditDetail) ? new Dictionary<string, object?> { ["protectedPrincipalServiced"] = gate.AuditDetail } : null;`
  then `Audit.LogModuleAction(..., opResult.Success, ..., errorDetail: opResult.Success ? null : opResult.Message, extra: serviced);`.
  Before kd-6 the condition was `opResult.Success && ...` (`eb017102:481`); kd-6 widened it to an unconfirmed outcome and
  left a plain failure out.
- `gate.AuditDetail` is set only by `BlockedSenderGateDecision.AllowAsServicer` (`Services/BlockedSenderProtectionGate.cs`,
  the protected-and-serviced branch of `EvaluateAsync`): the target IS protected and this operator was allowed because
  they hold the module's servicer grant. Every deny, and every ordinary allow, carries none.
- The rule: `Models/PermissionResult.cs:83-87` (pgwt-7) - "After a servicer override EVERY outcome - success or failure -
  must reach the audit with the note, or a failed write on a protected target loses the record of who was authorised to
  attempt it".

What changes: the condition becomes `!string.IsNullOrWhiteSpace(gate.AuditDetail)` - the note rides the row whatever the
outcome (success, failure, unconfirmed). It still goes in `extra`, never `errorDetail`, and the literal
`extra: serviced` that `PageAuthorizationRecheckTests.BlockedSenders_ServicedUnblock_IsRecordedWhereSuccessAuditsSurvive`
pins is kept. Edited in place: the comment above it is reworded on the same lines, so the page's line count is unchanged
(the page is `NotYetConverted` in `ClickGateRegistry`, so nothing keys its lines today, but the brief asked for it).

A guard that drives the compiled page: `ConfirmUnblock` by reflection, the real `BlockedSenderProtectionGate` over a
scripted protected-principal service that reports the target protected, and a section-access store granting the
operator's group the module's servicer key - so the gate's own `AllowAsServicer` produces the note - with the unblock
answered by the stub cmdlets (kd-6's `MigrationStubExchange`): once failing, once succeeding. Both rows must carry the
note.

Declared files: `Components/Pages/BlockedSenders.razor`, `ExchangeAdminWeb.Tests/BlockedSendersServicedUnblockAuditTests.cs`
(new), `Modules/ModuleCatalog.cs` (one comment line), this record. Module version: Blocked Senders is already at 1.5.0 on
this branch for kd-6, unreleased; this goes into that version's catalog comment rather than a second bump.

Mutation: the note dropped on failure (the condition `opResult.Success && ...` restored).
