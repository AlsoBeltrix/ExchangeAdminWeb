# kd-75: Conference Rooms can start its first write after the operator cancelled, while waiting for a pool connection

**Severity**: MEDIUM - the kd-73 (2) check at `Services/ConferenceRoomService.cs` about 630 runs before `RunAsync`, and
`RunAsync` supplies no token to the pool, whose `borrow()` (`Services/ExoConnectionPool.cs` about 507) awaits a free
connection before the callback runs. With every connection busy, a cancel during that wait is not seen; when a connection
frees, `Set-Place` (about 637-652) and the remaining writes proceed, though nothing had been written at the cancel.

## As implemented (implementer, 2026-10-27; lines at this commit)

Read first, confirmed at `ec5a19f7`: `SetRoomMetadataAndListAsync` checks the token at 632 (kd-73 (2)) and then calls
`RunAsync` (`Services/ExchangeServiceBase.cs` 49), which hands `RunWithRetryAsync` a borrow with no token
(`Services/ExoConnectionPool.cs` 455: `() => BorrowAsync()`); `RunWithRetryCoreAsync` awaits it (507) before the callback, and
`BorrowAsync` waits up to two minutes for a slot (294). `RunAsync` catches every throw of its callback and returns it as a
failed result (`ExchangeServiceBase.cs` 70-99), so a cancellation thrown in the callback would have been a failed Set-Place,
filed Failed in the framework's words.

- **The look inside the call** (`Services/ConferenceRoomService.cs` 639-655). The Set-Place callback's first statement looks at
  the token; cancelled, it marks `cancelledBeforeSetPlace` and returns before the trace step, the command or `Invoke`. A
  retry runs the callback again and looks again: the pool retries only on the precheck error that proves the first
  attempt sent nothing, so a cancel between the attempts ends the row the same way.
- **The cancellation surfaced** (670-673). Once `RunAsync` has returned - the connection back in the pool, the callback
  having sent nothing and so returned a clean result - the mark is thrown as `OperationCanceledException(cancellationToken)`,
  exactly as the check before `RunAsync` throws. The page's existing catch (`Components/Pages/ConferenceRooms.razor` 1084)
  takes it when its activity's token is cancelled: banner and row error "Cancelled by the operator. Nothing was written.",
  the row filed Cancelled (kd-57), the administrators told as for a row that failed. "Nothing was written" is true by
  construction: nothing before Set-Place writes, and Set-Place was not sent.
- kd-59's rule kept: nothing after Set-Place takes the token. The bulk job passes `CancellationToken.None`, so its rows are
  unchanged.
- Comments brought into line, nothing else: the parameter's doc (504-514) and, in place on their own lines, the page's call
  comment (1075) and catch comment (1086). The page stays 1,791 lines, so `ClickGateRegistry` and `ProgressRegistry` do
  not move.
- Version: Conference Rooms 2.19.4 -> 2.19.5 (`Modules/ModuleCatalog.cs` 1070-1072). The service is the module's own; no
  shared service changed, so no base bump.

**What the operator sees**: a cancel made while every Exchange Online connection is busy now ends the setup the way a cancel
before the wait already did - "Cancelled by the operator. Nothing was written." - instead of the room being changed once a
connection frees. Nothing offered or withdrawn.
