# kd-73: two cancel checks missing after kd-59 - between Message Trace's cloud search windows, and before Conference Rooms' first write

**Severity**: LOW - the operator's cancel is honoured a little late or not at all at two points. (1) Message Trace's chunked
cloud search does not check the activity's token between windows, so a cancelled search is filed only once the cloud
windows finish (about ten seconds at most). (2) In Conference Rooms a cancel that lands after the last pre-write credential
fetch and before `Set-Place` is not noticed; one token check immediately before `Set-Place` closes it, and keeps kd-59's rule
that nothing after the first write takes a token.

## As implemented - (1) Message Trace (implementer, 2026-10-27; lines at this commit)

- Read first, confirmed at `0d6c272b`: `Services/MessageTraceService.cs` `GetChunkedCloudMessageTraceAsync` ran its windows
  in a `foreach` with no token in reach - the method took none, and `GetMessageTraceAsync` called it without one - so a
  search wider than one window ran every cloud window whatever the operator did. A cancel during the on-premises half's
  credential fetch came out only after the last window (kd-59's known gap); a cancel landing after that fetch was not
  noticed at all, and the search was filed as one that ran to its end.
- The method takes the search's token (379-381), handed on by `GetMessageTraceAsync` (29), and looks at it before every
  window but the first (392-395): `cancellationToken.ThrowIfCancellationRequested()`. The cancellation leaves through
  `RunMessageTraceBackendAsync`, whose kd-59 filter lets a cancellation of that token out as it is; `Task.WhenAll` ends
  cancelled; the page's existing `catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)`
  (`Components/Pages/MessageTrace.razor` 871) shows and files it Cancelled, "Cancelled by the operator", and `RunTrace`
  completes the activity not succeeded with the phrase. No page code changed.
- Unchanged, on purpose: the window under way runs to its end (no cloud read takes the token - kd-58, held for a plan); a
  search of one window is not looked at (the method's own rule, "must behave exactly as it did before"); a cancel during
  the last window leaves no window to stop, so that search comes back whole and is filed as it was; and the on-premises
  half, which takes no token after its credential fetch, is still awaited before the cancel comes out.
- Comments brought into line, nothing else: the parameter's doc (15-21) and the method's remarks (374-377) in the
  service; the page's catch comment (873-875) and `RunTrace`'s call comment (832) name the cloud windows beside the
  credential fetch. The page grows 1,424 -> 1,425 lines (the catch comment is a line longer); it is "not started" in
  `ClickGateRegistry` (no line-keyed entries), and `ProgressRegistry` names `RunRealtimeTrace`, still present.
- Version: Message Trace 1.8.4 -> 1.8.5 (`Modules/ModuleCatalog.cs` 542-544). The service is the module's own; no shared
  service changed, so no base bump.
- Test stand-in: `MigrationStubExchange` gains a `Get-MessageTraceV2` stub (661-665) - logged on every call, answering no
  messages - and `Behaviour["TraceWindowStalls"]`, a gate a call waits on once logged (92-100). No other test runs that
