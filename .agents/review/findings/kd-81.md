# kd-81: a Mailbox or Calendar Permissions change waiting for a pool connection is still made after the operator cancelled

**Severity**: MEDIUM - the kd-75 class in the two permission modules. The single Exchange Online change runs under an activity
whose token reaches neither the change nor the location read before it, and the change's wait for a pool connection takes
no token; once the operator confirms the cancel the change is still made when a connection frees, and it is filed and
notified as made. The on-premises half has the same fault deeper (throttle wait, runspace open and connect before the send
mark take no token - kd-59's recorded gap); that half is `docs/CancellationDepth-Plan.md` slice A5, because it reaches the
on-premises machinery.
**Status**: Cloud half fixed on branch, verified; closes on guard proof; on-premises half in `docs/CancellationDepth-Plan.md`
A6/A7 (the plan's numbering - the admission and the brief said "A5"; see "Plan numbering" below). One module per commit,
Mailbox Permissions then Calendar Permissions. Admitted 2026-10-28 from the CancellationDepth planning agent's reading at
`d8af27a8`
**Branch**: `fix/kd81` (worktree `D:\source\ExchangeAdminWeb-wt\kd81`, from master `113f4734`)
**Commit**: one per module - each module's is the commit that adds its section below (`git log -- .agents/review/findings/kd-81.md`)
**Reviewer**: implementer (candidate; reproduced by the record's mutants - the look inside the call removed, the change is made
after the cancel, in each module)

## Evidence

`docs/CancellationDepth-Plan.md` section 14 and slices A4/A5; the kd-75 record for the shape.

## Approach

- Cloud half (this row): as kd-75 did in Conference Rooms - check the activity's token inside the pooled callback
  immediately before the first write (the Add/Set command), and surface a pre-write cancellation as Cancelled in kd-57's
  words with nothing written and no notification; the location read before it takes the token where the seam exists.
  Only the activity's own token is the operator's cancel. Tests per module: pool saturated, cancel during the wait,
  connection freed - no command runs, row filed Cancelled, no notification. Mutation: the in-callback check removed.
  Patch bumps for both modules.
- On-premises half: plan slice A5, not here.
- Kept to (implementer, 2026-10-28): kd-57's filing - result "Cancelled", the words kd-59 built on its phrase,
  `PermissionChangeFailure.CancelledBeforeTheWrite`, "Cancelled by the operator before the change was sent. Nothing was
  written." - and its rule that only the activity's own token cancelled is the operator's cancel; kd-59's that nothing after
  the first write command looks at the token; kd-76's that a token already cancelled starts nothing. Not touched, as
  briefed: the pool, `RunPooledQueryAsync`, `RunAsync` and the on-premises steps (the throttle, the runspace, the connect).
  The location read's on-premises credential fetch takes the token through kd-37's existing seam, and nothing else
  on-premises does. The change's wait for a connection still takes no token (the plan's E1/E4, slices A1/A2), so the cancel
  is seen once a connection frees - before anything is sent.

## As implemented - Mailbox Permissions (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `113f4734`. `SubmitSingle` (`Components/Pages/MailboxPermissions.razor`) opens its activity (381) and
handed its token to nothing - not the location read (461), not the change (488-489). The change,
`Services/MailboxPermissionService.cs` `AddMailboxPermissionsAsync` and `RemoveMailboxPermissionsAsync`, ran
`submission.TrackAsync(() => RunPooledQueryAsync(...))` (53, 109); `RunPooledQueryAsync` (`Services/ExchangeServiceBase.cs`
113) hands the pool a borrow with no token (`Services/ExoConnectionPool.cs` 455, `() => BorrowAsync()`), which waits up to two
minutes for a slot (294) before the call runs (507). A cancel made during that wait was seen by nothing: once a connection
freed, the call read the mailbox and the trustee and sent the rights, and the page filed the row Success and sent the
administrators', the user's and the owner's notifications. Three facts the fix rests on, read there too: `RunPooledQueryAsync`
lets a throw of its call out to its caller (`ExchangeServiceBase.cs` 118-133); the pool's core gives the connection back for a
throw whose words do not name a dead session (`ExoConnectionPool.cs` 514-530); and `TrackAsync` makes any throw before
`Submitting()` a `PermissionWriteNotSubmittedException` (`Services/PermissionWriteSubmission.cs` 44-54).
