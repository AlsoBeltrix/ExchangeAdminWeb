# kd-39: ProcessBulk's finally calls Complete with no guard, so a throw there escapes the handler

**Severity**: LOW - the aud-a70 (9) shape on the bulk path. `MailboxPermissions.razor` about 632, `CalendarPermissions.razor` about 589.

## Evidence

At `ea565cbd`. Trigger: `Complete` throws. Predicted failure: an unhandled exception out of the handler after the writes.

Re-read at `f5c8c057`, both pages unchanged in this respect: `ProcessBulk`'s `finally`
(`Components/Pages/MailboxPermissions.razor` 629-633, `CalendarPermissions.razor` 586-590) sets `isLoading = false` and
then calls `bulkActivity.Complete(...)` bare, as its last statement. By then the service has written and audited every
row, the run is published to `bulkResult`, its summary row is written and the administrators are told (kd-38). The
handler's own catch sits above the `finally` and never sees a throw from it, so a completion that throws leaves
`ProcessBulk` by exception - with no ErrorBoundary in this app (aud-a70 (9)), out of the circuit - and the finished run
reads as failed. Latent: the shipped `ActivityProgress` cannot throw there (`Raise` swallows a subscriber's throw); only
another `IActivityHandle` could. aud-a70 (9) guarded the pages' other two completions for the same latent reason and left
this one.

## Approach

- The same guard (9) added to SubmitSingle's catch and ExecuteOnPrem's finally; test; mutation: guard removed. In place.

The implementing agent's (kd39-kd41 agent, `fix/kd39-kd41`, 2026-10-27). The aud-a70 agent started this on `fix/a70`
against `4c12dcbd` and was stopped before committing; its uncommitted diff was re-read hunk by hunk against `f5c8c057` and
applied by hand, with the changes named below.

- The call goes into its own try/catch on its own line - (9)'s shape, in place: the catch logs a warning naming the file
  and the run stands. `isLoading` is already false above it. Both pages keep 808 and 762 lines, so no ClickGateRegistry
  entry moves and `ExpectedLineCount` holds; ProgressRegistry still finds `bulkActivity.Complete(` after its `Begin`.
- Changed from the earlier draft: the warning names the file and says "the run stands", kd-38's wording for the same
  handler ("The progress of the CSV run on {File} could not be completed; the run stands"); the test also asserts the
  write was sent; Mailbox Permissions 1.6.1 and Calendar Permissions 1.4.1 (the draft bumped neither).
- Test (`PermissionPagesSelfGrantTests.ABulkRun_WhoseProgressCannotComplete_StandsAndNothingEscapesTheHandler`, both
  pages, through `ProcessBulkGrant` with `ProgressThatCannotComplete()`): the handler returns, no banner is set, the run
  stands (one success, the write sent), the completion was asked once with `(true, null)`, and the throw is logged once.
- Mutations: M39 the Mailbox guard removed, E39 the Calendar guard removed.
