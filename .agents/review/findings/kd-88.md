## Approach

1. **Seed set from `tokenGroups`, not a domain-wide walk.** Read the target's `tokenGroups` with a base-scope search at its
   DN (the kd-87 shape: `Get-ADUser -SearchBase <dn> -SearchScope Base -LDAPFilter (objectSid=<sid>) -Properties
   tokenGroups`) against the target's own domain, under the directory-read credential. It is the directory's precomputed
   transitive list of every security group the account is in, primary group included. Compare its SIDs with the resolved
   protected groups' SIDs. For a protected group that is a domain-local group of ANOTHER domain (hole 1), ask that domain
   the anchored question with the tokenGroups SIDs/DNs as seeds, as the evaluator does today - never unanchored. For a
   protected group that is a distribution group (absent from tokenGroups), ask the anchored question only. No unanchored
   in-chain query may remain anywhere; a tripwire test asserts it.
2. **One credential fetch per operation.** The directory-read credential is fetched once for a single change and once for a
   bulk file (aud-a70's own rule for the file), and handed to every check in that operation.
3. **A warm directory session.** The reads reuse the pooled/cached runspace the directory search service already keeps
   (`GetOrCreateRunspace`); no fresh AD-module import per check.
4. **Timing in the log.** One INF line per check: "Protected-principal check for {target} took {ms} ms ({reads} directory
   reads, {fetches} credential fetches)" so the owner can read the duration on dev. Target: under two seconds end to end on
   a warm session; the record states the measured figure after the owner's redeploy.
- Fail-closed rules unchanged: an unreadable tokenGroups, an unresolvable configured group, any error is a refusal; audit
  shape unchanged. Tests: the stand-in directory records every query and credential fetch; assert exactly one fetch, the
  base-scope tokenGroups read, no unanchored in-chain filter, the anchored query only for cross-domain domain-local and
  distribution protected groups, every hole case from aud-a3b still refused/detected. Mutations: the unanchored query
  restored; a second credential fetch introduced; the primary group dropped from the seeds. Shared service: base bump already
  owed. Then the owner redeploys dev and grants once; the log line gives the duration.

### 1. The groups an account is in are its token; nothing searches for whatever contains the target

At `280ff007`, `ProtectedGroupMembership.Evaluate` found the target's groups with `GroupsContainingAny` - one
`Get-ADGroup -LDAPFilter (|(member:1.2.840.113556.1.4.1941:=<target>)(member:...:=<primary group>))` over the target's
whole domain, every group of it whose member chain reaches the target - then `UniversalGroupsContainingAny`, the same over
every universal group of the forest at a global catalog. The first is the read the dev log shows timing out at the domain
controller (two minutes); the second is the same shape forest-wide. Both are gone from the seam and the code.

- **An account** (`RequiresPrimaryGroup`: a SID and not a group): after the target read (unchanged), one more read -
  `IProtectedGroupDirectory.ReadTokenGroups`, in `PowerShellProtectedGroupDirectory` a `Get-ADObject -SearchBase <its DN>
  -SearchScope Base -LDAPFilter (objectSid=<its SID>) -Properties tokenGroups -Server <its domain>` under the
  directory-read credential: kd-87's shape, which loads pages on the dev build since kd-87 merged. Its SIDs are read with
  the access re-check's parser (`OperatorMembershipDirectory.ParseSids`). The token a domain controller of the account's
  own domain computes carries its own domain's global and domain-local groups, every universal group of the forest (the DC
  expands them through a global catalog - aud-a3c) and the primary group (hole 2). **A token that does not carry the
  primary group fails closed** ("does not carry its primary group"): the attribute withheld from the reader comes back
  absent, and an empty token is not "in nothing". Each resolved protected group is compared with these SIDs.
- **What a token cannot carry is asked of the links, by name.** A protected group the token is not complete for - a
  distribution group, or a domain-local group of another domain (hole 1) - and, for a target with no token at all (a
  group, a contact), every protected group, is answered from the target's ancestry: `ReadMemberOf`, one
  `Get-ADObject -LDAPFilter (|(distinguishedName=<a>)(distinguishedName=<b>)...) -Properties objectSid,memberOf` per level
  (50 names a read), at a DC of the target's domain for that domain's objects and at the global catalog for all of them,
  starting from the target and, for an account, its primary group. A read of named objects, never a search for whatever
  contains them. Every object asked for must come back - each is the target or a group a link named - or the answer is
  incomplete; so is a nesting past 64 levels or 10,000 groups. A domain-local protected group not found there gets the one
  anchored question left, `DomainLocalGroupContainsAny` (`(&(distinguishedName=<group>)(|(member:...:=<seed>)...))`, asked
  of the group's own domain) with every DN the ancestry reached - the evaluator's hole-1 question as before, now seeded
  with distribution groups too.
- **A security group the token does not carry is not a member** (`TokenAnswers`): its own domain's global and
  domain-local groups and every universal group are in the token when the account is in them, and a global group of
  another domain cannot hold it. No link is read for the common case.
- `DirectoryGroup` carries `Security` (the module's `GroupCategory`; `GroupProperties` asks for it). A category that
  cannot be read counts as not security, so it takes the path that reads the links - more reads, never fewer.
- Seam (`IProtectedGroupDirectory`): `ReadTarget`, `ReadTokenGroups`, `ReadMemberOf`, `ResolveDomainServer`, `FindGroups`,
  `FindObjectDnsBySid`, `DomainLocalGroupContainsAny`. `ContainsAnyFilter` and `UniversalContainsAnyFilter` are gone; the
  in-chain rule is written only inside `GroupContainsAnyFilter`, anchored on the group's DN. The three callers of the
  evaluator - the protected-principal check, the self-grant check (aud-a52/a60) and the self-service resource-domain Deny
  check (aud-a4b finding 7) - all take it.
- **Reads a grant now costs** (single-domain configuration of security groups given by DN, the usual one): the target
  read, the token read and one read per configured group - three for one protected group, against the 2026-10-21
  version's target read, primary-group lookup, the domain-wide walk, the forest-wide walk and the entry reads. A
  distribution group, a domain-local group of another domain or a group target adds two reads per level of nesting and,
  for a domain-local group, its one anchored question.

### 2. One credential fetch per operation

At `280ff007` the protected-principal directory-read secret was fetched by each read that needed it:
`ResolveWithStatusAsync` (once per resolution, twice when the canonical address is re-read), `FindMailboxGuidHoldersAsync`
(the mailbox proof) and `CheckGroupMembershipAsync` (the group check) each called
`DelineaService.GetCredentialsBySecretIdAsync` - the three fetches of the dev log, 4.1 s, 2.7 s, 2.7 s - and the self-grant
check fetched it again (`PermissionValidator.DirectoryReadCredentialAsync`, once per run since aud-a61). A bulk file paid the
first three per row.

- **`Services/DirectoryReadOperation.cs` (new).** One operation's directory-read secret, carried by the async flow
  (`AsyncLocal`), so no virtual method of the protected-principal service changes shape. `Begin()` begins an operation or
  joins the one the flow is in; only the outermost dispose ends it. `DirectoryReadSecretAsync(secretId, fetch)` runs the
  fetch once per operation and Secret ID and hands every later caller its answer - the secret, or its failure: a fetch that
  failed is that failure for the rest of the operation and is not repeated in it (aud-a61's rule). Outside an operation it
  fetches as before. Nothing outlives the operation: the next change fetches afresh.
- **`ProtectedPrincipalService`**: the three fetches go through `DirectoryReadSecretAsync` (a fetch that throws reads as not
  retrieved, as the store's own failures already did). `ResolveExchangeTargetAsync` and `ResolveWithExchangeFallbackAsync`

  `DirectoryReadSecretFetch` (null in production: the store, as before) and `DirectoryRunspace` (the session the three read
  sites open, unchanged in production; still one per read until item 3).
- **`PermissionValidator`**: `DirectoryReadCredentialAsync` fetches through the operation, so the self-grant check shares the
  protected-principal check's fetch; `ValidateTargetMailboxAsync` begins an operation over its resolution, its check and the
  check of the typed string.
- **The single change**: `Components/Pages/MailboxPermissions.razor` 405 and 704, `Components/Pages/CalendarPermissions.razor`
  383 and 658 - `SubmitSingle` and `ExecuteOnPrem` begin one operation on the line that reads the operator's principal, ahead

### 3. A warm directory session

At `280ff007` every group check built a runspace, imported the ActiveDirectory module and only then read
(`CheckTransitiveGroupMembership`: `RunspaceFactory.CreateRunspace`, `Import-Module ActiveDirectory -ErrorAction Stop`),
and the next check did it all again; so did the resolution and the mailbox proof, each in a runspace of its own.

- **`Services/DirectorySessionPool.cs` (new)**: warm sessions - runspaces with the module already imported (through
  `ActiveDirectoryModuleImport.Import`, its first command, as before) - lent to one check at a time and given back. It keeps
  `ADDirectorySearchService.GetOrCreateRunspace`'s rule: a session is reused while it stays open, and one a read failed in
  is thrown away and a fresh one built the next time (`Fail`), so a session a failure may have broken is never lent again.
  At most four; a check that finds none free within 30 s is refused as busy (`TimeoutException`, which the group check's
  existing catch turns into its "Group membership check failed" refusal). A session holds no identity: every read in it
  names its own `-Credential`, or runs as the app pool exactly as it did in a session of its own.
- **`ADDirectorySearchService.CheckSessions`** (new): the warm sessions for checks, created when first asked for, from
  `CreateCheckRunspace` (the default session; a seam like `CreateSearchRunspace`). Kept apart from the searches' own
  cached runspace: one runspace under one lock serves the picker's keystrokes (30 s wait), and a check queued behind them - or
  they behind a check of a slow domain controller - would cost the operator either way. The class summary says the searches
  are still never used for authorization; the sessions are lent, not its searches.
- **`ProtectedPrincipalService`** takes the directory search service (an optional constructor parameter, so the suite's
  direct constructions are unchanged; DI supplies it) and borrows its sessions (`DirectorySessions`); built without one, it
  keeps warm sessions of its own over `DirectoryRunspace`. The group check runs in a lent session
  (`CheckGroupsInWarmSession`, which leases, runs `CheckTransitiveGroupMembership` over the session's pipeline, and marks the
  session failed on a throw or an incomplete answer). The resolution and the mailbox proof move to the warm sessions in their
  own commits (the sweep, S1 and S2).

Cases (`ExchangeAdminWeb.Tests/WarmDirectorySessionTests.cs`, over the harness's `ProtectedValidator`, which now takes the
directory search service): two checks borrow one session from the directory search service - one runspace handed out, one
module import, `CheckSessions.Opened` 1; a session a read failed in is not lent again (two); six checks at once leave at most
the two sessions the service lets run together, each warm; a full pool refuses after its wait and never lends one session
twice.

### 4. The timing line

- **`DirectoryReadOperation.BeginCheck(logger, check, target)`**: a timed check - inside the current operation, or as an
  operation of its own - that logs one Information line when it ends: `"{Check} for {Target} took {ElapsedMs} ms ({Reads}
  directory reads, {Fetches} credential fetches)"`, which renders as the brief's "Protected-principal check for <target>
  took <n> ms (<r> directory reads, <f> credential fetches)". `Reads` counts the directory cmdlets the check ran
  (`CountRead`, at every read site: the evaluator's runspace reads and the catalog's discovery, the resolution, the mailbox
  proof, the group check's sAMAccountName fallback, the self-grant check's searches), `Fetches` the credential fetches it
  started - 0 when another check of the same operation had already fetched. A check begun inside one of the same name is part
  of it and logs nothing of its own, so a target validation that reaches the service's own check logs once.
- **Where**: `ProtectedPrincipalService.CheckAsync` (a check begun outside any other is timed on its own);
  `ProtectedPrincipalService.BeginCheck(target)` (new, public: what a caller begins around its resolution and its check -
  the sweep); `PermissionValidator.ValidateTargetMailboxAsync` (the target's whole validation - resolution, checks, the
  mailbox it binds - one line); `PermissionValidator.ValidateSelfGrantAsync` ("Self-grant check for <grantee>").

Cases: `ExchangeAdminWeb.Tests/ProtectionCheckTimingTests.cs` - over the real validator and service and the stand-in forest,
each line matched whole (`^... took \d+ ms \(<r> directory reads, <f> credential fetches\)$`) and exactly once: the
protected-principal check alone (3 reads - the target, its token, the protected group's own read - and 1 fetch); a target
validation (one line, the service's own check inside it part of it: 5 reads - the resolution's lookup and the mailbox proof
besides - and 1 fetch); a change's self-grant check (its own line: 3 reads - the catalog's discovery, the operator by SID,
the grantee - and 0 fetches, the change's one being the target check's); a check begun around a resolution (one line, 5
reads, 1 fetch). `DirectoryReadOperationTests` +2: a check counts what ran while it was open, its nested checks included, a
nested check of the same name logs nothing and one of another name logs its own; reads outside any check count nowhere.

### What a grant costs now

A Mailbox Permissions grant to a synced mailbox with protected groups configured (security groups given by DN, one
domain), on a warm session: **one credential fetch** for the change, and **eight directory reads** - the target check's
five (the resolution's lookup, the mailbox proof, the target read, its token, the protected group's own read; one more per
further protected group) and the self-grant check's three (the catalog's discovery, the operator by SID, the grantee).
At `280ff007` the same grant fetched the credential four times (three on the dev log before it timed out), opened four
cold sessions with a module import each, and sent the domain-wide and forest-wide walks.

Estimate, not measured (no live directory was reached): on a warm session a directory read through the AD web services is
tens of milliseconds, so the eight reads are well under a second; the fetch is the floor - 2.7 to 4.1 s on the dev log -
and Exchange Online's lookups come on top. The record's target of under two seconds end to end is therefore not reachable
while the secret store answers in that time (below). The owner's redeploy and one grant give the figure: the log's
"Protected-principal check for <target> took <n> ms (...)" and "Self-grant check for <grantee> took <n> ms (...)" lines.

### Still able to take seconds in the write path (named, not fixed)

1. **The directory-read secret fetch** - 2.7-4.1 s each on the dev log (`DelineaService.GetCredentialsBySecretIdAsync`, one
   HTTP call; the store keeps no cache). Now once per operation. Keeping it between operations - a short-lived in-memory
   credential - would take it off nearly every grant; that is a change to how a credential is held and is the owner's to
   decide (Constitution, Planning Rules: credential changes). 2026-10-30: now kept five minutes after its last use, the
   supervisor's call, which the owner may veto (the Addition section at the end).
2. **Exchange Online lookups**: the target's `Get-Recipient` (`AskExchangeAsync`), the self-grant check's two recipient
   lookups, the excluded-user list's and the bind's - each a pool round trip, seconds on a cold connection.
3. **The on-premises write**: its own module credential fetch (`ModuleCredentialService`, another secret, not shared) and the
   on-premises Exchange session.
4. **Module writes** that build a runspace and import the module per write (Group Management, Emergency Disable, AD
   Attribute Editor, Self-Service Groups, Conference Rooms, Licensing, Migration): writes, not checks - outside this sweep.
5. **The access re-check** (`OperatorMembershipDirectory`): a fresh runspace and module import per lookup, on a page load
   past the interval - outside the write path.
6. **A domain controller that does not answer**: a read still waits for the AD web services' own timeout (two minutes) and
   then refuses; no read here can now be the slow walk itself.

## Known gaps

- **Not run against a live directory, by instruction.** What this rests on: `tokenGroups` read base-scope at an account's DN
  bound by its SID (kd-87's read, which loads pages on dev under the app pool's identity - here under the directory-read
  credential; were the attribute withheld from that account it comes back absent and every account check refuses as "does
  not carry its primary group", loud, not open); a global catalog's `memberOf` carrying universal groups' links; the AD
  module's `GroupCategory` (unreadable reads as distribution: more reads, never fewer); a warm runspace reused across checks.
  The first live run is the owner's redeploy of dev.
- **A distribution group nested inside a protected SECURITY group.** A token carries a security group only through security
  groups: Windows does not expand membership through a distribution group. So a target that is in a protected security group
  only by way of a distribution group nested in it is not in the token, and the token's answer for a security group is taken
  as the answer (`TokenAnswers`). The 2026-10-21 version's walk and the version before it followed member links and counted
  such a target; this one does not. The record's approach takes the token for security groups; the owner's question is
  whether protection follows distribution-group nesting. If it should, reading the links for every account check (two reads
  a level of nesting, typically four to ten, still sub-second warm) closes it - one condition in `TokenAnswers`. Not pinned by
  a test, because a test would pin the gap.
- **Distribution groups and domain-local groups of another domain are answered from the links**, read at the target's
  domain and the global catalog: a chain that passes through a group whose links neither holds - a global group of a third
  domain cannot hold the target, so only a domain-local group, which the anchored question asks in its own domain - is the
  only shape left, and it is the one the question exists for.
- **The global catalog's scope**: the ancestry read and the forest-wide entry lookups send `-Server <gc>:3268` with no
  `-SearchBase`, the idiom `ADDirectorySearchService` measured to cover every domain (aud-a2j). An object the ancestry read asks
  for and does not get back fails the check closed, so a narrower answer refuses rather than passes.
- **Warm sessions live as long as the app**: at most four shared runspaces with the AD module loaded (plus a test seam's).
- **The bulk job runner fetches per row** (Conference Rooms jobs): each row is processed by its own call and may resume after
  a restart; joining a job's rows into one operation would hold the credential for the job's life.
- **Flaky test, unrelated**: `MessageTraceSubmittedValueTests.ASecondDownloadWhileADownloadRuns_IsIgnored_NotRunBesideIt`
  failed once in a full run after item 3 and passed alone three times and in every other full run; it touches none of this.

- five minutes after its last use, sliding (`DefaultCredentialWindow`); a fetch inside the window is answered from memory,
  makes no request to the store, and slides the window on;
- process memory only: the password as a read-only `SecureString` inside a `PSCredential`, the domain beside it; never
  written to disk or to any log - the reuse is traced (`VaultCredentialReused`) and logged at Debug ("Using kept Delinea

- invalidated on a fetch error: a fetch that fails - an HTTP status, a secret missing a field, an exception, no bootstrap

  is never handed out for a fetch that failed;
- a changed Secret ID is another entry and is fetched; the old ID's entry is not asked for again and lapses five minutes
  after its last use;
- `GetSecretFieldsAsync` (Graph app secrets) is unchanged; so is the access-token cache.

`DirectoryReadOperation`'s per-operation sharing is unchanged and sits on top: inside one operation the first check asks
`GetCredentialsBySecretIdAsync`, which is now usually answered from memory.

**Known gaps, for the owner.**
- **A rotated password.** A credential in steady use is kept until five minutes pass with no use of that Secret ID. If the
  secret store changes the account's password (a scheduled rotation, a manual change), the app goes on using the old one
  until then: every directory read and on-premises session under it fails, the checks refuse (fail closed, loud), and the
  first fetch after a five-minute lull picks up the new password. Invalidation on a fetch error does not cover it: no fetch
  happens while the credential is in use. An absolute cap, or dropping the entry when a read under it fails to bind, would;
  neither was asked for.
- **The timing line** ("... took <n> ms (<r> directory reads, <f> credential fetches)") counts a fetch the operation asked
  for, whether the store or the window answered it; the trace's `VaultCredentialReused` step tells the two apart.
- The first fetch after the app starts, and after every five-minute lull, still costs the store's 2.7-4.1 s.
