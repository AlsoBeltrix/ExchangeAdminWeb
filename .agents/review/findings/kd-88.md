# kd-88: the protected-group check takes minutes and refuses; the owner's requirement is near-instant

**Severity**: HIGH - on the deployed dev build (2026-10-30 08:23) a Mailbox Permissions grant waited two minutes and was refused:
`Protected-group check could not read target ... or its groups in ad.analog.com - failing closed`, inner
`System.TimeoutException: ... net.tcp://<dc>:9389/ActiveDirectoryWebServices/Windows/Enumeration did not receive a reply within
the configured timeout (00:02:00)`, then "Group expansion had errors and no matches found - failing closed" and "Blocking
operation ... protected-principal check failed". The same log shows the directory-read credential fetched from Secret Server
three times for the one grant (08:23:02 4.1 s, 08:23:06 2.7 s, 08:23:09 2.7 s).
**Owner requirement, 2026-10-30, verbatim:** "this cannot take 2 minutes. this cannot take 10 seconds. this has to be
near-instant."
**Cause**: `Services/ProtectedGroupMembership.cs` (aud-a3b/a3c/a4b, 2026-10-21, never run live before) collects the groups the
target's own domain links it into with `ContainsAnyFilter`, an UNANCHORED domain-wide in-chain search
(`member:1.2.840.113556.1.4.1941:=<dn>` over every group). Before 2026-10-21 the check asked one ANCHORED question per
configured protected group (`(&(distinguishedName=<group>)(member:1.4.1941:=<target>))`), which ran live for months. The
2026-10-21 fix closed three real fail-open holes (a domain-local protected group in another domain; the primary group; the
DOMAIN\Name resolver) and must stay closed.
**Status**: In progress on branch - items 1 and 2 landed; items 3 and 4 and the sweep follow
**Branch**: `fix/kd88` (worktree `D:\source\ExchangeAdminWeb-wt\kd88`, from master `280ff007`)
**Commit**: item 1 `3d9d987c`; item 2 - the commit that adds its section below

## Approach

1. **Seed set from `tokenGroups`, not a domain-wide walk.** Read the target's `tokenGroups` with a base-scope search at its
   DN (the kd-87 shape: `Get-ADUser -SearchBase <dn> -SearchScope Base -LDAPFilter (objectSid=<sid>) -Properties
   tokenGroups`) against the target's own domain, under the directory-read credential. It is the directory's precomputed
   transitive list of every security group the account is in, primary group included. Compare its SIDs with the resolved
   protected groups' SIDs. For a protected group that is a domain-local group of ANOTHER domain (hole 1), ask that domain
   the anchored question with the tokenGroups SIDs/DNs as seeds, as the evaluator does today - never unanchored. For a
   protected group that is a distribution group (absent from tokenGroups), ask the anchored question only. No unanchored
   in-chain query may remain anywhere; a tripwire test asserts it.
2. **One credential fetch per operation.** The directory-read credential is fetched once for a single change and once for a
   bulk file (aud-a70's own rule for the file), and handed to every check in that operation.
3. **A warm directory session.** The reads reuse the pooled/cached runspace the directory search service already keeps
   (`GetOrCreateRunspace`); no fresh AD-module import per check.
4. **Timing in the log.** One INF line per check: "Protected-principal check for {target} took {ms} ms ({reads} directory
   reads, {fetches} credential fetches)" so the owner can read the duration on dev. Target: under two seconds end to end on
   a warm session; the record states the measured figure after the owner's redeploy.
- Fail-closed rules unchanged: an unreadable tokenGroups, an unresolvable configured group, any error is a refusal; audit
  shape unchanged. Tests: the stand-in directory records every query and credential fetch; assert exactly one fetch, the
  base-scope tokenGroups read, no unanchored in-chain filter, the anchored query only for cross-domain domain-local and
  distribution protected groups, every hole case from aud-a3b still refused/detected. Mutations: the unanchored query
  restored; a second credential fetch introduced; the primary group dropped from the seeds. Shared service: base bump already
  owed. Then the owner redeploys dev and grants once; the log line gives the duration.

### 1. The groups an account is in are its token; nothing searches for whatever contains the target

At `280ff007`, `ProtectedGroupMembership.Evaluate` found the target's groups with `GroupsContainingAny` - one
`Get-ADGroup -LDAPFilter (|(member:1.2.840.113556.1.4.1941:=<target>)(member:...:=<primary group>))` over the target's
whole domain, every group of it whose member chain reaches the target - then `UniversalGroupsContainingAny`, the same over
every universal group of the forest at a global catalog. The first is the read the dev log shows timing out at the domain
controller (two minutes); the second is the same shape forest-wide. Both are gone from the seam and the code.

- **An account** (`RequiresPrimaryGroup`: a SID and not a group): after the target read (unchanged), one more read -
  `IProtectedGroupDirectory.ReadTokenGroups`, in `PowerShellProtectedGroupDirectory` a `Get-ADObject -SearchBase <its DN>
  -SearchScope Base -LDAPFilter (objectSid=<its SID>) -Properties tokenGroups -Server <its domain>` under the
  directory-read credential: kd-87's shape, which loads pages on the dev build since kd-87 merged. Its SIDs are read with
  the access re-check's parser (`OperatorMembershipDirectory.ParseSids`). The token a domain controller of the account's
  own domain computes carries its own domain's global and domain-local groups, every universal group of the forest (the DC
  expands them through a global catalog - aud-a3c) and the primary group (hole 2). **A token that does not carry the
  primary group fails closed** ("does not carry its primary group"): the attribute withheld from the reader comes back
  absent, and an empty token is not "in nothing". Each resolved protected group is compared with these SIDs.
- **What a token cannot carry is asked of the links, by name.** A protected group the token is not complete for - a
  distribution group, or a domain-local group of another domain (hole 1) - and, for a target with no token at all (a
  group, a contact), every protected group, is answered from the target's ancestry: `ReadMemberOf`, one
  `Get-ADObject -LDAPFilter (|(distinguishedName=<a>)(distinguishedName=<b>)...) -Properties objectSid,memberOf` per level
  (50 names a read), at a DC of the target's domain for that domain's objects and at the global catalog for all of them,
  starting from the target and, for an account, its primary group. A read of named objects, never a search for whatever
  contains them. Every object asked for must come back - each is the target or a group a link named - or the answer is
  incomplete; so is a nesting past 64 levels or 10,000 groups. A domain-local protected group not found there gets the one
  anchored question left, `DomainLocalGroupContainsAny` (`(&(distinguishedName=<group>)(|(member:...:=<seed>)...))`, asked
  of the group's own domain) with every DN the ancestry reached - the evaluator's hole-1 question as before, now seeded
  with distribution groups too.
- **A security group the token does not carry is not a member** (`TokenAnswers`): its own domain's global and
  domain-local groups and every universal group are in the token when the account is in them, and a global group of
  another domain cannot hold it. No link is read for the common case.
- `DirectoryGroup` carries `Security` (the module's `GroupCategory`; `GroupProperties` asks for it). A category that
  cannot be read counts as not security, so it takes the path that reads the links - more reads, never fewer.
- Seam (`IProtectedGroupDirectory`): `ReadTarget`, `ReadTokenGroups`, `ReadMemberOf`, `ResolveDomainServer`, `FindGroups`,
  `FindObjectDnsBySid`, `DomainLocalGroupContainsAny`. `ContainsAnyFilter` and `UniversalContainsAnyFilter` are gone; the
  in-chain rule is written only inside `GroupContainsAnyFilter`, anchored on the group's DN. The three callers of the
  evaluator - the protected-principal check, the self-grant check (aud-a52/a60) and the self-service resource-domain Deny
  check (aud-a4b finding 7) - all take it.
- **Reads a grant now costs** (single-domain configuration of security groups given by DN, the usual one): the target
  read, the token read and one read per configured group - three for one protected group, against the 2026-10-21
  version's target read, primary-group lookup, the domain-wide walk, the forest-wide walk and the entry reads. A
  distribution group, a domain-local group of another domain or a group target adds two reads per level of nesting and,
  for a domain-local group, its one anchored question.

Cases (`ExchangeAdminWeb.Tests/ProtectedGroupMembershipTests.cs`, `FakeForest.cs`): the fake forest computes a token as a
domain controller of the account's domain does - security groups only, through the links that DC holds and the ones its

### 2. One credential fetch per operation

At `280ff007` the protected-principal directory-read secret was fetched by each read that needed it:
`ResolveWithStatusAsync` (once per resolution, twice when the canonical address is re-read), `FindMailboxGuidHoldersAsync`
(the mailbox proof) and `CheckGroupMembershipAsync` (the group check) each called
`DelineaService.GetCredentialsBySecretIdAsync` - the three fetches of the dev log, 4.1 s, 2.7 s, 2.7 s - and the self-grant
check fetched it again (`PermissionValidator.DirectoryReadCredentialAsync`, once per run since aud-a61). A bulk file paid the
first three per row.

- **`Services/DirectoryReadOperation.cs` (new).** One operation's directory-read secret, carried by the async flow
  (`AsyncLocal`), so no virtual method of the protected-principal service changes shape. `Begin()` begins an operation or
  joins the one the flow is in; only the outermost dispose ends it. `DirectoryReadSecretAsync(secretId, fetch)` runs the
  fetch once per operation and Secret ID and hands every later caller its answer - the secret, or its failure: a fetch that
  failed is that failure for the rest of the operation and is not repeated in it (aud-a61's rule). Outside an operation it
  fetches as before. Nothing outlives the operation: the next change fetches afresh.
- **`ProtectedPrincipalService`**: the three fetches go through `DirectoryReadSecretAsync` (a fetch that throws reads as not
  retrieved, as the store's own failures already did). `ResolveExchangeTargetAsync` and `ResolveWithExchangeFallbackAsync`
  begin an operation, so their lookups share one fetch even for a caller that began none. Test seams:
  `DirectoryReadSecretFetch` (null in production: the store, as before) and `DirectoryRunspace` (the session the three read
  sites open, unchanged in production; still one per read until item 3).
- **`PermissionValidator`**: `DirectoryReadCredentialAsync` fetches through the operation, so the self-grant check shares the
  protected-principal check's fetch; `ValidateTargetMailboxAsync` begins an operation over its resolution, its check and the
  check of the typed string.
- **The single change**: `Components/Pages/MailboxPermissions.razor` 405 and 704, `Components/Pages/CalendarPermissions.razor`
  383 and 658 - `SubmitSingle` and `ExecuteOnPrem` begin one operation on the line that reads the operator's principal, ahead
  of the target check and the self-grant check. In place: the pages keep 828 and 782 lines, so no ClickGateRegistry or
  ProgressRegistry entry moves. The on-premises re-check after the operator confirms is its own operation - a new pause, a
  fresh fetch, as the Constitution's re-check before the write wants.
- **A bulk file**: `MailboxPermissionService` and `CalendarPermissionService` begin one operation beside the file's
  `SelfGrantRun`: every row's target check and self-grant check share one fetch.

Cases: `ExchangeAdminWeb.Tests/DirectoryReadOperationTests.cs` (8: outside an operation every check fetches; inside, once,
across `Task.Run` too; another Secret ID is its own fetch; a fetch that answered nothing or threw is kept as that failure and
not repeated; a nested operation joins and only the outermost ends it; nothing is kept between operations; two operations at
