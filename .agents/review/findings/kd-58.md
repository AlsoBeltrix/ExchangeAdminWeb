# kd-58: the Exchange Online reads take no cancellation token at all

**Severity**: LOW, scope. `RunPooledQueryAsync` and the Exchange Online pool take no `CancellationToken`, so a cancel
during the cloud half of any module's work is noticed only at the next hop that has one. kd-37 threaded the token from
the Recipient Lookup page to the vault; the cloud read in the middle still cannot be cancelled.
**Status**: In progress under `docs/CancellationDepth-Plan.md` (approved 2026-10-28): the shared slices A1-A3 - the pool and
the Exchange base, Recipient Lookup their first user - fixed on branch, verified, each closing on its guard proof (the
single review is spent); the module slices A6-A10 and C1 follow. Sized 2026-10-27 as needing a written plan under the
Constitution ("Exchange service or shared infrastructure refactors"); that plan is the one above.

### Sizing (implementer, 2026-10-27; lines at master `69f11c23`)

**Verdict: not a local pass-through. A token threaded through `RunPooledQueryAsync` has to enter the pool's retry entry
point and its borrow, and to reach the cloud read itself it has to stop a borrowed pipeline, whose fate - back into the
pool or discarded - is the pool's lifetime decision. A written plan is needed; no code was written.** Read, not run.

1. **The base hands the pool a delegate and no token.** `Services/ExchangeServiceBase.cs` 113-115:
   `protected Task<T> RunPooledQueryAsync<T>(Func<PowerShell, ConnectionErrorTracker, T> query, bool allowRetry = false)`
   / `return _exoPool.RunWithRetryAsync(pooled => Task.Run(() =>`, closed at 134 by
   `}), allowRetry, PoolFailurePolicy.Return);`. `RunAsync` (49-51, closed at 106) has the same shape. There is nothing
   in the base to pass a token to except the pool's own method.
2. **The pool's entry point is its retry loop.** `Services/ExoConnectionPool.cs` 451-456:
   `internal Task<T> RunWithRetryAsync<T>(Func<PooledRunspace, Task<PooledOutcome<T>>> run, bool allowRetry, PoolFailurePolicy nonConnectionFailurePolicy)`
   `=> RunWithRetryCoreAsync(() => BorrowAsync(), Return, Discard, run, ...)`. A token reaches the borrow only through a
   new parameter on this method, and inside `RunWithRetryCoreAsync` the borrow is a step of every attempt of the retry
   loop: 505-507 `attempt++; var canRetry = allowRetry && attempt < 2; var pooled = await borrow();`. That is the retry
   handling, changed for every pooled query in the app.
3. **The borrow is the pool's lifetime.** `BorrowAsync(TimeSpan waitTimeout, CancellationToken ct = default)` (262)
   already takes a token, and it reaches the slot wait (294 `if (!await _slots.WaitAsync(waitTimeout, ct))`) and the
   connect (359 `var connected = await Task.Run(() => _connect(current, currentGen, ct), ct);`, then 784
   `if (!_connectGate.Wait(ConnectGateTimeout, cancellationToken))` inside `CreateConnected`), while the destroy of a
   stale runspace is deliberately given none (337-341, aud-a6d: "no token here. This runspace has already left the pool,
   so destroying it is cleanup this borrow owes"). **No production caller passes it one**: `RunWithRetryAsync` passes
   none (455) and the only other caller, `Components/Shared/RecipientAutocomplete.razor` 113, passes a five-second wait
   only (`await ExoPool.BorrowAsync(TimeSpan.FromSeconds(5))`). Every cancelled-borrow path - a slot wait given up, a
   connect abandoned at the gate, the slot released by the catch at 374-379 - has never run in production, and threading
   a token puts every pooled caller on them.
4. **Even then the cloud read itself would not stop.** The read is the synchronous cmdlet inside the delegate: 120
   `var result = query(pooled.PowerShell, tracker);` - for example `Services/MessageTraceService.cs` 155-160, ending
   `var events = Invoke(ps, tracker);`. The delegate type has no token, and a token handed to `Task.Run` is looked at
   only before the delegate starts. Stopping a running read means stopping the borrowed pipeline (`PowerShell.Stop`),
   which throws `PipelineStoppedException` - "The pipeline has been stopped." (its message, read on this host's
   PowerShell 7.6.9). The retry core sorts a throw by its words: 514 `catch (Exception ex) when (isConnectionError(ex))`,
   and `IsConnectionError` (463-468) looks for "connection", "session", "runspace" and "Connect-ExchangeOnline", none of
   which that message carries - so a stopped read falls to 523-529 and, under the `PoolFailurePolicy.Return` both base
   helpers pass, the stopped session goes back into the pool (`else ret(pooled);`). Whether a session stopped in the
   middle of a cmdlet may be lent again is exactly the pool-lifetime question this row was told to stop at.
5. **And a stopped write is a third question.** `RunAsync` with `allowRetry: true` carries single writes (Set-Place,
   Remove-BlockedSenderAddress); a write stopped after it was sent may have applied - the aud-a73 / aud-a76 / kd-6 rule
   for an unknown outcome. kd-6 chose not to stop the call for exactly this: `Services/BlockedSenderService.cs` 67-68,
   "Stopping the wait does not stop the call: the pooled pipeline runs on, and the pool returns or discards its
   connection when it ends", and bounds only its own wait (104, `return await run.WaitAsync(UnblockBound, cancellationToken);`).

**What a plan would have to settle** (for the owner's plan, not decided here): whether a cancel reaches only the queue in
front of the read (the slot wait and the connect, point 3) or the read itself (point 4); what becomes of a stopped
session (returned or discarded) and how the retry loop reads a stopped pipeline; what a stopped single write is filed
as; and whether the base should instead stop only its own wait, as kd-6 does - which leaves the pooled call running and
its slot held until it ends, so an operator who cancels and searches again queues behind their own abandoned read.

Consequence for the neighbouring rows: kd-59 and kd-70 do not need this. kd-59 passes the token to the on-premises
credential fetch, which is not pooled; kd-70 stops Message Trace's detail download between messages, at the page, so a
cancel waits at most for the one cloud read in flight.

## As implemented - A1, the pool (implementer, 2026-10-28; lines at this commit)

Read first, confirmed at `401ec828` (master after the Recipient Lookup accuracy merge): the plan's 3.1 still held for the
pool. `RunWithRetryAsync` borrowed with `() => BorrowAsync()`, no token; the retry core's borrow was each attempt's first
step; `BorrowAsync`'s slot wait and connect gate already honoured a token no production caller gave; `Return` pooled any
connection of the current generation without looking at its pipeline. Nothing in `Services/ExoConnectionPool.cs` stopped a
pipeline.

- **E1, the borrow** (`RunWithRetryAsync`, 526): an optional last `CancellationToken`, handed to `BorrowAsync` and to the core.
  The slot wait (up to two minutes) and the connect gate (up to ninety seconds) end at once on a cancel. A connect already past
  the gate runs to its end and its connection is pooled (E2). The destroy of a stale connection keeps no token (aud-a6d).
- **E2, before the delegate** (the core, 590-601): the token looked at before every attempt's borrow - so a retry never
  borrows after a cancel - and again as the borrow returns, when the unused connection goes back through `ret` and the
  cancellation is thrown.
- **3.5, a cancel is not a failure** (616-627): a cancellation of the caller's token thrown by the delegate is caught ahead of
  the connection-error filter, given back under the caller's policy (Return for the base helpers, Discard for a caller that
  cannot vouch for its pipeline) and rethrown unchanged; never retried. "The caller's token" is `IsCancellationOf` (434, E8):
  that token cancelled and the one the throw names, so a cmdlet's own timeout - another token, or none - is sorted by its
  words as before, whether or not the caller has cancelled.
- **E6, a stopped pipeline is never lent again**: `PooledRunspace.WasStopped` (55) reads the pipeline's own state - Stopping or
  Stopped now, or a stop it reported at any point since it was made (an `InvocationStateChanged` latch, 46-52), so a delegate
  that runs another command after a stop, leaving the state Completed, still cannot launder it. `Return` (444-450) destroys
  such a connection ahead of its generation test, releases its slot and traces `ExoConnectionDiscardedStopped`. The core
  routes a stopped pipeline to `ret` whatever the delegate threw (609-614) or returned (645-652), and never retries it -
  without that routing, a stop the delegate reported as a dead session would have been discarded and run again.
- **Traces (3.6)**: a cancelled slot wait is `ExoPoolSlotRequested` / `Cancelled` (328; no slot was taken), a cancel after the
  slot `ExoConnectionBorrowed` / `Cancelled` (417; the slot given back), a cancel at the gate `ExoConnectionCreated` / `Cancelled`
  (958-959). None is logged, at Error or any level. No new counter, timer or probe; `FreeSlots` (202) is a test seam.
- **E5**: nothing here or anywhere in `Services/` or `Components/` stops an Exchange pipeline; a tripwire holds it.
- Tests changed to follow the code: the two pool-trace helpers that count a borrow still waiting
  (`ConferenceRoomCancellationTests` 462, `PermissionCloudChangeCancellationTests` 618, 624) count a `Cancelled` slot step as a
  wait that ended, as they count `Failed`.
- README, Architecture: the pool's bullet says what a cancel does to a call and that no command already sent is stopped.

Every caller passes no token until A2, so nothing an operator sees changes in this slice: with no token only E6 can change
anything, and only for a pipeline something stopped - nothing in the app does.

**Assumptions 2 and 3, settled by a probe on this host's PowerShell 7.6 SDK** (a throwaway test, not committed): a synchronous
`Invoke` stopped from another thread (`BeginStop`) throws nothing - it returns no rows, `HadErrors` set and no error record
written, and the state reads `Stopped`, its reason a `PipelineStoppedException`; the events were Running, Stopping (raised on
the stopping thread, at once) and Stopped; the same PowerShell can be invoked again afterwards, ending `Completed`. And
`BeginStop` queues the stop, so a pipeline blocked in a .NET call stops at a later statement, not necessarily the next one:
the test's stand-in read waits, bounded, at statements a stop can land at. So a stop reaches a delegate as the base's helpers
present an error flagged and none written - `Invoke` throws "The command flagged an error but surfaced none ...", `RunAsync`
makes that a failed result, `ReadUnlessNotFound` reads it as no such object - and only the pipeline's state tells it was a
stop. That is why E6 reads the state, never the delegate.

**Found, not fixed (outside kd-58)**: the plan's "nothing in the app stops a pipeline" holds for Exchange pipelines.
`Services/PowerShellDirectoryCommands.cs` 117 stops its own Active Directory read (`StopAsync`) when its caller gives up - the
operator-membership and AD-site directory reads, run under the app's own identity in a runspace of their own per call that is
disposed after it. Not an Exchange connection, not pooled, and the operator's navigation cancel reaches neither caller today.
The tripwire names it as its one exemption, with that reason, and checks it holds no Exchange connection.
