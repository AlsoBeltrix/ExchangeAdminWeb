# kd-58: the Exchange Online reads take no cancellation token at all

**Severity**: LOW, scope. `RunPooledQueryAsync` and the Exchange Online pool take no `CancellationToken`, so a cancel
during the cloud half of any module's work is noticed only at the next hop that has one. kd-37 threaded the token from
the Recipient Lookup page to the vault; the cloud read in the middle still cannot be cancelled.
**Status**: Open - sized 2026-10-27, no code: threading a token through reaches the Exchange Online pool's lifetime and
its retry handling, so it needs a written plan under the Constitution ("Exchange service or shared infrastructure
refactors"). Stopped here; the plan is not written.

**Commit**: the commit that carries "Sizing" below (`git log -1 -- .agents/review/findings/kd-58.md`)

### Sizing (implementer, 2026-10-27; lines at master `69f11c23`)

**Verdict: not a local pass-through. A token threaded through `RunPooledQueryAsync` has to enter the pool's retry entry
point and its borrow, and to reach the cloud read itself it has to stop a borrowed pipeline, whose fate - back into the
pool or discarded - is the pool's lifetime decision. A written plan is needed; no code was written.** Read, not run.

1. **The base hands the pool a delegate and no token.** `Services/ExchangeServiceBase.cs` 113-115:
   `protected Task<T> RunPooledQueryAsync<T>(Func<PowerShell, ConnectionErrorTracker, T> query, bool allowRetry = false)`
   / `return _exoPool.RunWithRetryAsync(pooled => Task.Run(() =>`, closed at 134 by
   `}), allowRetry, PoolFailurePolicy.Return);`. `RunAsync` (49-51, closed at 106) has the same shape. There is nothing
   in the base to pass a token to except the pool's own method.
2. **The pool's entry point is its retry loop.** `Services/ExoConnectionPool.cs` 451-456:
   `internal Task<T> RunWithRetryAsync<T>(Func<PooledRunspace, Task<PooledOutcome<T>>> run, bool allowRetry, PoolFailurePolicy nonConnectionFailurePolicy)`
   `=> RunWithRetryCoreAsync(() => BorrowAsync(), Return, Discard, run, ...)`. A token reaches the borrow only through a
   new parameter on this method, and inside `RunWithRetryCoreAsync` the borrow is a step of every attempt of the retry
   loop: 505-507 `attempt++; var canRetry = allowRetry && attempt < 2; var pooled = await borrow();`. That is the retry
   handling, changed for every pooled query in the app.
3. **The borrow is the pool's lifetime.** `BorrowAsync(TimeSpan waitTimeout, CancellationToken ct = default)` (262)
   already takes a token, and it reaches the slot wait (294 `if (!await _slots.WaitAsync(waitTimeout, ct))`) and the
   connect (359 `var connected = await Task.Run(() => _connect(current, currentGen, ct), ct);`, then 784
   `if (!_connectGate.Wait(ConnectGateTimeout, cancellationToken))` inside `CreateConnected`), while the destroy of a
   stale runspace is deliberately given none (337-341, aud-a6d: "no token here. This runspace has already left the pool,
   so destroying it is cleanup this borrow owes"). **No production caller passes it one**: `RunWithRetryAsync` passes
   none (455) and the only other caller, `Components/Shared/RecipientAutocomplete.razor` 113, passes a five-second wait
   only (`await ExoPool.BorrowAsync(TimeSpan.FromSeconds(5))`). Every cancelled-borrow path - a slot wait given up, a
   connect abandoned at the gate, the slot released by the catch at 374-379 - has never run in production, and threading
   a token puts every pooled caller on them.
4. **Even then the cloud read itself would not stop.** The read is the synchronous cmdlet inside the delegate: 120
   `var result = query(pooled.PowerShell, tracker);` - for example `Services/MessageTraceService.cs` 155-160, ending
   `var events = Invoke(ps, tracker);`. The delegate type has no token, and a token handed to `Task.Run` is looked at
   only before the delegate starts. Stopping a running read means stopping the borrowed pipeline (`PowerShell.Stop`),
   which throws `PipelineStoppedException` - "The pipeline has been stopped." (its message, read on this host's
   PowerShell 7.6.9). The retry core sorts a throw by its words: 514 `catch (Exception ex) when (isConnectionError(ex))`,
   and `IsConnectionError` (463-468) looks for "connection", "session", "runspace" and "Connect-ExchangeOnline", none of
   which that message carries - so a stopped read falls to 523-529 and, under the `PoolFailurePolicy.Return` both base
   helpers pass, the stopped session goes back into the pool (`else ret(pooled);`). Whether a session stopped in the
   middle of a cmdlet may be lent again is exactly the pool-lifetime question this row was told to stop at.
5. **And a stopped write is a third question.** `RunAsync` with `allowRetry: true` carries single writes (Set-Place,
   Remove-BlockedSenderAddress); a write stopped after it was sent may have applied - the aud-a73 / aud-a76 / kd-6 rule
   for an unknown outcome. kd-6 chose not to stop the call for exactly this: `Services/BlockedSenderService.cs` 67-68,
   "Stopping the wait does not stop the call: the pooled pipeline runs on, and the pool returns or discards its
   connection when it ends", and bounds only its own wait (104, `return await run.WaitAsync(UnblockBound, cancellationToken);`).

**What a plan would have to settle** (for the owner's plan, not decided here): whether a cancel reaches only the queue in
front of the read (the slot wait and the connect, point 3) or the read itself (point 4); what becomes of a stopped
session (returned or discarded) and how the retry loop reads a stopped pipeline; what a stopped single write is filed
as; and whether the base should instead stop only its own wait, as kd-6 does - which leaves the pooled call running and
its slot held until it ends, so an operator who cancels and searches again queues behind their own abandoned read.

Consequence for the neighbouring rows: kd-59 and kd-70 do not need this. kd-59 passes the token to the on-premises
credential fetch, which is not pooled; kd-70 stops Message Trace's detail download between messages, at the page, so a
cancel waits at most for the one cloud read in flight.
