### Verification

True. `TicketPresence.IsPresent` (`Services/TicketPresence.cs:34-35`) is `!IsNullOrWhiteSpace && !Any(char.IsControl)`.
U+200B (zero-width space) and U+200E / U+200F (bidi marks) are Unicode format characters (category Cf): neither white
space nor control, so a ticket made only of them is "present", and a dormant ServiceNow passes it - the kd-24 class,
for characters that are invisible rather than control. A combining mark standing alone (for example U+0301) is the
same in effect: nothing visible, yet not white space.

### What changes

- `TicketPresence.IsPresent`, walked rune by rune: refused for an unpaired surrogate, a control character (kd-24) or a
  format character anywhere - a bidi mark reorders the text around it, so a ticket that merely displays as
  "INC0042" is not recorded as one; and present only with at least one visible rune - not white space, and not one
  that draws nothing alone (a combining mark, an unassigned or a private-use code point). Spaces inside a ticket stay
  allowed. The class remarks say so.
- Every gate already calls this rule (kd-24), so none changes; kd-45's sites will get it as they move over.
- Guard: `TicketPresenceTests` gains the invisible cases (U+200B, U+200E, U+200F, U+FEFF, U+202E, U+2066, a format
  character inside a real ticket, combining marks alone, unpaired surrogates, private use) and visible ones (accented
  letters, a combining mark after its base, a surrogate pair); `TicketValidationServiceTests` and the M365 Group
  Management page test gain U+200B, so the rule is seen through a service gate and a page gate too.
- Mutation: the format check removed.
- Versions: the rule is shared code, so this is part of the base bump the supervisor makes at close. Each module whose
  accepted tickets it narrows moves one minor step, from the value this branch has (the kd-50 precedent):
