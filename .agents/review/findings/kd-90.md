# kd-90: session revalidation can sign an operator out silently when it reads a disposed Windows identity

**Severity**: HIGH - sweep item 5, seen on dev 2026-10-30 09:45:36 (`app-20261030.log` 1886-1897): "[ERR] An error occurred
while revalidating authentication state", `ObjectDisposedException ... SafeAccessTokenHandle ... at WindowsIdentity.get_Name()
at MembershipRevalidatingAuthenticationStateProvider.Revoke`, then "User Unknown carries 0 group claim(s)" and every module
denied. `Authorization/MembershipRevalidatingAuthenticationStateProvider.cs` about 296 reads `user?.Identity?.Name` after
`TryRevoke` (about 293); the throw skips the warning (about 300) and the audit line (about 304); the framework signs the
circuit out. A reload fixes it. Tests cannot see it: test principals are never disposed.
**Status**: Fixed on branch, verified; closes on guard proof
**Branch**: `fix/sweep-a` (worktree `D:\source\ExchangeAdminWeb-wt\sweep-a`, from master `cfd011da`)
**Commit**: the commit that adds this line (its SHA in the implementer's hand-back) | **Reviewer**: implementer (candidate)

## Approach

- Capture the operator's SID and name as strings when the circuit starts and never read the WindowsIdentity again in the
  revalidator or the provider; the same in `CircuitMembershipRevalidator` (about 296). Test with a principal whose identity
  throws ObjectDisposedException on Name: the revocation is audited and warned, no exception escapes, no sign-out beyond the
  intended one. Mutation: the captured name replaced by the live read.

## The fix (implementer, 2026-10-30; branch `fix/sweep-a` from master `cfd011da`)

The dev log (read only, `D:\inetpub\ExchangeAdminWebDev\logs\app-20261030.log` 1886-1897) shows the path exactly: the
framework's revalidation loop called `ValidateAsync`, the verdict was a revocation, `Revoke` set it and then read
`user?.Identity?.Name`; `WindowsIdentity.get_Name` went to `GetTokenInformation` over a disposed `SafeAccessTokenHandle`
and threw `ObjectDisposedException`, which skipped the warning and the audit line and reached the loop, which logged "An
error occurred while revalidating authentication state" and signed the circuit out. A `WindowsIdentity` caches its name
and claims only once something reads them, and its token is disposed with the request (or SignalR connection) that carried
it, while the circuit holds the principal for its whole life; a principal nothing read while its token was alive cannot be
read afterwards at all. The check reads the same identity (`CircuitMembershipRevalidator` read the name again for the
directory lookup), so a disposed one also failed the check itself - and was then revoked, silently.

- **`Authorization/MembershipRevalidatingAuthenticationStateProvider.cs`**: a copy of each principal - every identity's
  claims (name, account SID, groups) as plain strings, its authentication type and claim types, nothing behind them - is
  taken the first time the circuit is handed it or reads it, and kept beside it (`ConditionalWeakTable`, so a principal no
  longer held goes with its copy). It is taken in `IHostEnvironmentAuthenticationStateProvider.SetAuthenticationState`,
  which the framework calls inside the request that carries the token, for the circuit's first principal and every
  reconnect's. From then on the revalidation path reads only the copy: `ValidateAsync` hands it to the check, the
  circuit-open check reads whether it is authenticated from it, and `Revoke` names the account from it (`AccountOf`, which
  never throws and returns "Unknown" when there is nothing to read). A principal that cannot be read even the first time
  is revoked as a lookup that failed - "The signed-in principal could not be read, so its access cannot be re-checked:
  ..." - and warned and audited like every other revocation. The revocation still comes first; the warning and the audit
  line now always follow it.
- **`Authorization/CircuitMembershipRevalidator.cs`**: the account name is read once at the start of the check, beside the
  SID, and passed to the directory lookup as a string - the line the record names (about 296) no longer reads the principal.
  The page-request path hands it the live request principal, during the request, as before.

Not changed: what is compared, when, and every verdict; the off-switch; the gate; the audit line's shape. No module version
(Authorization is shared): the base app version bump is already owed (2.36.0, not deployed, absorbs it).

## Known gaps

- Not run on a deployed instance. The dev log's check, after a working day on the redeployed build: `Select-String
  D:\inetpub\ExchangeAdminWebDev\logs\app-*.log -Pattern 'error occurred while revalidating','User Unknown denied'` finds
  nothing, and any revocation has its "Session for ... ended by access revalidation" line and its audit row.
- The copy is what the check compares for the circuit's life of that principal: a group the token gains or loses is read
  from the next principal the framework hands over (a reconnect), as it was: a token's groups are fixed when it is issued.
- Why the 09:45 verdict was a revocation at all is not in the log (the throw hid it). The likeliest reading is that the
  check's own read of the disposed identity failed (it read the same name, about 296) and was filed as a failed lookup;
  with the copy that read cannot fail.
