## Approach

### Verification

True. `ExecuteReset` (`Components/Pages/MfaReset.razor:282`) raises `isLoading`, clears `resetConfirmPending` and then
`await Task.Yield()` (`:286`) - a real yield back to the message loop. Everything it acts on is read AFTER that:
`listedUpn` (`:291`), `ticketNumber.Trim()` (`:301`) and `methods` (`:302`, and again at `:321` for the activity's
size). The ticket box binds on `oninput` (`:107`) and carries `disabled="@isLoading"`, but the browser's copy of that
attribute is one round trip stale, so a keystroke landing in the yield window changes the ticket this handler
validates, writes into every audit row and sends in the administrator email - a different ticket from the one on
screen when Reset was clicked. This is the Item 24 / aud-a7b capture rule, which the other pages in this stream
already follow.

`listedUpn` and `methods` are the same shape and are captured with it: `ListMethods` replaces both, and its button
ungates on `isLoading`, which drops in this handler's own `finally`. The A13 guard that chose `listedUpn` over the
editable box stays exactly as it is - this moves when it is read, not what.

### What changes

- The three reads move above the raise and the yield, at the top of the handler: `upn`, `ticket`, `methodsAtClick`
  and the `methodTypesBeforeReset` array built from that one snapshot. The activity's size reads `methodsAtClick`
  too, so the bar, the audit row and the reset all describe one reviewed account. Nothing else moves: the
  nothing-listed guard, every refusal and the whole protected-principal preamble keep their order and wording.
- The page is not ClickGate-converted, so no line keys; `ProgressRegistry` keys by method and the covered calls are
  untouched.
- Guard: the existing `MfaResetTicketPresenceTests` fixture, driven by reflection, with a new test that changes
  `ticketNumber`, `listedUpn` and `methods` while the handler is suspended at its yield - and asserts the audit row
  carries the values from click time, not the later ones.
- Mutation: the ticket read moved back below the yield.
- Module `MfaReset` one minor step; no base bump.

## Guard proof

The new test is synchronous and runs the handler over a pumping `SynchronizationContext`, so the race is won on
purpose rather than hoped for: `await Task.Yield()` posts its continuation to that context, the test asserts the
handler really is suspended there (`running.IsCompleted` is false - which also fails if the yield is ever removed),
changes `ticketNumber` to "INC9999" and `listedUpn` to another address as a keystroke in that window would, and only
then pumps the continuation to completion. The authorization re-check refuses, as this fixture's always does, so the
row asserted is that refusal's - and it carries the ticket and the target from click time.
