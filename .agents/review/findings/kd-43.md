## Approach (to be written by the implementing agent before code)

- A separate tracker for the fallback; if the Set failure is `OutcomeUnknown`, stop and return Unconfirmed, never attempting Add; fall back only on a known Exchange "no existing permission" refusal; tests for the drop-then-preflight shape; mutation: shared tracker restored.

The implementing agent's (aud-a70 agent, `fix/a70`, 2026-10-23), written before code. Confirmed at `d609001e`:
`Services/CalendarPermissionService.cs` 54-74 - `SetCalendarPermissionAsync` invokes `Set-MailboxFolderPermission` on the
attempt's tracker and, on ANY failure (a `catch` with no filter), clears the pipeline and invokes
`Add-MailboxFolderPermission` on the same session and the same tracker. When the Set's session drops once it is sent, the Add
meets the pre-flight error ("You must call Connect-ExchangeOnline ..."), which sets `HasRetriablePrecheckError` on the shared
tracker, and `Unanswered` (126-129) reads the attempt as "nothing ran": the plain Failed result, the row Failed, the
administrators' notice without `_UNCONFIRMED`.

- The Set runs on a tracker of its own (`set`) and its catch is filtered:
  `when (!OutcomeUnknown(setFailure, set) && NamesNoPermissionEntry(setFailure))`. A Set whose failure the attempt reads as
  its session's (`ExchangeServiceBase.OutcomeUnknown`: a connection or transport failure, not the pre-flight error) is never
  followed by an Add: the exception leaves, `RunAsync` makes it the failed result, and `Unanswered` returns it Unconfirmed.
  That test comes first, whatever the failure's words.
- The Add follows only Exchange's answer that the user holds no entry on the folder - `NamesNoPermissionEntry`, new,
  `internal static`: "no existing permission entry" in the message or the captured errors, or the
  `UserNotFoundInPermissionEntry` identifier, anywhere in the inner-exception chain. Any other refusal is the write's own
  answer and stands Failed with no Add sent (the catch-all also sent an Add after every refusal and reported the Add's error
  in place of the Set's).
- The Add runs on a tracker of its own (`add`). Both are carried to the attempt's tracker in `finally` (`Carry`, new: the
  two flags OR-ed), which the pool reads to discard the connection and `Unanswered` reads for the outcome: an Add whose own
  session drops after the no-entry answer is Unconfirmed, and one that meets the pre-flight error (nothing ran, and the Set
  had been refused) is Failed.
- Labelled assumption, not probed: Exchange Online's no-entry refusal reads "There is no existing permission entry found for
  user: ..." and carries `UserNotFoundInPermissionEntryException`; the existing fixture
  (`CalendarPermissionWriteIdentityTests.ASetThatFallsBackToAdd_AddsOnTheValidatedMailboxsCalendar`) uses that text. If the
  live words differ, a set for a user with no entry fails with Exchange's words instead of adding: fail closed, nothing
  written, the refusal shown.
- Tests (`PermissionWriteSubmissionTests`): the drop-then-preflight shape is Unconfirmed with no Add sent; the no-entry
  answer adds; any other refusal is Failed with no Add; a failure whose words name no entry but whose session dropped sends
  no Add; the fallback Add's own failure read on its own (session lost: Unconfirmed; pre-flight: Failed);
  `NamesNoPermissionEntry` reads only the no-entry answer, in the captured errors and in an inner exception.
- Mutations: M43 the shared tracker restored with the catch-all fallback (the `d609001e` code); E43a the no-entry condition
  dropped; E43b only the separate trackers replaced by the shared one, the filter kept; E43c the session-first condition
  dropped.
- Not in scope: the on-premises script's own Set-then-Add (`SetCalendarPermissionOnPremAsync`, about 384) runs both commands
  server-side inside one `Invoke-Command`, so a dead session cannot reach its Add; a broken session fails the whole command,
  already read Unconfirmed (aud-a70 (14)).

**E43b survived, and that is reported rather than papered over.** With the filter in place the two trackers are
behaviourally equivalent on this path today, so no test can tell them apart: the Add runs only after Exchange's no-entry
answer, which sets no flag, and every step above the write (`BindValidatedMailbox`, `ValidateRecipient`,
`GetCalendarFolderName`) goes through the throwing `Invoke`, so a classified failure there leaves the operation before the
write and cannot reach the attempt's tracker un-thrown. The separate trackers are isolation for what comes later, not for
what happens now: they keep `OutcomeUnknown(setFailure, set)` reading the Set's own invoke, so a step added above the write
that classifies WITHOUT throwing (`InvokeBestEffort` does exactly that) cannot silently turn an ordinary Exchange refusal
into "the session dropped" and skip the fallback. The behaviour the finding is about is pinned by M43, E43a and E43c.
