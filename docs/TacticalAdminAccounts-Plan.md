# Tactical Admin Accounts Plan

Status: In progress - not ready for implementation
Owner: Michael
Last verified against code: eb017102160665c45ec49cbc030eb4dfa651a264 / 2026-10-23

## Exec summary

Build a disabled-by-default incident-response module for a very small security-leadership audience to create and manage tactical Microsoft Entra ID admin accounts. Version 1 should make Global Administrator the expected configured access, preferably through native time-bound PIM active assignment so access can expire even if this app is down, while leaving room for later predefined lesser options after stakeholders have used the first release. Credentials are generated by the app, shown once on the page, and never saved; any later reset, reactivation, or recreation generates fresh credentials and shows them once. These accounts are not tied to employees and have no owner mailbox or employee ID. The operator supplies an arbitrary identifier such as an incident codename or task marker so audit, notifications and the account list can group related accounts and support cleanup by identifier. Anyone trusted with this module can create, reset credentials, disable, delete, reactivate, recreate, and clean up tracked tactical accounts; do not split those actions into separate module permissions. At creation, the operator chooses a duration and the expiration action. Expiration may revoke access, disable the account, or delete the Entra account, but it never removes the saved row from the app list. Rows stay in the app until a module user explicitly deletes the saved record, and a row whose Entra account was deleted can be used to recreate the account from saved identifier, purpose and access settings with a new duration and fresh credentials. The cost and risk are high: the module's dedicated Graph credential is tenant-takeover-class for the accounts it creates, needs privileged role-management and admin-user password/account permissions, and its configuration lives in the shared dev/prod config database. Approving this plan approves the module scope; under `AGENTS.md`, coding still waits for an explicit implementation go.

## Constitution reconciliation

This module intentionally has no employee owner and no affected-person mailbox. Before implementation, record a durable owner ruling that tactical accounts created by this module are not affected-user notification targets; mutating actions still require administrator/security notification.

Protected-principal handling remains required, but this plan must not pretend the current protected-principal list fully fences cloud-only tactical accounts. Current Cloud Password Reset planning records the known gap: cloud-only accounts cannot be entered as protected principals today, so the existing check is not armed for this population unless platform support is added first. Implementation must run the current protected-principal flow where it can, fail closed when its required lookup/config is unavailable, and state this gap in operator/setup docs. A real cloud-only protection fence, or any cleanup bypass for tracked tactical accounts, needs a named owner ruling before implementation.

Normal list/filter reads are operational lifecycle reads for this mutating module. They should be audited but should not send administrator alerts unless the owner classifies them as security-response read alerts; mutating create, disable, delete, bulk, refusal, denial and partial outcomes always notify.

Automatic expiry processing is a governance exception, not ordinary page code. The app previously removed an unattended hosted worker that mutated directory state under a synthetic actor, and the shared config database can be read by more than one app instance. Before implementation can ship timed disable/delete actions, the owner must record the allowed actor model and the single-runner mechanism. Without that ruling, version 1 may still use native time-bound access assignment, but app-driven timed disable/delete must stay out of enabled expiration choices.

## 1. Goal

Create a new `TacticalAdminAccounts` module for security-team leadership to create, track, reset credentials for, disable, delete, reactivate and recreate tactical cloud-only Microsoft Entra ID admin accounts used for specific incident-response or security tasks.

The account is not owned by an employee, has no `employeeId` requirement, and is not delivered to any user's mailbox. The app generates the credential and reveals it once on the page to the authorized operator after the account is created, reset, reactivated, or recreated. The module records an arbitrary operator-supplied identifier with every created account so related accounts can be found later, including quick cleanup such as "delete all accounts for identifier X".

The module uses the current Microsoft name, Microsoft Entra ID. Operator-facing copy may mention Azure AD only as secondary familiarity text.

## 2. Non-goals

- No employee owner selection, owner mailbox lookup, `employeeId` stamping, or employee/affected-person notification to a mailbox.
- No Temporary Access Pass delivery in version 1 unless a later owner ruling adds it.
- No ServiceNow validation or external ticket validation. The identifier is arbitrary text metadata, not a gate.
- No on-premises AD account creation.
- No guest or B2B invitation creation.
- No licensing, mailbox creation, Exchange mailbox conversion, or Intune device enrollment.
- No bulk creation or bulk reactivation of accounts in version 1.
- No arbitrary Graph role ID, group ID, UPN domain, or password typed by the operator at creation time.
- No delegated Graph flow where the signed-in operator acts directly against Microsoft Graph. The app continues to use app-only Graph credentials from this module's own PAM secret.
- No lifecycle management for accounts this module did not create.

## 3. Acceptance criteria

- AC1: The module is registered as `TacticalAdminAccounts`, route `tactical-admin-accounts`, category `ModuleCategories.IdentityAndAccess`, disabled by default, non-system, version `1.0.0`, and its module permission is fail-closed.
- AC2: The module exposes one module permission for its small security-leadership audience. That permission grants the full module surface: list, create, reset credentials, disable, delete account, reactivate, recreate and remove saved records. Each mutating operation re-checks that module permission server-side immediately before the Graph write or saved-record deletion.
- AC3: The module uses only its own `GraphDelineaSecretId` and never borrows a Graph secret, Delinea secret, token, or client from another module. Missing, corrupt, unreadable, incomplete, or under-privileged config refuses before any Graph write. Setup documentation must list the expected dedicated app registration, Graph application permissions, consent actor, Delinea fields, and service-principal directory role assignments before implementation starts.
- AC4: Each created account requires a non-blank arbitrary identifier. The identifier is not externally validated and is not a security gate. It is stored with the account record, included in audit records, included in administrator/security notifications, displayed in the module's account list, and available as a filter for lifecycle actions.
- AC5: Each created account requires a non-blank purpose/task note. The note is audit metadata and operator context, not an external validation gate.
- AC6: The tactical account UPN is generated from configured naming rules and an allowed configured domain. The operator cannot type an arbitrary UPN or domain. Collision checks include active users and recoverable deleted users; a collision refuses unless a later approved revision defines a deterministic collision policy.
- AC7: Before the first Graph write, the module stores a pending local record for the intended account creation. It creates a cloud-only member user through Microsoft Graph, stamps a non-secret Entra-side marker if a verified writable marker exists, and verifies the created object by Graph object ID before any later step relies on it. If Graph cannot prove the object ID, the run refuses and records cleanup status.
- AC8: Account access is constrained by module configuration, not operator-entered role IDs. Version 1 expects Global Administrator as the default configured access set, with room for later predefined lesser options after stakeholder use. Any access selection is available to operators holding the module permission; it is not a per-request approval gate.
- AC9: The app generates the initial password by reusing the existing password generator path unless implementation proves it cannot satisfy Entra policy. The password is shown once on the page only after successful creation, tracking, and configured access assignment. It is never emailed, audited, traced, logged, stored locally, included in administrator/security notification, or retrievable later from the app. Force-password-change-at-next-sign-in is an operator-visible creation option, default unchecked for this tactical workflow unless owner/stakeholder validation changes the bootstrap model, and the selected value is audited.
- AC10: The account record exists before account creation and is updated as Graph state becomes known. It includes a local record ID, intended UPN, Graph object ID when known, deleted-item ID when known, identifier, purpose, access tier or configured access set, native access assignment IDs/expiration where used, force-change choice, expiration action, duration/expiration UTC, created by, created IP, created UTC, current lifecycle status, last observed Graph state, last action, and last action UTC. It stores no credential material.
- AC11: The account list shows all saved module-created accounts and supports filtering by identifier, status, UPN, creator, and creation/expiration windows. Rows are not removed automatically when the Entra account expires, is disabled, is deleted by the module, or is deleted out of band.
- AC12: Authorized operators can reset credentials for a saved tactical account from the module. Reset re-checks the module permission immediately before the Graph write, generates a fresh password, reveals it once on the page, stores no credential material, audits the attempt, updates the local record, and sends administrator/security notification.
- AC13: Authorized operators can disable a saved tactical account from the module. Disable re-checks authorization immediately before Graph writes, removes configured access before disabling where Graph permits, revokes sign-in sessions where supported, audits the attempt, updates the local record, and sends administrator/security notification.
- AC14: Authorized operators can delete a saved tactical account from the module. Delete re-checks authorization immediately before Graph writes, removes configured access before deleting where Graph permits, revokes sign-in sessions where supported, audits the attempt, updates the local record, and sends administrator/security notification. Version 1 delete means Microsoft Graph user delete into the recoverable deleted-user state, not permanent purge, unless a later owner ruling adds purge. A successful manual delete removes the saved row from the app list only after Graph confirms delete/recoverable-deleted state or confirms the account is already absent. A failed or indeterminate delete keeps the row with the exact state.
- AC15: Authorized operators can reactivate or recreate a saved tactical account. If the Entra account still exists, reactivation re-enables it, grants the configured access, applies a newly selected duration/expiration action, generates fresh credentials and reveals them once. If the Entra account no longer exists, recreation creates a new account from the saved identifier, purpose and access settings, applies a newly selected duration/expiration action, generates fresh credentials and reveals them once.
- AC16: Authorized operators can run bulk cleanup actions against module-created accounts matching an identifier, after a preview and typed confirmation. Per-account results are tracked individually; partial success is explicit. Bulk cleanup supports at least disable, delete account/remove saved row, and remove saved rows for already-absent accounts.
- AC17: At account creation, the operator selects a duration and an expiration action. Expiration actions are configured choices such as remove configured access, disable account, or delete account. For Global Administrator access, native time-bound PIM active assignment is the preferred access-removal floor when available, so privilege ends at the deadline even if the app is unavailable. App-driven disable/delete expiration actions require the governance ruling named above and a single-runner mechanism before they can be enabled. Expiration processing never removes the saved row from the app list; the row remains for recall, audit context, reactivation, recreation, or explicit saved-record deletion.
- AC18: Administrator/security notification is sent for every mutating attempt: create, reset credential, disable, delete, reactivate, recreate, bulk cleanup action, expiry action, denial, refusal, partial completion, and compensation failure. Notification failure is logged and audited as a notification gap, but it does not rewrite the backend outcome.
- AC19: Every Graph write is audited with actor, IP, action, account UPN and object ID when known, identifier, purpose, configured access set/tier, expiration action, expiration UTC, result, refusal reason or partial state, and sanitized Graph status/error. Scheduled expiry actions must record the configured scheduler actor plus the original creator and the authorization/ruling basis used for the unattended write. Saved-record deletion is also audited. Secrets and credentials are never audit fields.
- AC20: Operation trace records show sanitized milestones: config read, Graph credential load, authorization re-check, identifier/purpose validation, UPN generation, pending local record write, user create, object-ID verification, access assignment, credential reveal marker, credential reset, access removal, session revocation, disable/delete actions, reactivation/recreation, expiry action processing, saved-record deletion, and compensation. Raw Graph payloads, OAuth responses, tokens, generated passwords, and PAM responses are excluded.
- AC21: Partial success is explicit. If the user is created but access assignment, local record write, notification, reset, disable, delete, reactivation, recreation, expiry action, or cleanup fails, the result says exactly what exists in Entra ID and what manual remediation remains. It must never collapse a multi-step run into blanket success or blanket no-change.
- AC22: Credentials are revealed once per create, reset, reactivation, or recreation result. Reloading the page, switching rows, opening account detail later, reading audit, or reading the local tracking table cannot retrieve the credential.
- AC23: The page displays `<ModuleVersion />`, follows the current module authorization pattern, keeps controls disabled while busy, and prevents direct event paths from bypassing the same server-side gates.
- AC24: Because this module adds shared config-store schema and likely a runner/setup surface beyond a pure module descriptor/page, implementation bumps the base app version as well as setting the new module's version.

| --- | --- | --- | --- |

| Mutating permission re-check | Denies or cannot evaluate | Action refused | No Graph write; denial audited |
| Module config read | Missing, corrupt, or invalid | Configuration error naming the bad setting | No Graph call |
| Graph secret load | Missing, unreadable, or incomplete | Module not configured / credential unavailable | No Graph token requested; no Graph call |
| Identifier missing | Required metadata refusal | Identifier required | No Graph call |
| Purpose missing | Required metadata refusal | Purpose required | No Graph call |
| Access set config invalid | Config refusal | Access configuration unavailable | No Graph call |
| Required Graph permission or service-principal directory role missing | Setup preflight refuses | Module credential lacks required tenant privileges | No Graph write |
| Duration or expiry action missing/invalid | Required lifecycle selection refusal | Duration and expiry action required | No Graph call |
| UPN generation/collision check | Config invalid, active UPN exists, or recoverable deleted user reserves the UPN | Naming refusal | No Graph write |
| Pending local record write | Database unavailable or refuses | Tracking unavailable; creation refused | No Graph call |
| `POST /users` | Graph rejects or times out before a response | Account creation failed or indeterminate, depending on status | No later access/credential steps; if indeterminate, lookup by intended UPN before reporting |
| Created-object verification | Graph cannot re-read the created object ID | Verification failed | Update pending record if possible; attempt disable/delete by object ID if known; record cleanup result |
| Local record update after create | Fails after Graph create | Tracking update failure | Report partial/manual remediation; account has no configured access yet; attempt disable/delete and record exact residue |
| Access assignment | One role/group assignment fails | Partial grant failure | Attempt to remove any successful assignments, revoke sessions where supported, and disable/delete the new user; record exact residue |

| Expiry processor unavailable | Due action cannot run on time | Account overdue; cleanup action pending or failed | Native time-bound access still expires where used; saved row remains; processor catches up when available |
| Expiry processor not authorized by governance/single-runner config | Timed disable/delete would be unattended or could double-run | Expiry action unavailable or pending manual cleanup | No app-driven timed disable/delete write |
| Expiry action | Remove-access, disable or delete action fails or is indeterminate | Expiry action failed or unknown | Saved row remains with exact action state |
| Audit write | Fails after backend operation | Operation result stands; audit gap logged | Backend state unchanged; separate audit failure log |
| Admin/security notification | Fails | Operation result stands; notification gap shown/logged | Backend state unchanged |
| Disable/delete/reactivate/recreate write | Access removal, session revoke, account disable, account delete, re-enable, recreate or access regrant rejects/times out | Action failed or indeterminate | Local record marks exact failed/unknown state and requires manual follow-up |
| Saved-record delete | Record cannot be removed after requested cleanup | Record deletion failed | Graph outcome stands; saved row remains with cleanup state |
| Bulk cleanup loop | Some rows fail | Per-row partial result table | Successful rows remain changed; failed rows retain previous/unknown state |
| Compensation cleanup | Delete/disable/revoke fails | Partial failure with manual remediation required | Exact known Entra residue recorded locally and in notification |

Preferred create ordering:

1. Validate authorization, config, identifier, purpose, duration, expiry action, naming, protected-principal status and access set.
2. Write a pending local tracking record keyed by a surrogate local ID and intended UPN.
3. Create the account enabled with a generated password, but with no configured admin access yet.
4. Verify the created object by Graph object ID and update the pending record.
5. Stamp a non-secret Entra-side marker if implementation verifies a writable marker field/extension.
6. Assign the configured access last.
7. Refresh and persist the assigned-access state.
8. Reveal the password once on the page.
9. Audit and send administrator/security notification without the password.

The account starts enabled with no configured admin access, then receives access only after tracking and object-ID verification. This ordering reduces failure residue and makes cleanup easier; it does not reduce the module credential's required privilege, because reset, disable, delete and access lifecycle actions against admin accounts still need privileged Graph setup. The password is not revealed until tracking and access assignment are complete.

Expiration is a selected lifecycle action, not saved-record removal. At creation the operator chooses a duration and an expiry action. For Global Administrator, the preferred implementation is a native time-bound PIM active assignment ending at the selected expiration time, plus app tracking of the chosen expiry action. When the duration elapses, the module runs the selected follow-up action where allowed by governance: remove configured access, disable the account, or delete the Entra account. The saved row remains after any expiry action so leadership can see what happened, reactivate or recreate the account, and remove the row only by explicit delete from the module list.

## 5. Rollback / blast radius

Rollback of the source change is ordinary app rollback: remove the module build and restart the app. Runtime config and account tracking records remain in the shared config database and must not be deleted automatically by rollback.

The production blast radius is tenant-wide identity state for tactical accounts created by this module. A bad configured access set can create overpowered accounts, and the module's Graph application credential is expected to need privileged role-management, password-profile, user lifecycle, and admin-user write authority. Because runtime config is the shared dev/prod database, changing this module's access-set config changes production behavior immediately. A broken cleanup path can leave incident-response accounts active. A broken reveal path can lose the only copy of the generated credential. A broken expiry runner can either fail to clean up or run the same due action from more than one app instance. The mitigations are disabled-by-default module enablement, fail-closed section access, fixed configured access sets, no operator-entered role IDs, native time-bound access where available, single-runner expiry control, tracking intent before Graph create, local tracking by object ID, bulk cleanup by identifier, access removal before disable/delete, no credential storage, and live validation with disposable accounts before production use.

Operational rollback for a bad account is in scope for the module: find it by identifier or UPN, disable it, delete it if appropriate, and record the remediation. Accounts this module did not create are intentionally out of scope.

## 6. Design sketch

### Module descriptor

Proposed descriptor:

- Id: `TacticalAdminAccounts`
- DisplayName: `Tactical Admin Accounts`
- Route: `tactical-admin-accounts`
- Category: `ModuleCategories.IdentityAndAccess`
- EnabledByDefault: `false`
- IsSystemModule: `false`
- Version: `1.0.0`
- Main permission alias: `TacticalAdminAccounts`

Main permission description should say it grants the full tactical-account management surface for the module: list, create, reset credentials, disable, delete, reactivate, recreate, bulk cleanup by identifier, and saved-record removal. Do not add separate create/reset/delete permissions unless a later owner ruling changes the audience model.

Config fields:

- `GraphDelineaSecretId`, required.
- `AllowedUpnDomain`, required. One verified Entra domain for tactical account UPNs.
- `AccountLocalPartFormat`, required. Limited token format such as `tac-{yyyyMMdd}-{sequence}`. Do not include the operator-supplied identifier in the default UPN format; incident codenames and task markers can become tenant-visible if embedded in an address. Parser must fail closed on unknown tokens or illegal characters.
- `DefaultDurationHours`, optional text parsed as integer. The create page may prefill this value, but the operator can change it.
- `MaxDurationHours`, optional text parsed as integer. If blank, the module has no hard maximum duration. If configured, it is a policy cap and must be visible before create.
- `AllowedExpirationActions`, required. Initial choices are remove configured access, disable account, and delete Entra account. Delete means recoverable Microsoft Graph user delete in version 1, not permanent purge. App-driven timed disable/delete choices stay disabled until the scheduled-runner governance ruling exists.
- `AccessMode`, required. Version 1 expects one fixed Global Administrator access set unless implementation receives a later owner ruling for named lesser options. Global Administrator should use native time-bound PIM active assignment when available; a direct unbounded role assignment requires an owner ruling because the app would be the only expiry enforcement. Exact role/group IDs live in structured access-set storage or an AdminGroups-only config surface, not operator text boxes.
- `ForceChangePasswordNextSignInDefault`, optional Boolean, default `false` for this tactical workflow. The operator can change it per create/reactivate/recreate/reset where Graph supports the flag.
- `SecurityNotificationRecipients`, optional override. If empty, the module uses the existing administrator notification path; if neither the override nor the global administrator notification path can resolve recipients, mutation results must record a notification gap.

If integer config remains text because the catalog has no numeric field type, implementation must use a bounded parse helper and refuse invalid non-empty values. Do not read invalid numbers as defaults.

Single-runner expiry control must not live only in shared module config, because dev and prod share the runtime config database. Use per-instance appsettings, a durable claim with expiry, or another owner-approved mechanism that prevents both app instances from processing the same due row.

  - `force_change_password_next_sign_in`
  - `expiry_status`
  - `expiry_claimed_by`, nullable
  - `expiry_claimed_at_utc`, nullable

  - `created_step`
  - `created_by`

Optional access-set storage, if more than one access tier is in scope:

  - `access_set_id` primary key
  - `display_name`
  - `description`
  - `enabled`
  - `max_duration_hours`
  - `updated_at`

The tracking table is authoritative for what the module is allowed to manage: lifecycle actions operate only on rows this module created or recreated. Entra remains authoritative for actual account state, so list/detail views should refresh observed state from Graph where practical and mark stale/unavailable observations clearly. If the account is missing in Entra, the saved row remains with `current_object_id` cleared and `last_known_object_id` retained for audit context.

Manual or expiry-triggered deletion of the Entra account never automatically deletes the saved row. A saved row is removed from the app list only when a module user explicitly selects delete/remove for that row and the module can either confirm the Entra account was deleted/recoverable-deleted by that action or confirm it is already absent from active and deleted-user lookups. Failed or indeterminate cleanup keeps the row.

Version 1 does not permanently purge deleted Entra users or restore deleted users. Recreate checks active users and recoverable deleted users before choosing a UPN. If the previous UPN is reserved by a deleted item, the module creates the next generation with a new generated UPN; it does not purge the deleted item to free the name without a later owner ruling.

If implementation verifies a safe writable Entra-side marker, the module must include a reconciliation view for marked Entra accounts missing from the local table. If no such marker is available, this plan must be amended before implementation claims crash reconciliation beyond the local pending records.

### Page

The page is the operational workflow:

1. Create panel:
   - Identifier, required arbitrary text.
   - Purpose/task note, required.
   - Duration, required, prefilled from config when available, not hard-capped unless `MaxDurationHours` is configured.
   - Expiration action, required, chosen from configured options such as remove access, disable account, or delete Entra account.
   - Access tier only if more than one configured tier exists.
   - Force password change at next sign-in, defaulting from module config and operator-visible.
   - Preview generated UPN, expiration time and expiration action.
   - Typed confirmation using the generated UPN.
   - Create button.
2. Result panel:
   - Created account UPN/object ID.
   - Generated credential shown once for create, reset, reactivation, or recreation.
   - Copy control for the credential if allowed by browser/UI pattern.
   - Clear/dismiss action that removes the credential from UI state.
3. Account list:
   - Filter by identifier, status, UPN, creator and date/expiration windows.
   - Show active, disabled, expired, recoverable-deleted, no-longer-extant, partial and unknown rows.
   - Per-row reset credential, disable, delete, reactivate/recreate, and saved-record remove actions.
   - Bulk preview by identifier for cleanup actions, with typed confirmation.

The page must include `[Authorize(Policy = "TacticalAdminAccounts")]`, explicit initialization authorization, `<ModuleVersion />`, `ClientInfoService`, and one busy predicate that covers create/list/lifecycle operations so a second action cannot invalidate the staged result.

### Service

Create `TacticalAdminAccountService` as a scoped service unless implementation proves singleton is correct. The create method takes:

- `ClaimsPrincipal actingUser`
- actor name and IP, captured before the write
- identifier
- purpose
- requested duration
- expiration action
- access set ID, if more than one exists
- force password change at next sign-in
- confirmation token

It does not take role IDs, group IDs, UPN domain, password, recipient address, owner identity, employee ID or Temporary Access Pass value.

The service performs create, reset credential, disable, delete, reactivate, recreate, expiry action and bulk cleanup flows with sanitized `OperationTraceService` steps and typed result objects. It reuses the existing `PasswordGenerator` path unless implementation proves it cannot satisfy tenant password policy. The page handles rendering only; it does not own Graph sequencing or compensation.

### Graph surface

Prerequisites and API assumptions to verify before implementation:

- Microsoft Entra ID is the current product name replacing Azure Active Directory / Azure AD / AAD.
- The module uses a dedicated single-tenant app registration and service principal stored only through this module's `GraphDelineaSecretId`.
- The setup checklist must name the exact Microsoft Graph application permissions and directory roles required for: user create/read/update/delete, password-profile write, sign-in session revocation, active/deleted-user collision checks, role/access assignment, native time-bound PIM active assignment where used, and access removal.
- The expected permission family includes user lifecycle write, password-profile write, sign-in-session revoke, and role-management/PIM-schedule write authority. For Global Administrator credential reset or lifecycle writes, use the Cloud Password Reset precedent: the service principal must hold the directory role required for privileged admin-user password/account operations, such as Privileged Authentication Administrator where Microsoft requires it. Missing role/permission preflight is a setup refusal, not a partially attempted create.
- The setup doc must name who can grant consent and role assignments, the Delinea fields, dry-run behavior if helper tooling is updated, and the manual setup path if this module is too privileged for automatic provisioning.
- Create user is `POST /users`; application permission `User.Create` may be least privileged for basic user creation, but this module also needs later lifecycle and access-assignment writes, so the setup preflight must validate the whole configured access shape before the create page enables writes.
- Setting the initial password uses `passwordProfile` in the create body. Tenant password policy can reject generated passwords; use the existing Cloud Password Reset rejection/indeterminate-outcome patterns rather than inventing a new error model.
- `forceChangePasswordNextSignIn` is an operator-visible option. The version 1 default recommendation for tactical accounts is `false` unless an approved sign-in bootstrap exists, because first-sign-in password-change and MFA registration can block the immediate-response use case.
- Credential reset uses the same Graph password-profile pattern as Cloud Password Reset, by object ID, and reveals the new credential only after Graph confirms the change.
- Disabling uses `PATCH /users/{id}` with `accountEnabled = false`; reactivation uses `accountEnabled = true` on an existing tracked account.
- Deleting uses `DELETE /users/{id}` and is treated as recoverable delete in version 1. Permanent deletion/purge is out of scope without a later owner ruling.
- Recreation uses the saved row as the source for identifier, purpose and configured access shape, but creates a new Entra account and new Graph object ID. It requires a newly selected duration and expiration action and generates fresh credentials. It checks active users and recoverable deleted users before choosing the UPN for the new generation.
- Access assignment depends on the configured access type. Directory role assignment, role-assignable group membership, PIM eligibility, or PIM activation each needs its own verified permission, licensing check, and live tenant check. Global Administrator should be granted through a native time-bound PIM active assignment when the tenant and Graph permissions support it. Direct role assignment or role-assignable group membership without native expiry requires a named owner ruling because the app would be the only enforcement path.
- Expiration has two layers. Native time-bound access ends the privileged access where available. The module's expiry processor records the due action and applies the selected follow-up action only where governance has approved unattended processing and single-runner controls.
- Revoke sign-in sessions before disable/delete where Graph supports it for the account type and permission set.

Any Graph permission widening beyond the stated setup list and configured access set is a plan amendment.

### Create sequence

1. Capture actor, IP, identifier, purpose, requested duration, expiration action, access set, force-change choice and confirmation text into locals.
2. Read module config and access set, fail closed.
3. Validate identifier and purpose are non-blank and within length limits.
4. Generate and collision-check the UPN against active users and recoverable deleted users.
5. Run the protected-principal check for the intended cloud address where the current service can evaluate it; fail closed if the check cannot run.
6. Write a pending local account record before any Graph write.
7. Re-check the module permission immediately before the first Graph write.
8. Create the Entra user enabled with generated password and no configured admin access.
9. Re-read the created user by object ID and update the local record with the object ID.
10. Stamp the verified Entra-side marker, if available.
11. Assign configured access last, using native time-bound PIM active assignment for Global Administrator where available.
12. Refresh assigned access and update the local record.
13. Reveal the generated credential once in the returned result.
14. Write success audit and administrator/security notification without the credential.

Every step after user creation has compensation. Compensation must be best-effort but explicit. A failed compensation step turns the result into partial/manual-remediation, never success.

### Disable/delete sequence

1. Select only local account records created by this module.
2. Refresh observed Graph state where practical.
3. Capture actor, IP and target object ID into locals.
4. Run the protected-principal check for the tracked object/address and fail closed if the check cannot run or matches, unless a later owner ruling creates a cleanup exception.
5. Re-check the module permission immediately before each Graph write.
6. Remove configured access first where Graph permits.
7. Revoke sign-in sessions where supported.
8. Disable or recoverable-delete by Graph object ID, never by mutable UPN.
9. For manual delete, remove the saved row only after Graph confirms recoverable-deleted state or confirms the account is already absent from active and deleted-user lookups.
10. For disable, and for failed or indeterminate delete, update local status and last-action fields and keep the saved row.
11. Audit and notify with identifier and purpose.

Bulk cleanup actions perform the same sequence per row and aggregate per-row results. They must never report blanket success when one row fails.

### Credential reset sequence

1. Select only a saved local account record created or recreated by this module.
2. Refresh observed Graph state by object ID where present, or by intended UPN only to determine whether the account still exists.
3. Refuse reset if the account is no longer present; offer recreation instead.
4. Capture actor, IP and target object ID into locals.
5. Run the protected-principal check for the tracked object/address and fail closed if the check cannot run or matches, unless a later owner ruling creates a cleanup exception.
6. Re-check the module permission immediately before the Graph password write.
7. Generate a fresh password and send the password-profile update with the operator-selected force-change setting where Graph supports it.
8. Reveal the new password once only after Graph confirms the update.
9. Update `last_credential_reset_at_utc`, audit, and notify without the password.

### Expiry action sequence

1. Native time-bound access assignment, where used, ends privileged access at the selected expiration time without waiting for the app.
2. A durable expiry processor finds saved rows whose expiration UTC has passed and whose expiry action is still pending.
3. Before any app-driven disable/delete write, it verifies the owner-approved scheduler actor model and acquires the single-runner claim for the row. Without that governance/config, the row remains overdue pending manual cleanup.
4. It refreshes observed Graph state. If the account is already absent from active and deleted-user lookups, mark the expiry action complete with no Graph write and keep the saved row.
5. It reuses the same protected-principal, access-removal, session-revocation, disable and recoverable-delete primitives as manual actions.
6. It records per-account success, failure or indeterminate state and sends administrator/security notification naming the scheduler actor and original creator.
7. It never removes the saved row from the app list, even when the selected action deletes the Entra account.

If the app is down at the expiration time, native access expiry still applies where available. The processor runs due follow-up actions when the app next starts or the processor next wakes. The UI must make overdue pending actions visible.

### Reactivation/recreation sequence

1. Select a saved row and require the operator to choose a new duration and expiration action.
2. Refresh observed Graph state.
3. If the account exists, re-enable it if disabled, reset credentials with the selected force-change setting where Graph supports it, grant or refresh configured access, update expiration fields, reveal the fresh credential once, audit and notify.
4. If the account is absent, increment `generation`, create a new account from the saved identifier, purpose and access settings, choose a UPN that is free across active and recoverable deleted users, store the new object ID, apply the selected duration and expiration action, reveal fresh credentials once, audit and notify.
5. Failed or indeterminate reactivation/recreation keeps the saved row with exact residue.

### Credential reveal

The generated password is returned only in the create, reset, reactivation or recreation result object and only for immediate rendering. It is not stored in the local account table, not written to audit, not sent in administrator/security notification, not logged, not traced and not retrievable after the result is dismissed or the page reloads.

A successful credential-bearing result should make clear that this is the only time the credential will be displayed. If the operator loses it, the remediation path is to reset the credential from the saved account row, or reactivate/recreate from the saved row when appropriate; this module must not have a hidden credential cache.

Temporary Access Pass is out of scope for version 1 unless the owner explicitly changes the delivery model. The v1 delivery model is generated credential shown once on the page. MFA and first-sign-in password-change behavior are deployment prerequisites to validate with disposable accounts, not reasons to add an unplanned delivery path.

## 10. Owner guidance and remaining implementation rulings

The owner guidance already settled by this plan:

- The audience is a very small security-leadership group, not helpdesk, normal administrators, or the general user community.
- Module access is the management boundary. Do not split create, reset, delete, reactivate, recreate or cleanup into separate module permissions for version 1.
- Version 1 should expect Global Administrator as the main configured access. Lesser predefined options may be added later after stakeholder feedback from the first release.
- Credentials are delivered on the page only. They are never saved; reset, reactivation and recreation always generate fresh credentials.
- Duration is selected at creation together with an expiration action. A maximum duration is optional configuration, not a hard requirement of the module.
- Expiration may remove access, disable the account, or delete the Entra account, depending on what the operator selected at creation.
- Expiration actions and out-of-band deletion never remove saved rows automatically. Rows leave the app list only when a module user explicitly deletes/removes the saved record through the module.
- A saved row for a missing Entra account remains useful: reactivate/recreate uses the saved identifier, purpose and access settings and asks for a new duration/action.

Implementation still needs repo-governance records before coding. First, tactical accounts created by this module have no affected-user notification target because they are not tied to a person, so administrator/security notification is the notification path. Normal list/filter/refresh reads should be classified audited-only; mutating actions and expiry actions notify. Protected-principal behavior remains fail-closed unless the owner later grants a narrow cleanup exception for tracked tactical accounts.

Implementation also needs explicit owner rulings before timed disable/delete can ship:

- The allowed actor model for an unattended expiry write.
- The single-runner mechanism when dev and prod share config storage.
- Whether any direct unbounded Global Administrator assignment is allowed if native time-bound PIM active assignment cannot be used.
- Whether permanent deletion/purge of deleted Entra users is ever in scope. Version 1 says no.
- Whether to add platform support for protecting cloud-only principals, or to accept that the current protected-principal fence is not armed for this module-created population.
